STEP 1fetch.min.bytes trades latency for batching

Proves: the fetch is a broker-side wait, not a client-side poll.

Predict first

A consumer with fetch.min.bytes=100000 and fetch.max.wait.ms=2000 is subscribed to a quiet topic. One 16-byte record is produced. How long before the consumer sees it?

Run

python3 01_fetch_tuning.py 1 500
python3 01_fetch_tuning.py 100000 2000

Expected

fetch.min.bytes=1       fetch.max.wait.ms=500    first record after      ~5 ms
fetch.min.bytes=100000  fetch.max.wait.ms=2000   first record after    ~2000 ms

Why

The broker holds the fetch request open until it has fetch.min.bytes to return or fetch.max.wait.ms elapses. One small record satisfies neither condition, so the consumer waits out the full timeout. This is a long-poll, and the latency is on the broker side — no amount of polling faster helps.

The practical reading: fetch.min.bytes is a throughput optimisation that costs tail latency exactly when traffic is thin, which is the mirror image of linger.ms on the producer. On a busy topic it is nearly free; on a quiet one it is the dominant latency term.

Check yourself

You have a low-volume topic with a 100 ms end-to-end latency requirement. What are the defaults of fetch.min.bytes and fetch.max.wait.ms, and which one would break your SLA if someone "tuned for throughput"?

STEP 2Read the offsets topic directly

Proves: consumer progress is just records in a compacted Kafka topic.

Run

python3 02_autocommit_window.py consume lab06-peek   # Ctrl+C after ~10s

docker exec lab06-kafka /opt/kafka/bin/kafka-consumer-groups.sh \
  --bootstrap-server localhost:19092 --describe --group lab06-peek

docker exec lab06-kafka /opt/kafka/bin/kafka-console-consumer.sh \
  --bootstrap-server localhost:19092 --topic __consumer_offsets \
  --from-beginning --max-messages 10 \
  --formatter 'kafka.coordinator.group.GroupMetadataManager$OffsetsMessageFormatter'

Expected

--describe gives the familiar table: current offset, log end offset, lag, and the member owning each partition. The raw topic shows records keyed by (group, topic, partition) carrying an offset and metadata.

Why

__consumer_offsets has 50 partitions and is compacted, so it converges to the current position per key — exactly the compaction behaviour from M2, applied to consumer progress. The partition a group hashes to also determines its group coordinator: the broker leading that partition. That is why a single broker going down can affect some groups' rebalances and not others.

Also note what a committed offset means: the next record the group wants, not the last one processed. Off by one here and you reprocess or skip exactly one record per commit, forever, with no error.

Check yourself

offsets.retention.minutes defaults to 7 days. What happens to a batch consumer that runs monthly, and which auto.offset.reset value makes that failure silent?

STEP 3Measure the auto-commit window

Proves: auto-commit commits what was returned, not what was processed.

Predict first

A consumer with auto-commit on processes ~100 records per second and is killed 12 seconds in. On restart, roughly how many records does it see again — 0, a handful, or hundreds?

Run

python3 02_autocommit_window.py consume lab06-ac1    # Ctrl+C after ~10s
python3 02_autocommit_window.py recount lab06-ac1

Expected

The second run replays a batch of records the first had already processed — everything since the last 5-second auto-commit tick.

Why

Auto-commit fires on a timer, during poll(), and commits the offsets that poll() returned. It has no idea whether your code finished with them. So the guarantee is at-least-once with a window of up to auto.commit.interval.ms — a window you did not choose and cannot see in any metric.

Worse in the other direction: if poll() returns 500 records and you crash after processing 10, the next poll may still auto-commit all 500 as done, and the remaining 490 are skipped. Whether auto-commit over- or under-commits depends on timing, which is the real objection to it.

The fix is enable.auto.commit=false, process, then commitSync() — the commit becomes a statement about processing, which is how everyone reads it anyway.

Check yourself

Your consumer is idempotent downstream. Is auto-commit now fine? Name the one thing you would still check before leaving it on.

STEP 4Cause a rebalance storm

Proves: heartbeats and progress are different things, and the group punishes the second.

Predict first

max.poll.interval.ms=10000, session.timeout.ms=45000, and the consumer sleeps 12 seconds per batch. The heartbeat thread is healthy the whole time. Does the consumer get evicted — and if so, which timeout fires?

Run — two terminals

python3 03_poll_interval.py 12 c1
python3 03_poll_interval.py 12 c2

Expected

Repeated REVOKED / ASSIGNED churn in both terminals. Each eviction rebalances the whole group, so the other consumer stops too, and the cycle repeats indefinitely.

Why

session.timeout.ms never fires — the background heartbeat thread is fine, because the process is alive. max.poll.interval.ms exists precisely for this: an application that is alive but not making progress. Exceed it and the coordinator removes the member.

Now the self-sustaining part. The eviction rebalances the group, so every consumer stops. Work since the last commit is reprocessed, adding load. The added load makes the next consumer exceed the interval. The group spends more time rebalancing than consuming and does not recover on its own.

The fix is almost never a bigger timeout. Lower max.poll.records so each poll-to-poll cycle is shorter and bounded — the timeout measures cycle duration, not throughput — then find out why processing slowed. Raising max.poll.interval.ms to 30 minutes ends the storm by making a genuinely stuck consumer take 30 minutes to detect: a loud failure traded for a slow one.

Check yourself

Try it: restart both with python3 03_poll_interval.py 2 c1. The sleep is now under the interval. Which setting did you effectively change, and what would the equivalent production change be?

STEP 5Eager versus cooperative sticky

Proves: an incremental rebalance revokes only what moves.

Run — three terminals, twice

# round 1: eager
python3 05_assignor_compare.py range c1
python3 05_assignor_compare.py range c2
# ...then start c3 and watch c1 and c2
python3 05_assignor_compare.py range c3

# round 2: cooperative, fresh group
python3 05_assignor_compare.py cooperative-sticky c1
python3 05_assignor_compare.py cooperative-sticky c2
python3 05_assignor_compare.py cooperative-sticky c3

Expected

With range, adding the third consumer makes c1 and c2 revoke every partition before anything is reassigned. With cooperative-sticky, they revoke only the partitions actually moving to c3 — often one each, sometimes none.

Why

Eager rebalancing is stop-the-world by construction: everyone gives everything back, rejoins, waits at a join barrier while one elected consumer computes the assignment, then receives it. Nothing is consumed throughout. Cooperative sticky (KIP-429, 2.4) splits this into two short rounds and revokes only what is moving, so a group that is otherwise healthy keeps consuming while one member joins.

The number to carry away is the revoked total printed on exit. On a 4-partition topic the difference is small; on a 200-partition topic with 20 consumers it is the difference between a deploy being invisible and a deploy being an incident.

Both of these are still client-side assignment. KIP-848 (GA in 4.0, group.protocol=consumer) moves it to the broker and removes the join barrier entirely — try it if your client build supports it, since client support lags the broker.

Check yourself

Cooperative sticky makes rebalances cheaper. Name the situation where the right answer is to have no rebalance at all, and which feature provides that.

STEP 6Static membership

Proves: a planned restart does not have to cost a rebalance.

Run — two terminals

# dynamic: no group.instance.id
python3 04_static_membership.py c1
python3 04_static_membership.py c2
# Ctrl+C c2, restart it, watch c1

# static: fresh group, both with instance ids
python3 04_static_membership.py c1 static-1
python3 04_static_membership.py c2 static-2
# Ctrl+C c2, restart within 45s, watch c1

Expected

Dynamic: c1 logs REVOKED/ASSIGNED twice — once when c2 leaves, once when it returns. Static: c1 logs nothing. The returning member reclaims its own partitions.

Why

With group.instance.id set, a member that disappears is not immediately removed from the group — the coordinator holds its assignment until session.timeout.ms expires. Restart inside that window and it resumes its old partitions with no rebalance for anyone.

This is what makes rolling deploys of a large consumer group survivable. Without it, a 20-pod rollout is 20 rebalances, each one stopping the entire group. With it, zero — provided each pod has a stable identity, which in Kubernetes means a StatefulSet or an explicitly injected ordinal rather than a random pod name.

The trade: a genuinely dead static member is not noticed until session.timeout.ms elapses, so its partitions sit idle for that long. Static membership moves you from "every restart costs a rebalance" to "every crash costs 45 seconds of that partition's throughput" — which is the right trade for a group that deploys often.

Check yourself

You set group.instance.id from the pod name in a Deployment, not a StatefulSet. What happens on the next rollout, and why is it worse than not using static membership at all?
