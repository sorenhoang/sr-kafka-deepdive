Module 0

Positioning Kafka

Before any mechanism: what Kafka actually is, what follows from that, and when the honest answer is to use something else. Most wrong answers in a Kafka interview trace back to a broken mental model at this level.

One definition, derive everything else from it

Mental model

Kafka is a distributed, replicated, append-only commit log in which the broker is only responsible for storing and serving the log, while the read position is owned by the consumer.

This is the one thing worth memorising. Every characteristic property of Kafka follows from it, so in an interview you can derive the answer on the spot instead of reciting it.

Answering “Kafka or RabbitMQ?”

Do not compare throughput. Compare the unit of state: Kafka tracks state as a stream plus an offset, RabbitMQ tracks it per message. If the problem needs control over individual messages — its own retry, its own delay, its own priority — you are fighting Kafka's design. If the problem needs one event stream that several consumers share and can replay, the opposite holds.

When not to use Kafka

  1. Low-latency request/reply. Kafka is not RPC — use gRPC or HTTP.
  2. A task queue with per-task retry, delay and priority and a worker count that swings widely — RabbitMQ, SQS or Celery fit more naturally.
  3. Fan-out to end clients (mobile, browser, millions of connections). Kafka is not client-facing; it sits behind a WebSocket or push layer.
  4. Small scale, one consumer, no replay needed. Postgres with an outbox table, or a Redis stream, costs far less to operate.
  5. Querying by message content, or updating or deleting one specific message. That is a database.
  6. Scheduled or delayed delivery. Kafka has none natively — you would build tiered delay topics or an external scheduler.

Share Groups (KIP-932) — the 2026 talking point

Share Groups reached production-ready status in Kafka 4.2. Interviews have started asking about this and many candidates have not caught up.

Module 1

Core concepts

Topic, partition, offset, replica, consumer group — and the one guarantee Kafka actually makes about ordering.

A partition is the unit of four things at once

A topic is purely logical — just a name; no file on disk is named after it. The partition is the real object: one log on disk, and simultaneously the unit of

  1. parallelism
  2. ordering
  3. replication
  4. storage and retention

Being able to say “a partition is the unit of all four” already separates you from the average candidate. A single partition cannot scale past one broker, which is why partition count is your parallelism ceiling and has to be chosen when the topic is created.

An offset is a monotonically increasing integer scoped to one partition. There is no topic-wide offset. A record is uniquely identified by (topic, partition, offset).

The assignment rule inside a consumer group

Within one group, each partition is assigned to exactly one consumer. Three partitions, four consumers:

part 0012345→ c1
part 1012345→ c2
part 2012345→ c3
—0c4 · idle, no partition assigned

So the number of useful consumers in a group is at most the partition count. Separate groups read the same topic completely independently, each with its own offsets stored in the internal __consumer_offsets topic. Groups serve both shapes — queue (consumers in one group split the work) and pub/sub (several groups read the same data) — with no separate exchange concept.

Reading the output of describe

$ kafka-topics.sh --describe --topic lab01.orders
Topic: lab01.orders  Partition: 0  Leader: 2  Replicas: 2,3,1  Isr: 2,3,1
Topic: lab01.orders  Partition: 1  Leader: 3  Replicas: 3,1,2  Isr: 3,1,2
Topic: lab01.orders  Partition: 2  Leader: 1  Replicas: 1,2,3  Isr: 1,2,3
  • Leader — the only broker that serves reads and writes for that partition. Leaders spread across the three brokers is exactly how Kafka scales writes.
  • Replicas — the replica list in preference order; the first entry is the preferred leader.
  • Isr — in-sync replicas. Isr equal to Replicas means a healthy cluster; a shorter Isr means a follower has fallen behind (M3 digs into this).

Followers behave like internal consumers fetching from the leader. The one exception is KIP-392 fetch-from-follower, where a consumer reads a rack-local replica to avoid cross-AZ traffic — a cost optimisation, not a throughput one.

Key → partition, and why adding partitions breaks ordering

partition = toPositive(murmur2(keyBytes)) % numPartitions
  • With a key, the same key always lands on the same partition — this is the only mechanism Kafka gives you for ordering related events.
  • With a null key you get the sticky partitioner: records pile into one partition until the batch fills or linger.ms expires, and only then does it switch. It is not per-record round-robin — a detail people routinely get wrong.
One-way door

Changing numPartitions changes the divisor, so roughly half the keys jump to a different partition. Old events for a key stay on the old partition while new ones go to the new one, and the consumer no longer sees that key's events in order. That is why adding partitions cannot be undone, and why there is no way to add them while preserving order — only creating a new topic and migrating deliberately.

Ordering guarantees, stated precisely

Kafka guarantees the order of records within a partition, provided the producer is configured correctly. Kafka does not guarantee order in any of these cases:

SituationWhy order is lost
Across partitions, or topic-wideNo shared clock and no global sequencer
Producer retries without idempotence and max.in.flight > 1A later request can succeed before the one being retried
Null keyRecords for the same entity spread across partitions
After increasing the partition countKeys jump partitions while old data stays behind
Consumer hands records to a thread pool after poll()Kafka delivered them in order; your code broke it
Share groups (KIP-932)Ordering traded away for parallelism
A sentence worth having ready

“Kafka gives me ordering at partition scope. For ordering at business-entity scope I have to key by entity id, enable the idempotent producer, and process each partition sequentially.”

Six common traps

“Kafka is a FIFO queue”FIFO only within a partition
“Kafka is exactly-once by default”The default is at-least-once; EOS needs transactions and only holds Kafka-to-Kafka (M7)

Module 2

Storage internals

The module that turns "Kafka is fast because sequential writes" into four separate mechanisms you can defend one at a time — and then shows what deletes data, which is where production surprises actually come from.

The log is a directory of segments

A partition is a directory named <topic>-<partition>. Inside it, the log is split into segments, each a trio of files sharing a name:

lab02.segments-0/
  00000000000000000000.log        # records
  00000000000000000000.index      # offset   -> byte position
  00000000000000000000.timeindex  # timestamp -> offset
  00000000000000000317.log        # next segment, starts at offset 317
  00000000000000000317.index
  00000000000000000317.timeindex

The filename is the segment's base offset, zero-padded to 20 digits. That is not decoration: it is the index. To find offset 400, the broker binary-searches the filenames to pick the segment, with no file opened yet.

Only the newest segment — the active segment — is open for writing. It rolls when either limit is hit: segment.bytes (default 1 GiB) or segment.ms (default 7 days). Remember both; the second one is the cause of the most common retention bug, below.

How a read resolves an offset

  1. Binary search the segment filenames → the segment containing the offset.
  2. Look up the .index → the nearest indexed offset at or below the target, giving a byte position.
  3. Scan forward in the .log from there to the exact record.

The index is deliberately sparse: one entry roughly every log.index.interval.bytes (default 4 KiB) of log, not one per record. Dense would make lookups marginally faster and cost memory proportional to record count — and these files are memory-mapped, so the index competes with the page cache for exactly the memory that makes reads fast. Sparse plus a short forward scan is the better trade, and it is why the final step is a scan rather than a direct hit.

.timeindex does the same for timestamps, which is what makes --to-datetime offset resets and time-based seeks possible.

The batch is the unit, not the record

Records are stored in record batches exactly as the producer framed them — baseOffset, lastOffsetDelta, producerId, isTransactional, then the compressed records. Compression is applied per batch, so a batch of 500 similar records compresses far better than 500 individually; this is why linger.ms affects your storage bill and not just latency.

The important property: the on-disk format is byte-identical to the wire format. The broker never parses a record, never re-frames one, never keeps per-record bookkeeping. It receives bytes, appends bytes, and later sends the same bytes. Hold on to that — it is what makes the next section possible.

Why it is fast — four mechanisms

1 · Sequential I/O

Appending to a file is sequential, and sequential throughput beats random access by roughly an order of magnitude on spinning disks and still substantially on NVMe. The index files preserve this on the read path too: an offset becomes a byte position by lookup, so reads are a seek followed by a sequential scan rather than a walk.

2 · Page cache instead of an application cache

Writes land in the OS page cache. Kafka does not fsync per record — log.flush.interval.messages defaults to effectively never, and durability comes from replication to other brokers, not from reaching the platter. Three consequences worth stating:

  • A broker process crash loses nothing, because the page cache belongs to the kernel and survives the process. A machine power loss can lose unflushed data on that broker — which is precisely why acks=all with min.insync.replicas is the durability story, and M3 is about getting that right.
  • The JVM heap stays small, since the data lives in the kernel's cache rather than a buffer pool. GC pauses stay out of the request path. A broker serving terabytes runs comfortably on a heap of a few gigabytes.
  • The cache is shared and warm across restarts of the broker process, and a consumer reading recent data usually never touches a disk at all.

3 · Zero-copy on the read path

Because the bytes a consumer wants are already in the page cache in the exact format it expects, Kafka serves them with sendfile: the kernel moves them from page cache directly to the socket, with no copy into user space and no deserialisation. The broker never materialises a record on a fetch.

The senior follow-up

When does Kafka not get zero-copy? When the connection is encrypted. TLS has to encrypt the bytes, which means pulling them into user space — so sendfile is off and throughput drops measurably. That is a real capacity-planning input, not trivia, and it is the question an interviewer asks after you say "zero-copy".

A second case is broker-side recompression: if a topic sets a compression.type different from what the producer sent, the broker has to decompress and recompress each batch, touching the bytes. Leaving the topic at compression.type=producer is what keeps the broker out of the data path.

Historically there was a third case: serving an old client that needed an older message format forced the broker to down-convert, losing zero-copy and spiking broker CPU. Kafka 4.0 removed message formats v0 and v1 (KIP-724) along with message.format.version, so on a 4.x broker that case is gone — worth saying, because it shows you know what changed and when.

4 · Batching, which is what ties the other three together

The broker does no per-record work because it never needs to look inside a batch. No parsing, no re-framing, no per-message state. That is not an optimisation layered on top — it is the reason zero-copy is possible at all, since any transformation would force the broker to touch the bytes.

The through-line for the whole section: Kafka is fast because the broker was given almost nothing to do, and every mechanism above follows from refusing to keep per-message state. That refusal is the same one that costs you per-message retry and priority back in M0.

Retention — what actually deletes data

Deletion is driven by policy, never by consumption. Two limits, both enforced per partition:

  • retention.ms — delete segments older than this (default 7 days)
  • retention.bytes — keep at most this many bytes per partition, deleting oldest first (default unlimited). A 100 GB budget on a 50-partition topic is 5 TB, not 100 GB. People get this wrong.
The bug everyone hits once

Deletion happens at segment granularity, and the active segment is never deleted. So "I set retention.ms=60000 and nothing is being deleted" is almost always correct behaviour: on a low-traffic topic the active segment has not rolled, because rolling needs 1 GiB of data or 7 days of time. Every record is eligible and none can go, because they share a file with records that are not.

The fix is to make segment.ms (or segment.bytes) small enough that segments close and become whole-segment eligible. Retention is a floor on how long data lives, never a ceiling — the real guarantee is "at least retention.ms, plus up to one segment's worth of time".

The retention thread also only runs every log.retention.check.interval.ms (default 5 minutes), which adds another lag between eligible and gone.

Log compaction — retention by key

cleanup.policy=compact changes the question from "how old is this record" to "is this the newest value for its key". The cleaner rewrites segments keeping only the latest record per key. A record with a null value is a tombstone: it marks the key as deleted, survives for delete.retention.ms (default 24 h) so that consumers have a chance to see the deletion, then disappears with the key.

What compaction gives you is a log that converges to a table: replay it from the start and you end up with current state per key. That is the mechanism behind __consumer_offsets, Kafka Streams changelog topics, and CDC snapshots.

PropertyWhy it matters

Tiered storage (KIP-405)

With remote.storage.enable=true, a topic keeps recent segments locally (local.retention.ms / local.retention.bytes) and moves older closed segments to object storage, while retention.ms continues to govern total lifetime. Consumers read through transparently; the offset space is unchanged.

Two things it buys that matter in an interview:

  • Cost. Long retention stops requiring broker disks sized for it. Keeping a year of history becomes an object-storage bill rather than a cluster-sizing problem.
  • Recovery time. Replacing a broker previously meant replicating every byte it held. With most history remote, a new broker only pulls the local window, so rebuild drops from hours to minutes. This is the one people forget, and it is the stronger argument.

The cost is a read-latency cliff for consumers that fall behind into remote segments, plus the operational surface of a second storage system. And it does not apply to compacted topics.

Module 3

Replication & ISR

The durability module. Everything here is one question asked in different ways: under which failures does Kafka lose an acknowledged write, and which settings move that line. This is where acks=all stops being a magic word.

Leaders, followers, and a fetch loop

Each partition has one leader and replication.factor - 1 followers. All produce and consume traffic goes to the leader. Followers are not pushed to — they run a fetch loop against the leader exactly like a consumer does, using the same protocol. There is no separate replication channel, which is a large part of why replication costs so little to implement and reason about.

Two offsets per replica matter:

  • LEO (log end offset) — the offset the next record will be written at. Every replica has its own.
  • HW (high watermark) — on the leader, the minimum LEO across all in-sync replicas. This is the furthest point consumers are allowed to read.
Why consumers cannot read past the high watermark

A record that only exists on the leader is not yet durable: if the leader dies, a follower that never received it becomes the new leader and the record is gone. Serving it would mean a consumer could read something that later ceases to exist — the log would appear to go backwards. Holding reads at the HW means anything a consumer can see has been replicated to every in-sync replica, so no surviving failover can take it away.

The visible cost is latency: a record is produced, and only becomes readable one replication round-trip later. That gap is not a bug, it is the durability guarantee showing itself.

ISR — the set that actually decides everything

The in-sync replica set is the replicas currently keeping up with the leader. A follower is in the ISR while it has fetched up to the leader's LEO within replica.lag.time.max.ms (default 30 s). Fall behind for longer — GC pause, slow disk, saturated network, a restart — and the leader removes it. Catch up again and it is re-added.

The ISR is not a static list and it is not Replicas. Almost every durability question comes down to how large is the ISR at the moment of failure, which is why IsrShrinksPerSec is a metric worth alerting on rather than merely graphing.

acks and min.insync.replicas — read them as a pair

acks is a producer setting; min.insync.replicas is a topic/broker setting. Neither is sufficient alone, and the single most common durability misconfiguration is setting one and assuming the other.

acksLeader responds whenLost if
0Immediately — the producer does not waitAnything at all. A network blip loses records silently; there is no retry because there is no response to retry on.
1The leader has written to its own logThe leader dies before a follower replicates. The write was acknowledged and is gone — a silent loss, invisible to the producer.
allEvery replica in the ISR has the recordOnly if the ISR had shrunk far enough first. This is the whole point below.
Why acks=all alone guarantees nothing

acks=all means "all replicas in the ISR", not "all replicas". If two of three followers fall behind and drop out, the ISR is just the leader — and acks=all is then satisfied by the leader alone. It has silently degraded to acks=1, with no error and no warning, at exactly the moment the cluster is least healthy.

min.insync.replicas is the floor that closes this. With min.insync.replicas=2, a producer using acks=all gets NOT_ENOUGH_REPLICAS when the ISR drops below two — the write is rejected rather than silently under-replicated. You have chosen to fail loudly instead of losing data quietly.

The standard safe configuration, and the reasoning behind each number:

replication.factor   = 3     # tolerate one failure and still have a choice
min.insync.replicas  = 2     # a write needs leader + one follower
acks                 = all   # producer waits for the whole ISR

RF 3 with min ISR 2 survives one broker loss while still accepting writes. Setting min.insync.replicas=3 on RF 3 is a common mistake: it means any single broker failure stops writes entirely, trading all availability for a durability gain you mostly already had.

Worth knowing for a 4.x interview: since Kafka 3.0 the producer defaults are acks=all and enable.idempotence=true (KIP-679). Older answers that say "the default is acks=1" are out of date, and saying so is a cheap way to show the knowledge is current.

Leader epoch, and why truncation used to lose data

When a failed replica rejoins, it may hold records the new leader never had, so it must truncate before it can follow. The question is truncate to where.

Originally a recovering replica truncated to its own high watermark, which created a real divergence window: because the HW propagates to followers one round-trip after it advances, two replicas could disagree about it during a double failure, and committed records could be lost or the logs could silently diverge while both believed they were in sync.

Leader epoch (KIP-101) fixed this. Every leader election increments an epoch number, and each replica keeps a leader-epoch-checkpoint file — you saw it in the lab 01 partition directory — mapping each epoch to the offset where it began. A recovering follower asks the leader "where did epoch N end?" and truncates to exactly that offset, instead of guessing from a watermark that may be stale. Deterministic, and no divergence.

You do not configure this. It is worth knowing because it is the honest answer to "has Kafka ever lost data in normal operation" — yes, before 0.11, through exactly this path.

Unclean leader election

Every in-sync replica is gone and only an out-of-sync one remains. Two choices, no third:

unclean.leader.election.enableBehaviourYou are choosing
false (default)The partition goes offline and stays offline until an in-sync replica returnsConsistency. No acknowledged write is ever lost; the partition is simply unavailable, possibly for a long time.
trueAn out-of-sync replica becomes leader immediatelyAvailability. Writes resume at once, and every record the old leader had beyond this replica's log is permanently gone. Consumers that already read them see the log move backwards.

This is the clearest CAP trade-off Kafka exposes, and the right answer in an interview is not a preference but a per-topic decision. Clickstream or metrics where a gap is survivable and downtime is not: enable it. A payment ledger: never — take the outage. Naming the topic class is what makes the answer senior; "it depends" without naming the dimension is not an answer.

Module 4

KRaft & the metadata plane

Everything so far has been the data plane. This is the other half: how the cluster knows who leads which partition, and why Kafka spent five years replacing the system that used to answer that.

What ZooKeeper was actually doing

Before 4.0, a Kafka cluster was two distributed systems. ZooKeeper held the metadata: which brokers are alive, which topics exist, how partitions are assigned, who leads each one, the ISR, topic configs and ACLs. One broker was elected controller and was the only component allowed to write that metadata; everyone else read it.

The data plane never touched ZooKeeper — producing and consuming went broker to broker. ZooKeeper was the control plane only, which is why clusters could be enormous and still keep a modest ZooKeeper ensemble.

Why it had to go

  • Two systems to operate. Two sets of config, two security models, two upgrade paths, two sets of failure modes, two on-call runbooks — for one product. Most Kafka outages that were not disk-related were ZooKeeper-related.
  • Controller failover was O(partitions). A new controller had to load the entire cluster state out of ZooKeeper before it could act. On a large cluster that was minutes of no leader elections, no topic changes, and no recovery from any other failure happening at the same time. Failover time grew with the thing you most wanted to grow.
  • Metadata propagation was RPC push. The controller pushed updates to brokers individually. A broker that missed one had no way to notice: there was no version, no offset, nothing to compare. Divergence was possible and hard to detect.
  • A hard ceiling on partitions. Roughly 200k per cluster in practice, set by that load-everything failover, not by disk or throughput.

KRaft: metadata as a Kafka log

The insight behind KIP-500 is almost circular, and it is the thing to lead with in an interview: Kafka is a replicated log, and metadata is a thing that needs replicating — so store the metadata in a Kafka log.

A set of controller nodes forms a Raft quorum over a single-partition internal topic, __cluster_metadata. The Raft leader is the active controller; the others are followers that already hold the whole log.

Three consequences are worth being able to state in your own words:

  1. Brokers are observers of the metadata log. They fetch records and apply them in order, exactly as a consumer does. Metadata becomes eventually consistent with a measurable lag rather than a push that might have been missed — and "this broker is 4,000 metadata records behind" is now a sentence you can say, and alert on.
  2. Failover is fast because nothing is loaded. Standby controllers have been applying the same log all along, so promotion is a Raft election, not a state transfer. Milliseconds instead of minutes, and it no longer scales with partition count.
  3. The metadata log is compacted, with snapshots. It would otherwise grow forever. Periodic snapshots capture the full state so the log can be truncated, and a new controller or a far-behind broker loads the latest snapshot and replays only what came after.

Deployment shapes and quorum sizing

Every node declares process.roles:

  • Isolated — controller or broker, never both. Dedicated controllers are small, cheap, and insulated from data-plane load; a broker under GC pressure cannot destabilise the control plane. This is the production shape.
  • Combined — broker,controller on one node. Fewer machines, fine for development and small clusters, and what every lab in this repo uses. The risk is exactly the one it saves money on: data-plane load can starve the controller.

Quorum sizing follows Raft, not replication factor: a quorum of N tolerates (N-1)/2 failures, so 3 controllers tolerate one loss and 5 tolerate two. Even numbers buy nothing — 4 tolerates the same single failure as 3, while adding another node that must agree. Three is the normal answer; five is for clusters where controller loss is genuinely costly.

Controllers are sized by metadata volume, meaning partition count, not by throughput. This surprises people: a cluster pushing gigabytes a second can run a perfectly happy three-node controller quorum on small instances.

The weak answer is "to simplify operations" — true, and it sounds like a slide. The strong answer names the mechanism: controller failover required loading the entire cluster state out of ZooKeeper, so recovery time scaled with partition count and capped cluster size. Putting metadata in a Raft-replicated Kafka log means standby controllers already hold the state, so failover becomes an election rather than a state transfer — and brokers consume metadata as a log with an offset, which makes "behind" a measurable quantity instead of an invisible one. Operational simplicity is a consequence, not the reason.

Producer internals

What actually happens between send() returning and the record reaching a log — and why the idempotent producer is the first thing in this course that is genuinely subtle.

The path of one record

send() does not send anything. It is asynchronous, returns a future, and hands the record to a buffer that another thread drains.

send(record)
  → serializer            key and value to bytes
  → partitioner           pick a partition
  → RecordAccumulator     append to that partition's current batch, in memory
  → [returns]            the future is not yet complete
      ⋮
  Sender thread           drains ready batches, groups them per broker,
                          sends one request per broker, handles the response,
                          completes the futures and fires the callbacks

Two consequences fall out immediately. A callback runs on the Sender thread, so blocking in it stalls all sending for that producer. And a producer that has not been flushed or closed can lose everything still sitting in the accumulator — which is why close() matters and why a container killed with SIGKILL mid-batch loses records that send() appeared to accept.

The accumulator is a memory pool, and it can block you

buffer.memory (default 32 MiB) is the total memory for all unsent batches. When it is exhausted — the broker is slow, a partition's leader is unavailable, the application produces faster than the network drains — send() stops being asynchronous and blocks for up to max.block.ms (default 60 s), then throws.

The symptom nobody attributes correctly

"Our service got slow and we don't know why" is frequently a producer blocked on buffer.memory, propagating broker backpressure into application latency through a call everyone assumes is non-blocking. The giveaway is that request latency rises in a service that is doing no more work than usual. max.block.ms also covers waiting for topic metadata, so a producer writing to a topic that does not exist blocks the same way.

Batching: the two settings and the thing people get wrong

  • batch.size (16 KiB) — maximum bytes per partition in one batch. Not a global size, and not a count.
  • linger.ms (0 in the Java client) — how long to wait for more records before sending a partially full batch.

A batch goes when it is full or linger expires. The part that surprises people: linger.ms=0 still batches. While a request is in flight to a broker, records for that broker keep accumulating, and the next request takes everything that arrived meanwhile. Under load you get large batches with zero configured linger — batching is driven by the in-flight window, not only by the timer. Raising linger.ms adds a latency floor to get bigger batches at low load, where there is nothing in flight to accumulate behind.

This matters beyond throughput: compression is applied per batch, so bigger batches compress better. linger.ms is also a storage-cost setting, and the M2 point that the broker stores exactly the bytes the producer framed is what makes that true end to end.

Compression

The partitioner changed, and the old answer is now wrong

With a key, the partition is murmur2(key) % partitions — unchanged since M1. With a null key:

  • Before 2.4: round-robin per record, which spread a small number of records across every partition and produced many tiny batches.
  • 2.4 (KIP-480): the sticky partitioner — fill one partition's batch, then switch. Far fewer, far larger batches.
  • 3.3 (KIP-794): the strictly uniform sticky partitioner. The 2.4 version allocated batches equally but, because slow brokers drain slower, could send more bytes to the brokers least able to take them. The new default assigns by how much each partition has actually accepted, and with partitioner.adaptive.partitioning.enable it steers away from slow brokers. DefaultPartitioner is deprecated; leave partitioner.class unset to get the current behaviour.

Knowing all three, and that the answer changed twice, is the kind of detail that marks someone who has followed Kafka rather than learned it once.

Retries, timeouts and ordering

Tuning retries is the classic mistake: it has not been the limit since delivery.timeout.ms was introduced. If you want a producer to give up after 10 seconds, that is the setting to change.

And the M1 point, now with its mechanism: a retry reorders only when max.in.flight > 1, because request 2 can succeed while request 1 is being retried. max.in.flight=1 is safe and slow. The real fix is idempotence.

The idempotent producer

enable.idempotence=true — the default in the Java client since 3.0 (KIP-679), along with acks=all. The mechanism:

  • The producer requests a producer id (PID) and an epoch from a broker.
  • Every batch carries the PID, the epoch, and a sequence number per partition, incrementing by batch.
  • The broker keeps the last sequence number per (PID, partition). A batch whose sequence it has already seen is acknowledged and discarded — the duplicate never reaches the log. A batch arriving ahead of the expected sequence is rejected with OutOfOrderSequenceException.

So the broker both deduplicates and enforces order, which is why idempotence makes max.in.flight up to 5 safe instead of forcing it to 1: out-of-order arrivals are rejected and retried in order rather than being written in the wrong order.

Those are the producerId and sequence fields visible in kafka-dump-log.sh since lab 01 — this is what they were for.

What idempotence does not do

It does not survive a producer restart. A new producer instance gets a new PID, so the broker has no way to recognise records the previous instance already wrote. Retry after a crash duplicates. Idempotence is per producer session.

It is not cross-partition or cross-topic atomicity. Two records to two partitions can still end with one written and one not. That is transactions, and it is M7.

It is not end-to-end exactly-once. It removes duplicates introduced by producer retries. An application that calls send() twice sends two records, and the broker is right to store both.

The honest one-liner: idempotence makes a retry safe, not a system exactly-once.

Two more things that bite

Record size has two limits and they are set in different places. max.request.size (producer, 1 MiB) and message.max.bytes (broker/topic). Raise one without the other and the failure appears at whichever is lower — and the broker-side rejection arrives as a confusing error after the record has crossed the network. Consumers have fetch.max.bytes and max.partition.fetch.bytes to match; a message too large for a consumer to fetch is a stall, not an error.

Errors come in two kinds. Retriable — NotLeaderOrFollower, NotEnoughReplicas, timeouts — the client handles them within delivery.timeout.ms. Non-retriable — RecordTooLarge, serialization failures, authorization — fail immediately and reach your callback. Code that treats every callback error the same either retries what can never succeed or drops what would have.

Consumer internals

Where most real Kafka incidents actually happen. Producers fail loudly; consumers fail by quietly rebalancing in a loop, reprocessing everything, or stalling on a message nobody notices.

The poll loop is not what it looks like

poll() does not fetch on demand. A background fetcher keeps requests in flight to the brokers leading the assigned partitions and fills a local buffer; poll() hands you records from that buffer and returns. If the buffer has data, poll() returns immediately without any network call.

Since 0.10.1 heartbeats are on their own background thread, which is the fact the rest of this module hangs on: liveness and progress became two separate things, with two separate timeouts, and confusing them causes most consumer incidents.

max.poll.records is the one people reach for when processing is slow, and it is usually the right lever — not because it fetches less, but because it bounds how long one poll()-to-poll() cycle takes, which is what the timeout below actually measures.

The distinction is the whole point. Heartbeats come from a background thread, so a consumer whose processing is wedged keeps heartbeating happily — the session timeout never fires. max.poll.interval.ms exists precisely to catch that: an application that is alive but not making progress.

(session.timeout.ms was raised from 10 s to 45 s in Kafka 3.0, KIP-735, because the old value evicted healthy consumers during ordinary GC pauses and cloud network blips. Quoting 10 s dates an answer.)

The rebalance storm, step by step

Processing slows — a downstream service degrades, a batch is unusually large. One consumer exceeds max.poll.interval.ms and is evicted. The group rebalances, so every consumer stops. Partitions are reassigned, and work since the last commit is reprocessed, which makes everyone slower. The next consumer exceeds the interval. Another rebalance. The group now spends more time rebalancing than consuming and never recovers on its own.

The fix is almost never a bigger timeout. It is max.poll.records down so each cycle is shorter and bounded, plus finding out why processing slowed. Raising max.poll.interval.ms to 30 minutes makes a stuck consumer take 30 minutes to be noticed.

Offsets: where progress actually lives

Committed offsets go to __consumer_offsets — 50 partitions, compacted, keyed by (group, topic, partition). Compaction is why it converges to current position per group, and the M2 lesson applies directly. The partition a group's offsets land in also determines its group coordinator: the broker leading that partition.

A committed offset means "the next record I want", not "the last one I processed". Off-by-one here reprocesses or skips exactly one record per commit, forever.

StrategyBehaviourFailure mode
enable.auto.commit=true (default)Commits the last returned offsets every auto.commit.interval.ms (5 s), during poll()Commits what was returned, not what was processed. A crash loses up to 5 s of processing — at-least-once with a window you did not choose

Offsets also expire: offsets.retention.minutes (7 days). A group idle longer than that loses its position and falls back to auto.offset.reset — which, on latest, silently skips everything that arrived meanwhile. Seasonal and batch consumers hit this.

auto.offset.reset applies in exactly two situations: no committed offset for the group, or the committed offset is out of range because retention deleted it (M2, step 4). earliest reprocesses, latest skips, none throws. latest is the dangerous default because its failure is silent.

Rebalance protocols — three generations

A group coordinator on one broker tracks membership. When it changes, the group rebalances. How it rebalances has been rewritten twice.

Eager — the original

Every consumer revokes all its partitions, rejoins, and waits for a new assignment computed by one elected consumer (the group leader) and distributed through the coordinator. Nothing is consumed during the join barrier. Assignment itself is client-side, which means the assignment logic lives in every client in every language. RangeAssignor and RoundRobinAssignor work this way.

Cooperative sticky — 2.4, KIP-429

CooperativeStickyAssignor makes rebalances incremental: consumers keep partitions that are not moving and revoke only the ones being reassigned, across two short rounds instead of one global stop. Adding a consumer to a healthy group stops being a cluster-wide pause. Still client-side assignment.

KIP-848 — the new consumer group protocol, GA in 4.0

Assignment moves to the broker. There is no elected group leader, no client-side assignor, and no join barrier where everyone waits. Consumers reconcile their own assignment asynchronously against what the coordinator publishes, so membership changes stop being stop-the-world at the protocol level rather than by convention. Enable with group.protocol=consumer.

Two consequences worth naming: assignment logic no longer has to be reimplemented per client language, which was a real source of cross-client inconsistency; and rebalance behaviour becomes a broker-side property you can reason about centrally instead of a property of whichever client version each team deployed.

Static membership — 2.3, KIP-345

Give each consumer a stable group.instance.id and a restart within session.timeout.ms does not trigger a rebalance — the returning member reclaims its partitions. This is what makes rolling deploys of a large consumer group survivable; without it, a 20-pod rollout is 20 rebalances.

Rebalance listeners, and the commit that must happen

  • onPartitionsRevoked — fires before partitions are taken. This is where you commit. Skip it and everything since the last commit is reprocessed by whoever gets the partition.
  • onPartitionsAssigned — after the new assignment; initialise or seek here.
  • onPartitionsLost — the partitions are already gone (the member was evicted), so committing is pointless and may fail. Clean up, do not commit.

Distinguishing revoked from lost is the detail that marks someone who has debugged this: committing in the wrong one of those two is a bug that only appears during incidents.

Reading consumer lag honestly

Lag is log end offset − committed offset. High lag means one of several very different things:

  • The consumer is genuinely slower than the producer — scale out, up to the partition count (M1).
  • A producer burst; the consumer is fine and will catch up.
  • The consumer is rebalancing repeatedly and barely consuming — lag plus a rising rebalance rate.
  • Partitions are unassigned because the group has no members at all.
  • Lag is concentrated in one partition — a hot key, not a slow consumer, and adding consumers will not help.

Check lag per partition before concluding anything. "Lag is high, add consumers" is wrong in four of those five cases.

Q7 · When would you advise a team against Kafka?

Three situations, each tied back to the same design decision — the broker stores a log and keeps no per-message state.

  1. Low-latency request/reply. Kafka is not RPC. A round trip through a log adds producer batching, replication and consumer poll latency, and the model gives you no correlation or timeout semantics — you would rebuild them. Use gRPC or HTTP.
  2. Work that needs per-task control — its own retry schedule, its own delay, a priority, a dead-letter path — especially with a worker count that swings. The broker tracks nothing per message, so all of that machinery becomes yours to build and operate. RabbitMQ and SQS give it natively. Share Groups (4.2) narrow this gap but do not close it: there is still no broker-side routing and no delayed delivery.
  3. Small scale, one consumer, no replay requirement. The decisive cost here is operational rather than technical: a cluster to run, metrics to watch, partition counts that cannot be undone, and somebody who can diagnose a shrinking ISR at 2am. A Postgres outbox table or a Redis stream is proportionate to the problem.

Three more worth having ready: fan-out to end clients (Kafka is not client-facing — it sits behind a WebSocket or push tier); querying or mutating a specific message by its content (that is a database); and scheduled or delayed delivery, which Kafka has no native answer for.

The trade is usually stated as “you give up ordering”, which is true but incomplete. The deeper trade is that the broker now keeps per-record state — exactly the thing Kafka refused to do in order to stay fast. A consumer group costs the broker one integer per partition; a share group costs it a state machine per in-flight record, plus the lock timeouts that go with it. Q9 · Delayed delivery on Kafka

Why the obvious design does not work. “Publish to a delay topic, read it, check the timestamp, and process once 30 minutes have passed” breaks on the first record. A partition is a sequential log and a consumer cannot skip its head: if the record at the head is due in 29 minutes, every record behind it waits too, however ready they are. That is head-of-line blocking, and it is the whole difficulty of the problem. Sleeping inside the poll loop makes it worse — exceeding max.poll.interval.ms gets the consumer evicted and triggers a rebalance.

A design that holds up. Tiered delay topics, one per granularity — delay-5s, delay-1m, delay-5m, delay-30m. Each carries records whose remaining wait is roughly uniform, which bounds head-of-line blocking to that tier's granularity. A consumer per tier reads the head record and computes its due time:

  • Not due → consumer.pause() the partition and seek() back to that offset, then keep calling poll() so heartbeats continue; resume when the remaining time has elapsed. Never sleep() inside the loop.
  • Due → republish to the next smaller tier, or to the destination topic when the remaining delay fits.

What it costs. Ordering is gone along the delay path. Retention on every delay topic has to exceed the maximum delay, or the message expires before it fires. Republishing means at-least-once, so the terminal consumer has to be idempotent. Delay precision is bounded by tier granularity plus one poll interval. And it is a topic, a consumer group and a dashboard per tier, forever.

The alternative worth naming. Keep the schedule in a database — a row with a due_at column and a poller that publishes to the destination topic when the time comes. “Find the rows that are due now” is a query a database is built for and a log is not. It is less clever, has no head-of-line blocking, and is usually the right answer unless the delay volume is large enough to make the database the bottleneck.

Q10 · Already running RabbitMQ — should a team add Kafka?

For. An event stream is a different problem from task dispatch. Modelling it on a queue forces the consumer list to be decided at publish time, because an exchange has to copy each message into one queue per consumer; a consumer that appears six months later sees nothing that came before it. In Kafka that consumer is a new group reading from offset 0, at no cost to anyone already running. Reprocessing after a bug is the same mechanism rather than a data-recovery project. And retention stops being a liability to manage and becomes the feature the design rests on.

Against. Two brokers is two sets of operational knowledge, two failure modes, two upgrade paths, two monitoring stacks and two on-call runbooks — a cost paid continuously by everyone, not once by the team that wanted it. Kafka's failure modes are also unfamiliar in a way that bites: a shrinking ISR, rebalance storms, consumer lag that means something other than a slow consumer, and a partition count that cannot be lowered once chosen.

The option that usually goes unexamined. RabbitMQ has had Streams since 3.9 — an append-only, replicated log with consumer-controlled offsets and replay, with superstreams adding partitioning. If what the team actually needs is replay and multiple independent readers, that may already be available on the broker in production today. Establishing whether it is should come before any comparison of Kafka against RabbitMQ queues, because that comparison answers the wrong question.

How to decide. The senior move is to name a test rather than a preference. Add Kafka when all four hold:

  1. More than one independent consumer of the same data exists today, not hypothetically.
  2. Replay or reprocessing is a stated requirement, not a nice-to-have.
  3. The event history itself has value beyond the processing of it.
  4. Somebody will own it operationally, by name, with a runbook.

If RabbitMQ Streams satisfies the first three, the answer is no. If fewer than three hold at all, the answer is to use what you already run — the scarce resource is operational attention, not throughput.

Q7 · 3 partitions, 30 parallel consumers, ordering per user_id

Four options. The useful move in an interview is to say out loud which of them actually removes the three-partition ceiling and which only works around it, then recommend one.

1 · Worker pool behind each consumer. Three consumers, one per partition; each hashes user_id and dispatches to a fixed worker, so records for one user stay on one worker and stay in order. Keeps the topic untouched, and it is the only option here that needs no migration.

The costs are all in offset management. A commit says “everything up to this offset is done”, but with a pool the records in flight finish out of order, so you may only commit up to the lowest unfinished offset — which means tracking completion per record and holding the commit back behind the slowest worker. On rebalance the partition is revoked while work is still in flight: either drain the pool inside the revoke callback or accept reprocessing, which makes idempotent handlers a requirement rather than a nicety. Add bounded queues, or a slow worker turns into unbounded memory growth and then a max.poll.interval.ms eviction.

2 · Share group (KIP-932). Removes the partition ceiling outright — many consumers per partition, per-record acknowledgement. It also removes ordering entirely, which is the requirement. So this answers half the question and fails the other half; name it, reject it, and move on. Mentioning it without rejecting it reads as not having checked the constraint.

3 · Repartition into a new topic. A new topic with 30+ partitions keyed by user_id is the only option that genuinely raises the ceiling while keeping ordering. Note that it has to be a new topic: --alter --partitions on the existing one moves roughly half the keys and breaks ordering at the cutover.

The cost is the migration. Producers have to switch over at a point in time; consumers have to read both topics until the old one is drained; and for any key in flight across the switch, ordering cannot be guaranteed, because its history is on one topic and its future on another. The usual mitigations are to drain with the producer stopped, or to accept a defined inconsistency window and make consumers tolerate it.

4 · Two-stage pipeline. Consume the three partitions and re-key into a wide internal topic, then run 30 consumers against that. Ordering is clean on the second stage, the first stage stays small, and the original topic is untouched. The price is an extra hop, extra storage, and at-least-once between the stages — so again, idempotent handlers.

Recommendation. If 30-way parallelism is needed because processing is slow rather than because the input rate is high, option 1 is enough and costs no migration — the three partitions can feed far more throughput than three threads can consume. If the input rate itself is the problem, only options 3 and 4 help, because a partition is read by one fetch stream and that is the real ceiling. Saying which case you are in, and why, is the answer; the list by itself is not.

Q8 · Scope of the ordering guarantee, and three ways to lose it with the key set

Scope: within a single partition, and only while the producer is configured correctly. There is no topic-wide ordering and there never can be: it would need a shared clock or a single sequencer, and either one undoes the parallelism the design exists for.

1 · Producer retries. The retry is not what reorders — the combination is. With max.in.flight.requests.per.connection > 1, batch 2 can be in flight while batch 1 is being retried, so batch 2 lands first and the partition now holds them out of order. With max.in.flight=1 retries are safe but throughput drops. The real fix is enable.idempotence=true: the producer attaches a producer id and a per-partition sequence number, and the broker rejects anything out of sequence, so ordering holds with up to five requests in flight. That number matters — idempotence caps max.in.flight at 5 for exactly this reason, and an interviewer will ask.

2 · Concurrency after poll(). Kafka delivered the batch in order; handing it to a thread pool undoes that in your own process. The fix is not to avoid threads but to partition them the same way Kafka does: hash the key to a fixed worker so one key is always handled by one thread, sequentially. The commit discipline from Q7 comes with it.

3 · Raising the partition count. The key's hash is taken modulo the partition count, so changing that count moves roughly half the keys while their existing records stay where they were. A consumer following one key sees its history stop on one partition and resume on another, with no relation between the two.

A fourth, worth having ready: consuming through a share group, which trades ordering away by design.

Q9 · Why Kafka is fast despite writing to disk

Four distinct mechanisms. Naming them is the easy half; the interview is in what each one actually does.

1 · Sequential I/O. A partition is an append-only file, so writes are sequential, and sequential throughput beats random access by an order of magnitude on spinning disks and still substantially on SSDs. The .index and .timeindex files preserve this for reads: an offset is resolved to a byte position by lookup rather than by scanning, so reads stay sequential too.

2 · Page cache instead of an application cache. Writes land in the OS page cache and are not fsynced per record — the broker acknowledges as soon as the data is in memory, and durability comes from replication to other brokers rather than from flushing to the platter. Two consequences people miss: a broker process crash loses nothing, because the page cache belongs to the kernel and not to the process; and the JVM heap stays small, which keeps GC pauses out of the request path. A conventional database would hold this data in its own buffer pool, paying for it twice in memory and once in GC.

3 · Zero-copy on the read path. Recent data is already in the page cache, and Kafka ships it with sendfile: the kernel moves bytes from page cache straight to the socket, without copying them into user space and without the broker deserialising anything. The broker never materialises a record on a fetch.

4 · Batching, and the format that makes the other three work. Records travel and are stored as compressed batches, and — this is the part that ties it together — the on-disk format is byte-identical to the wire format the producer sent and the consumer expects. So the broker does no per-record work at all: no parsing, no re-framing, no per-message bookkeeping. That identity is what makes zero-copy possible in the first place; if the broker had to transform anything, it would have to touch the bytes.

The through-line worth stating: Kafka is fast not because any one trick is clever, but because the broker was given almost nothing to do. Every one of these follows from refusing to keep per-message state.

Q7 · Four mechanisms, and how the fourth makes the third possible

There is more than one defensible decomposition here. What the question is testing is whether the mechanisms are understood as connected rather than as a list, so the fourth one has to be the one that explains the third.

1 · Sequential I/O. A partition is append-only, so writes land at the end of a file and never seek. Sequential throughput beats random access by roughly an order of magnitude on spinning disks and still substantially on NVMe. Segmenting and the sparse .index keep the read path sequential too: an offset resolves to a byte position by binary-searching segment filenames and then one index lookup, so a read is a seek followed by a sequential scan rather than a walk. The index is deliberately sparse — one entry per ~4 KiB — because these files are memory-mapped and a dense index would compete for the page-cache memory that makes reads fast in the first place.

2 · Page cache instead of an application cache. Kafka keeps no data in the JVM heap. Writes go to the OS page cache and are not fsynced per record; durability comes from replication to other brokers rather than from reaching the platter. Three consequences: a broker process crash loses nothing because the cache belongs to the kernel, while a machine power loss can lose unflushed data on that broker — which is why durability is acks=all plus min.insync.replicas; the heap stays small, so a broker serving terabytes runs on a few gigabytes with GC off the request path; and a consumer reading recent data usually never touches a disk.

3 · Zero-copy on the read path. A conventional read() then write() costs four copies — DMA disk to kernel buffer, CPU kernel to user space, CPU user space to socket buffer, DMA socket buffer to NIC — across two syscalls, so four context switches. sendfile collapses this to two copies and two context switches, and with scatter-gather DMA the second copy disappears as well: the NIC reads straight from the page cache. The broker never deserialises a record on a fetch.

4 · Batching, and the format identity that makes zero-copy possible at all. Records are stored and shipped as compressed batches, and the on-disk format is byte-identical to the wire format the producer sent and the consumer expects. So the broker does no per-record work: no parsing, no re-framing, no per-message bookkeeping. That identity is the precondition for mechanism 3 — sendfile can only hand raw file bytes to a socket, so the moment the broker has to transform anything, it must pull the bytes into user space and zero-copy is gone. Batching also makes compression effective, because 500 similar records in one batch compress far better than 500 compressed individually, which is why linger.ms affects the storage bill and not only latency.

The through-line. Kafka is fast not because any one trick is clever but because the broker was given almost nothing to do, and every mechanism above follows from one decision: refusing to keep per-message state. That is the same refusal that costs you per-message retry, delay and priority.

Q8 · When Kafka does not get zero-copy, and what it costs

TLS. An encrypted connection has to encrypt the bytes, which means pulling them out of the page cache into user space — so sendfile cannot be used and the read path falls back to copy, encrypt, write. The cost is measurable: higher broker CPU, allocation and GC pressure that the zero-copy path avoids entirely, and the extra context switches back. The operational conclusion is what matters in an interview: an encrypted cluster is not a drop-in swap for a plaintext one, and the difference belongs in capacity planning rather than being discovered after the migration.

Broker-side recompression. If a topic sets a compression.type that differs from what the producer sent, the broker has to decompress and recompress each batch — touching the bytes, so no zero-copy, plus real CPU on the write path. Leaving the topic at compression.type=producer is what keeps the broker out of the data path.

Down-conversion — historical, and worth saying so. A client requesting an older message format used to force the broker to rewrite batches, losing zero-copy and spiking CPU, sometimes badly enough to take a cluster down during a slow client migration. Kafka 4.0 removed message formats v0 and v1 (KIP-724) along with message.format.version, so on a 4.x broker this case no longer exists. Naming it and naming when it disappeared shows you track what changed rather than reciting an old blog post.

One thing that is not a loss of zero-copy, and is worth not confusing: a consumer reading data old enough to have been evicted from the page cache still uses sendfile. It just pays a disk read first. The path is unchanged; only the latency is.

Q9 · A compacted topic feeding a cache: what breaks

Compaction converges a log towards a table — replay it and you end with the current value per key. Four consequences follow, and all of them are the consumer author's problem.

Offsets have gaps. Compaction removes superseded records but never renumbers the survivors, because consumers have already committed against those offsets. A compacted log therefore reads 8, 10, 11, 15. Any logic that assumes offset + 1, infers progress by counting records, or treats a gap as data loss is wrong. Lag is still meaningful; record counts are not.

Intermediate values are gone. A consumer starting from the tail sees only the latest value per key, so a compacted topic cannot be used to reconstruct a history or to react to every transition — only a consumer keeping up near the head sees them all. If the cache needs to act on changes rather than hold state, a compacted topic is the wrong source, and the right answer is a separate non-compacted event topic.

Tombstones expire, and this is the real bug. A delete is a record with a null value. It survives delete.retention.ms (default 24 h) and is then removed along with the key. A consumer offline longer than that window comes back, sees no tombstone and no record for the key, and keeps its stale entry forever — a silent, permanent divergence with no error anywhere. This is the failure that bites CDC pipelines and cache invalidation in production. Mitigations, in order of honesty: raise delete.retention.ms past the longest plausible outage; alert on consumer downtime approaching it; and, as the thing that actually works, rebuild the cache periodically from a full read of the compacted log instead of trusting incrementally maintained state.

The active segment is never compacted. The head of the log always holds uncompacted duplicates, so the same key arrives repeatedly and handlers must be idempotent. Compaction is eventual: it is a property of old data, not a guarantee about what any given read returns.

Two supporting details worth having ready: a null key is rejected on a compacted topic, because there is nothing to compact on; and cleanup.policy=compact,delete applies both policies, which is how you stop an unbounded keyspace from growing forever.

Q10 · The case for tiered storage, and what it costs

What it does. With remote.storage.enable=true, a topic keeps recent closed segments on local disk (local.retention.ms / local.retention.bytes) and moves older ones to object storage, while retention.ms continues to govern total lifetime. Consumers read through transparently and the offset space is unchanged.

The cost argument. Long retention stops dictating broker disk size. Keeping a year of history becomes an object-storage bill instead of a cluster-sizing problem, and the cluster can be sized for throughput rather than for history.

The recovery argument, which is the stronger one. Replacing a broker used to mean replicating every byte it held, so rebuild time scaled with retention — a cluster holding 30 days took far longer to heal than one holding 3. With most history remote, a new broker pulls only the local window, dropping rebuild from hours to minutes. That removes a hidden constraint most teams never name out loud: long retention made clusters slow to heal and therefore riskier to operate, so retention was quietly capped by operational fear rather than by requirements. Tiered storage removes the coupling, and saying that is what separates this answer from a summary of the feature page.

What it costs. A latency cliff for any consumer that falls behind into remote segments — fine for a backfill, bad for a consumer you expected to stay near the head, and worth a separate alert. A second storage system inside the failure and security surface: its availability becomes the cluster's availability for historical reads, and its access control becomes part of the data's access control. And it does not apply to compacted topics.

How to decide. Tiered storage decouples retention from cluster size. So the question to ask first is whether retention is the thing sizing the cluster today. If the cluster is sized by throughput or partition count instead, tiered storage buys little and adds a dependency — and the honest recommendation is to leave it off.

Q1-Q3 · Junior tier, condensed

The ISR is the set of replicas currently keeping up with the leader — a follower stays in while it has fetched to the leader's log end offset within replica.lag.time.max.ms (30 s). It is not the replica list, and it moves continuously; almost every durability question reduces to how large it was at the moment of failure.

acks: 0 does not wait, so a network blip loses records with no retry possible. 1 returns once the leader has written to its own log, so a leader failure before replication loses an acknowledged write silently. all returns once every replica in the ISR has it. Since Kafka 3.0 the producer defaults are acks=all and enable.idempotence=true (KIP-679).

replication.factor=3 gives three copies on three brokers — one leader serving all traffic, two followers fetching. It lets the cluster lose a broker and still have a choice of replica to promote. On its own it guarantees nothing about data loss: a replica that exists but has fallen out of the ISR protects nothing.

Q4-Q6 · Mid tier, condensed

High watermark — the minimum log end offset across the ISR, and the furthest point consumers may read. A record only on the leader is not durable; serving it would let a consumer read something a failover could take away, making the log appear to go backwards. The cost is that a record becomes readable one replication round-trip after it is acknowledged.

Why acks=all is not enough — "all" means all replicas in the ISR. When followers drop out, the ISR is the leader alone and acks=all is satisfied by it, silently becoming acks=1 at the worst possible moment. min.insync.replicas=2 converts that into a rejected write (NOT_ENOUGH_REPLICAS).

Replicas: 2,3,1 · Isr: 2,3 with min ISR 2 — broker 1 has fallen behind and been evicted, so the partition is under-replicated. Writes still succeed because the ISR equals the floor, but there is no margin: one more failure and acks=all producers start failing. Broker 2 is the preferred leader and currently holds leadership. A warning, not an outage.

Q7 · Every configuration that can lose an acknowledged write

1 · acks=1. The leader acknowledges before any follower has the record, then dies. A follower is promoted, the record never existed there, and the producer was told it succeeded. Silent by construction.

2 · acks=all with min.insync.replicas=1. The dangerous one, because the configuration looks correct. The ISR shrinks to the leader alone and acks=all is satisfied by a single replica — identical exposure to case 1, reached through a setting that reads as safe in a review.

3 · Unclean leader election enabled. The whole ISR is lost, a stale replica is promoted, and every record past its log end offset is permanently gone. Consumers that already read those offsets see the log move backwards — the only case here where a consumer can observe the loss directly.

4 · Correlated power loss across the ISR. Kafka does not fsync per record; durability is replication, not flushing. If every replica sits in one rack, one availability zone or one power domain and they lose power together, data that every replica acknowledged can be gone. This is the case people omit, and it is the reason broker.rack and rack-aware placement exist.

The intended configuration is RF 3, min.insync.replicas=2, acks=all, unclean election off, replicas spread across racks. What it expresses is a single principle: Kafka's durability story is to refuse writes rather than lose them. Every setting above either upholds that or deliberately opts out of it, and framing the answer that way is what turns a list into a position.

Q8 · The whole ISR is gone and one stale replica survives

Two options and no third. Offline (unclean.leader.election.enable=false, the default): no acknowledged write is lost, and the partition is unavailable until an in-sync replica returns — possibly until one specific dead broker is physically recovered, which can be hours. Promote the stale replica (true): writes resume immediately, every record beyond its log end offset is permanently gone, and consumers that read those offsets see the log go backwards.

No setting avoids the trade; this is the clearest CAP choice Kafka exposes.

The decision is per topic class, and naming the dimension is what makes it a senior answer: does a downstream consumer treat this log as a source of truth? Clickstream, metrics, application logs — a gap is survivable, downtime is not, so enable it. A payment ledger, an event-sourced aggregate, anything another system reconciles against — never, take the outage and escalate. "It depends" without naming that dimension is not an answer.

Two things to add if pressed. The choice should be made per topic at creation time, not cluster-wide under incident pressure, because under pressure availability always wins the argument. And if you are reaching for unclean election regularly, the real problem is replica placement: a partition whose whole ISR can vanish at once was not spread across failure domains.

Q9 · Why leader epoch was introduced

When a failed replica rejoins it may hold records the new leader never had, so it must truncate before it can follow — the question is to what offset.

Originally it truncated to its own high watermark. The HW propagates to followers one fetch round-trip after it advances on the leader, so a follower's idea of the HW is always slightly stale. During a double failure — leader dies, a follower with a stale HW is promoted, the old leader returns — the two replicas could disagree about what had been committed. The outcomes were real: committed records silently lost, or two logs diverging at the same offsets while both replicas believed they were in sync, which is worse because nothing detects it.

Leader epoch (KIP-101, Kafka 0.11) replaced the guess with a fact. Every leader election increments an epoch number, and each replica keeps a leader-epoch-checkpoint file mapping each epoch to the offset at which it began — the file visible in any partition directory. A recovering follower asks the leader where epoch N ended and truncates to exactly that offset. Deterministic, and divergence becomes impossible rather than unlikely.

It is not configurable and needs no operational attention. It is worth knowing because it is the honest answer to "has Kafka ever lost data in normal operation" — yes, before 0.11, through precisely this path. Being able to say that, and say what fixed it, reads as someone who has read the design rather than the marketing.

Q10 · UnderMinIsrPartitionCount is 4 and producers are erroring

Read the signal first. The ISR has fallen below min.insync.replicas on four partitions, so acks=all producers are being rejected with NOT_ENOUGH_REPLICAS. The cluster is doing exactly what it was configured to do: refusing writes it cannot make durable. The errors are a symptom; the incident is the under-replication.

Split the diagnosis in two. Are brokers down, or alive but lagging? OfflinePartitionsCount and broker liveness answer the first; IsrShrinksPerSec answers the second. The two have completely different causes and fixes, and guessing wrong wastes the first ten minutes.

  • Brokers down → how many, and are the affected partitions' replicas concentrated on them? That points at replica placement rather than at the failure.
  • Alive but lagging → the follower fetch loop is behind. Usual causes: a GC pause, a saturated network link, a disk that has silently slowed, or one broker holding a disproportionate share of leadership after an earlier failover and now saturating.

The wrong instinct, and it is worth saying out loud. Lowering min.insync.replicas stops the errors immediately — and converts a loud failure into a silent one, accepting under-replicated writes during the exact window where a second failure loses them. It is the most tempting action on the page and the one to refuse. Mitigate by restoring replicas.

Afterwards. Check leadership distribution: leaders stay where a failover put them, so recovery is not finished when brokers return. auto.leader.rebalance.enable fixes it eventually; kafka-leader-election.sh --election-type preferred fixes it now. Then ask why the ISR could shrink that far at all — if these partitions share a rack or a disk, the placement is the finding, not the lag.

Q1-Q3 · Junior tier, condensed

ZooKeeper held the control plane: broker liveness, the topic list, partition assignments, leadership, the ISR, configs and ACLs. One broker was elected controller and was the only writer. It never touched the data plane — produce and consume went broker to broker — which is why big clusters ran on small ensembles.

In KRaft, metadata lives in __cluster_metadata, a single-partition internal topic replicated by Raft across the controllers. The Raft leader is the active controller; other controllers are followers with the same log; brokers are observers that fetch it like consumers.

process.roles picks the shape. Isolated means a node is either controller or broker — the production shape, because controllers stay insulated from data-plane load. Combined puts both on one node: fewer machines, fine for development. Quorum sizing follows Raft, so N voters tolerate (N-1)/2 failures: 3 tolerates one, 5 tolerates two, and even numbers buy nothing.

Q4-Q6 · Mid tier, condensed

Brokers fetch metadata rather than being pushed to. Under the old RPC push, a broker that missed an update had no version or offset to compare against, so divergence was possible and undetectable. With a log, every broker has an offset and lag is a number — MetadataLag is graphable and alertable.

Failover is fast because standby controllers have been applying the same log all along and hold the state in memory. Promotion is a Raft election, not a state transfer. Under ZooKeeper the new controller loaded everything from ZooKeeper first, making failover O(partitions) — minutes on a large cluster, which is also what set the practical ~200k partition ceiling.

Snapshots stop the metadata log growing forever and startup getting slower every month. A snapshot captures full state at an offset so earlier segments can go; a new controller or a far-behind broker loads the newest snapshot and replays only what follows. Same problem compaction solves for user topics, solved for the control plane.

Q7 · Why Kafka dropped ZooKeeper, at the mechanism level

"Operational simplicity" is the consequence. The reason is three specific mechanisms.

Failover scaled with partition count. A newly elected controller had to load the entire cluster state out of ZooKeeper before it could act. On a large cluster that was minutes during which no leader could be elected, no topic changed, and nothing could recover from any other failure happening at the same time. Recovery time grew with exactly the dimension you most want to grow.

That set the cluster ceiling. The practical limit of roughly 200k partitions per cluster came from failover time, not from disk, memory or throughput — an architectural ceiling with no tuning knob behind it.

Propagation was an unverifiable push. The controller sent metadata updates by RPC with no version and no offset. A broker that missed one could not detect it, so divergence was silent, and "is this broker's view current?" had no answer.

What KRaft changes. Metadata goes in a Raft-replicated Kafka log, so standby controllers already hold the state and promotion is an election rather than a state transfer — failover stops scaling with partitions, and the ceiling goes with it. Brokers consume that log with an offset, which turns "behind" from an invisible condition into a measurable one. Having one system to operate, secure and upgrade instead of two is a real benefit, but it is the payoff, not the rationale — and leading with it is how you sound like you read the announcement rather than the design.

Q8 · Planning a 3.4-on-ZooKeeper cluster onto 4.x

The constraint that shapes the whole plan: 4.0 removed ZooKeeper support outright, so there is no direct upgrade. The cluster must reach a 3.x release that supports migration, complete the KRaft migration there, verify it, and only then upgrade to 4.x.

Sequence, and why in this order:

  1. Upgrade 3.4 → a late 3.x, still on ZooKeeper. A routine rolling upgrade. Doing it first means the migration starts from a supported, current base.
  2. Provision the controller quorum — three dedicated nodes, isolated mode, sized by partition count rather than throughput.
  3. Start the controllers in migration mode and let them copy metadata out of ZooKeeper, with the cluster still serving traffic.
  4. Roll brokers into KRaft mode one at a time, verifying metadata lag after each.
  5. Dwell in dual-write. This is the window in which rollback is still possible, and the only reason to leave it is confidence. Finalising is irreversible.
  6. Finalise, then — separately, later — upgrade to 4.x.

Verification at each gate: kafka-metadata-quorum.sh --describe --status and --replication, MetadataLag across every broker, ActiveControllerCount summing to exactly 1, and under-replicated partitions back at zero before the next step.

The judgment the question is really testing: the risk is not the migration mechanics, which are well documented. It is combining a version upgrade with a metadata-plane migration so that when something degrades, nobody can attribute it to either, and the rollback decision has to be made under that ambiguity. Two changes, two windows, two rollback plans. Saying that is worth more than reciting the steps.

Q9 · ActiveControllerCount is 2 across the cluster

What it means. Exactly one node should report 1 and all others 0, so a cluster-wide sum of 2 means two nodes each believe they are the active controller — split brain in the control plane.

Why it is probably not what it looks like. Raft makes genuine dual leadership nearly impossible: becoming leader requires a majority of the quorum, and two leaders in the same epoch cannot both have one. So the realistic explanations are a partial network partition in which a superseded leader has not yet learned it lost, a metrics artifact from summing across a scrape window that contained an election, or a node excluded from the quorum still publishing its stale belief.

How bad. Metadata writes go through Raft, so a stale leader cannot commit anything without a majority. Divergent metadata is therefore unlikely; the real exposure is operator confusion and delayed metadata operations, not corruption. That distinction matters because the instinct — restart something immediately — is usually worse than spending two minutes establishing the facts.

How to diagnose. Ask the quorum, not the nodes: kafka-metadata-quorum.sh --describe --status from several nodes, using --bootstrap-controller so brokers being unhealthy does not block you. The quorum's own view of leader and epoch is authoritative; the per-node metric is only that node's belief about itself. Then check network reachability between controllers, since a partial partition is the explanation that actually needs fixing.

The calibration to state. A brief 2 during an election is noise. A sustained 2 is a partition to find — and the finding will be in the network, not in Kafka.

Q10 · Does KRaft change the durability story from M3?

For user data, no. Partition replication, the ISR, acks and min.insync.replicas are untouched. KRaft is the control plane; every durability guarantee from M3 holds unchanged.

What changes is the failure behaviour around it, and the answer lives in separating two things that sound alike:

  • The data plane keeps running. Losing the controller quorum does not lose data and does not stop produce or consume on partitions whose leaders are alive. Brokers act on the metadata they already hold.
  • Recovery freezes. No leader elections, no ISR changes recorded, no topic creation, no broker joining. So a partition leader failing while the quorum is down leaves that partition leaderless until the quorum returns. The cluster keeps doing what it was already doing and cannot respond to anything new.

Why faster failover matters here specifically. Under ZooKeeper, a controller failover window of minutes was a window in which no partition could recover from a broker failure — so an unlucky coincidence became a compound outage. KRaft shrinking that window to an election does not change any guarantee; it shrinks the period in which two independent failures can combine into something worse than either.

The two wrong answers are symmetrical: "KRaft doesn't affect durability, so controller loss is harmless" ignores the frozen recovery; "losing the controllers is catastrophic" ignores that the data plane is unaffected and nothing is lost. Being able to hold both halves at once is the answer.

Q1-Q3 · Junior tier, condensed

send() serializes, partitions, appends to an in-memory batch and returns a future. A Sender thread drains batches, groups them per broker and completes the futures. So callbacks run on the Sender thread — blocking in one stalls all sending — and a producer killed without close() loses whatever is still buffered.

batch.size (16 KiB) is maximum bytes per partition in one batch, not a global size and not a count. linger.ms (0 in Java) is how long to wait for more records before sending a partial batch. A batch goes when full or when linger expires.

Compression belongs on the producer because it is applied per batch before sending and the broker stores those bytes untouched. lz4 when CPU dominates, zstd when storage and cross-AZ bandwidth dominate — usually the right default. Setting a codec on the topic instead forces decompress-and-recompress per batch, costing CPU and losing zero-copy.

Q4-Q6 · Mid tier, condensed

linger.ms=0 still batches. It means "do not wait", not "send alone". Records accumulate while a request is in flight, and the next request takes everything that arrived meanwhile — so under load batching is driven by the in-flight window. Linger buys bigger batches specifically at low load, where nothing is in flight to accumulate behind.

A service slow for no reason is often send() blocking on buffer.memory. The accumulator is a fixed 32 MiB pool; when it fills, send() blocks up to max.block.ms (60 s) and then throws, propagating broker backpressure into application latency through a call assumed to be asynchronous. max.block.ms also covers metadata, so producing to a nonexistent topic looks identical.

retries=3 does almost nothing intended. retries defaults to Integer.MAX_VALUE and stopped being the limit when delivery.timeout.ms (120 s) arrived — that bounds the whole attempt. Worse, it can abandon a transient leader election that would have resolved. To give up after ten seconds, set delivery.timeout.ms=10000.

Q7 · The idempotent producer, and its boundaries

Mechanism. The producer obtains a producer id and an epoch. Every batch carries the PID, the epoch and a per-partition sequence number. The broker keeps the last sequence per (PID, partition): a batch whose sequence it has already seen is acknowledged and discarded, so the duplicate never reaches the log; a batch arriving ahead of the expected sequence is rejected with OutOfOrderSequenceException and retried in order.

Because the broker enforces dedupe and ordering, max.in.flight can stay at 5 rather than being forced to 1 — you keep pipelining and lose the reordering risk. That is the practical win, and it is why idempotence became a default rather than an option.

Three things it does not give you.

  • It does not survive a producer restart. The PID belongs to a producer session; a new instance gets a new one, and the broker has no way to recognise what the previous instance wrote. Crash before the response arrives, restart, retry — two copies.
  • It is not cross-partition or cross-topic atomicity. Two records to two partitions can still end with one written and one not. That is transactions.
  • It is not end-to-end exactly-once. It removes duplicates introduced by the producer's own retries. An application that calls send() twice has sent two records, and the broker is right to keep both.

The line worth having ready: idempotence makes a retry safe, not a system exactly-once. Candidates who stop at "it gives you exactly-once" get taken apart by the restart question.

Q8 · How the null-key partitioner changed, and why twice

Before 2.4 — round-robin per record. A modest produce rate spread records across every partition, so each batch held very little. Many small requests, poor compression ratios, more broker work per byte.

2.4, KIP-480 — the sticky partitioner. Fill one partition's batch, send it, then switch. Same traffic, far fewer and far larger batches. A straightforward win.

3.3, KIP-794 — strictly uniform sticky. The first fix equalised batches per partition. But a slow broker drains slower, so sticking to its partitions for the same number of batches meant sending it proportionally more bytes — pushing load toward the brokers least able to take it, which is exactly backwards and only shows up under real-world skew. The current partitioner assigns by how much each partition has actually accepted, and partitioner.adaptive.partitioning.enable actively steers away from slow brokers. DefaultPartitioner is deprecated; leaving partitioner.class unset gets current behaviour.

Why the second change is the interesting one. The first optimised a proxy for the thing that mattered — batch count instead of bytes delivered — and the error was invisible in design review and only appeared in production with heterogeneous broker performance. Being able to say that, rather than just listing three versions, is the point of the question.

Q9 · Intermittent RecordTooLargeException for the same payload size

Two limits, in different places. max.request.size on the producer (1 MiB) is checked client-side and fails before anything leaves the process. message.max.bytes on the broker or topic is checked after the record crosses the network. Raising one without the other relocates the failure rather than removing it, and the broker-side rejection arrives later and with a less obvious message.

Why it is intermittent, which is the real question. The limit applies to the compressed batch, not the individual record. A record that fits comfortably on its own can push a batch over the limit when it happens to be grouped with others, and whether it is grouped depends on timing, load and linger.ms. Compression ratio varies with the batch's contents too, so two batches of identical raw size can land on opposite sides of the limit. Same payload, different outcome, no pattern visible from the application.

Second source of intermittency: a topic-level max.message.bytes override means the limit can differ per topic, so a producer writing to several topics fails on some and not others.

How to diagnose. Compare max.request.size, the broker's message.max.bytes, and any topic override; measure the compressed batch size rather than the record size; and check whether failures correlate with load rather than with payload. Then check the consumer side before changing anything — fetch.max.bytes and max.partition.fetch.bytes must accommodate the new size, or the symptom moves from a visible error to a consumer that silently stalls forever on a message it cannot fetch. An error is the good outcome.

Q10 · Lowest possible end-to-end latency, and the floor

Producer side: linger.ms=0, a smaller batch.size so nothing waits to fill, compression.type=none or lz4, and keep idempotence on because it costs nothing in latency.

Two mistakes that look like tuning. Raising buffer.memory does nothing for latency and hides backpressure that you would rather see. Setting max.in.flight=1 "to be safe" serialises requests and adds a round-trip per batch, buying an ordering guarantee that idempotence already provides.

The floor is not on the producer. With acks=all, the leader cannot respond until every in-sync replica has the record, so a replication round-trip is in the critical path. And from M3, a consumer cannot read past the high watermark, which needs that same round-trip to advance. Add the consumer's fetch.max.wait.ms on an empty fetch and you have the floor: roughly one replication round-trip plus one fetch wait, with no producer setting that removes it.

Dropping to acks=1 removes the first half and buys a silent data-loss window — almost never the right trade, and worth naming as a rejected option rather than leaving unmentioned.

The move that makes this a senior answer: separate which half of the latency is yours to tune from which half is the durability guarantee showing itself — and then ask whether the requirement is genuinely end-to-end or just produce-ack. Teams routinely measure the second and specify the first, and the gap between them is the replication round-trip they are about to try to tune away.
