Lab 04 — KRaft and the metadata plane

Five steps, no Python. You read the controller quorum, find your own topic creation sitting in the metadata log as records, kill the active controller and time the failover. Metadata stops being an abstraction the moment you read it as a log.

Expect 30-40 minutes. Three nodes in combined mode; production uses isolated controllers, and step 5 covers why.

Setup

Broker ports clash with labs 01 and 03 — docker compose down in those first.

cd labs/lab04-kraft
docker compose up -d && docker compose ps

STEP 1Read the quorum

Proves: the control plane is a Raft quorum over a log, with offsets and lag like any other Kafka log.

Predict first

Three combined-mode nodes. How many are voters in the metadata quorum, how many are observers, and how many can report themselves as the active controller at once?

Run

docker exec lab04-kafka1 /opt/kafka/bin/kafka-metadata-quorum.sh \
  --bootstrap-server localhost:9092 --describe --status

docker exec lab04-kafka1 /opt/kafka/bin/kafka-metadata-quorum.sh \
  --bootstrap-server localhost:9092 --describe --replication

Expected

ClusterId:              MkU3OEVBNTcwNTJENDM2Qk
LeaderId:               2
LeaderEpoch:            4
HighWatermark:          1183
CurrentVoters:          [1, 2, 3]
CurrentObservers:       []

And a per-replica table with LogEndOffset and Lag for each node.

Why

That output is a Kafka log's vocabulary — leader, epoch, high watermark, log end offset, lag — applied to cluster metadata. That is the whole of KIP-500 in one screen: Kafka is a replicated log, metadata needs replicating, so metadata goes in a Kafka log.

All three nodes are voters here because all three have the controller role. In isolated mode, controllers are voters and brokers appear as observers: they fetch the log but do not vote. Exactly one node is leader — the active controller — and it is the only one allowed to write metadata. LeaderEpoch is the same epoch concept as M3's leader epoch, doing the same job one layer up.

Check yourself

Quorum sizing follows Raft: N voters tolerate (N-1)/2 failures. How many failures does a 4-controller quorum tolerate, and how does that compare to 3? What does that tell you about ever choosing an even number?

STEP 2Find your own topic inside the metadata log

Proves: metadata changes are log records, not a database write.

Predict first

You will create one topic with 3 partitions. How many records do you expect that to append to __cluster_metadata — one, three, or four? What would each one be?

Run

docker exec lab04-kafka1 /opt/kafka/bin/kafka-topics.sh --bootstrap-server localhost:9092 \
  --create --topic lab04.metadata-demo --partitions 3 --replication-factor 3

docker exec lab04-kafka1 /opt/kafka/bin/kafka-dump-log.sh \
  --cluster-metadata-decoder \
  --files /tmp/kraft-combined-logs/__cluster_metadata-0/00000000000000000000.log \
  | tail -30

Expected

Near the end of the dump, one TopicRecord carrying the topic name and its id, followed by one PartitionRecord per partition, each holding the replica list, the ISR, the leader and a leader epoch. Four records for a three-partition topic.

Why

Creating a topic is an append to a log. Every broker learns about it by fetching those records and applying them in order — the same mechanism as a consumer reading a topic, which is why the ordering guarantees are the ones you already understand from M1.

Notice what a PartitionRecord contains: replicas, ISR, leader, leader epoch. Everything M3 was about is stored here. When the ISR shrinks because a follower fell behind, that is a new record appended to this log by the active controller, and every broker learns of it by fetching.

Then try the state view

docker exec -it lab04-kafka1 /opt/kafka/bin/kafka-metadata-shell.sh \
  --snapshot /tmp/kraft-combined-logs/__cluster_metadata-0/00000000000000000000.log
# ls /
# cat /image/topics
# exit

The dump shows the log; the shell shows the state that replaying the log produces. Same relationship as a compacted topic and the table it converges to, from M2.

Check yourself

This log records every metadata change ever made and is replayed on startup. What stops it from growing forever and making startup slower every month?

STEP 3Kill the active controller and time the failover

Proves: failover is an election, not a state transfer.

Predict first

Under ZooKeeper, a controller failover on a large cluster took minutes because the new controller loaded all state from ZooKeeper first. Here, how long do you expect it to take — and what is the new controller not having to do?

Run

# LeaderId from step 1 tells you which node to kill
docker stop lab04-kafka2

docker exec lab04-kafka1 /opt/kafka/bin/kafka-metadata-quorum.sh \
  --bootstrap-server localhost:9092 --describe --status

# and confirm the data plane never noticed
docker exec lab04-kafka1 /opt/kafka/bin/kafka-topics.sh \
  --bootstrap-server localhost:9092 --describe --topic lab04.metadata-demo

Expected

A new LeaderId and an incremented LeaderEpoch, effectively immediately. Partitions whose leader was on the stopped node have been re-elected; the rest are untouched.

Why

The surviving controllers had been applying the same metadata log all along, so the promoted one already holds the full state in memory. Promotion is a Raft election — a majority vote and an epoch bump — with no state to load. That is why failover no longer scales with partition count, and why the practical ~200k partition ceiling of the ZooKeeper era went away: the ceiling was set by failover time, not by disk or throughput.

Note also what did not happen: no produce or consume was interrupted on partitions whose leader survived. The control plane and data plane are genuinely separate.

Check yourself

Suppose you stop two of the three nodes instead of one. Metadata operations stop — but can producers still write to a partition whose leader is the surviving broker? And what happens if that broker then loses a follower?

STEP 4Watch brokers follow the log by offset

Proves: "this broker is behind" is now a number.

Run

docker start lab04-kafka2
# immediately, repeatedly:
docker exec lab04-kafka1 /opt/kafka/bin/kafka-metadata-quorum.sh \
  --bootstrap-server localhost:9092 --describe --replication

Expected

The restarted node reappears with a LogEndOffset behind the others and a non-zero Lag, which closes over a few seconds as it catches up.

Why

This is the quiet improvement over ZooKeeper, and the one worth having an opinion about. Previously the controller pushed metadata updates by RPC; a broker that missed one had no way to notice, because there was no version and no offset to compare against — divergence was possible and undetectable. Now metadata is a log, every node has an offset, and being behind is a measurable quantity.

In production the metric is MetadataLag per broker. Sustained non-zero lag means a broker is acting on a stale view of leadership and topic configuration — which looks like inexplicable client errors long before it looks like a metadata problem.

Check yourself

A broker has 4,000 metadata records of lag. Name two client-visible symptoms that could produce, before anyone thinks to look at the control plane.

STEP 5Combined vs isolated, and what this lab is not showing you

Proves: the shape you run in production is not the shape in this compose file.

Run

docker exec lab04-kafka1 env | grep PROCESS_ROLES
docker exec lab04-kafka1 /opt/kafka/bin/kafka-metadata-quorum.sh \
  --bootstrap-controller localhost:9093 --describe --status

Why

Every node here is broker,controller — combined mode. Three containers instead of six, which is right for a laptop and wrong for production. The failure mode it invites is precisely the cost it saves: a node under data-plane pressure — GC, disk saturation, a hot partition — is also a controller, and starving the control plane during a data-plane incident is how a bad hour becomes a bad day.

Isolated mode gives controllers their own small nodes. They are sized by metadata volume, which means partition count, not by throughput — so a cluster pushing gigabytes a second runs a happy three-node quorum on small instances. Brokers then appear as observers in --describe --replication: they fetch the metadata log but do not vote.

Note the second command: --bootstrap-controller talks to the controller listener directly, which still works when brokers are unhealthy. During an incident where brokers are not answering, that is how you ask the control plane what it thinks is happening.

Check yourself

You are sizing a new cluster: 40 brokers, 50,000 partitions, 2 GB/s. How many controllers, isolated or combined, and what sizes them? Which of those three numbers is irrelevant to the answer?

Tear down

docker compose down -v

When something goes wrong

SymptomCause and fix
Ports already in useLab 01 or 03 is still up. docker compose down in those directories.
kafka-dump-log.sh prints nothing readable--cluster-metadata-decoder is required for this topic; without it the records are opaque bytes.
Metadata shell will not open the filePoint it at the newest .log or .checkpoint in __cluster_metadata-0/; list the directory first.
Quorum commands hang after stopping a nodeYou stopped the node you were connecting through. Use another container, or --bootstrap-controller.
No new leader after stopping one nodeGive it a second and re-run. If two of three are down there is no majority and no election is possible — that is the quorum working.
