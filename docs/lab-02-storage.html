Lab 02 — What a partition looks like on disk

Six steps. Module 1 said a partition is a log on disk; here you open that log, split it into segments, read its index, fail to delete from it, fix that, and compact it by key. Predict before every command — being wrong about step 3 in particular is the point of step 3.

Expect 45-60 minutes. One broker — storage is a per-partition, per-broker concern.

Setup

cd labs/lab02-storage
docker compose up -d && docker compose ps     # healthy in ~30s

python3 -m venv .venv
source .venv/bin/activate                     # once per terminal
pip install -r requirements.txt
cd scripts

Two broker settings are turned down so you are not waiting around: log.retention.check.interval.ms to 10s (default 5 minutes) and log.cleaner.backoff.ms to 5s. Production leaves both alone — and knowing they exist is half of why retention looks slow in real clusters.

STEP 1Roll some segments and read their names

Proves: a partition is a directory of segments, and the filename is the index into them.

Predict first

The topic will be created with segment.bytes=1024, then given 200 records of about 100 bytes each. Roughly how many .log files do you expect? And what do you think decides each file's name?

Run

docker exec lab02-kafka /opt/kafka/bin/kafka-topics.sh --bootstrap-server localhost:19092 \
  --create --topic lab02.segments --partitions 1 --replication-factor 1 \
  --config segment.bytes=1024

python3 01_fill_segments.py 200 100

docker exec lab02-kafka ls -la /tmp/kraft-combined-logs/lab02.segments-0/

Expected

00000000000000000000.index
00000000000000000000.log
00000000000000000000.timeindex
00000000000000000009.index
00000000000000000009.log
00000000000000000009.timeindex
...
00000000000000000193.log        # the active segment
leader-epoch-checkpoint
partition.metadata

The exact offsets depend on how batching fell out on your run — the producer writes batches, and a segment rolls when the batch that would exceed segment.bytes arrives. The shape is what matters: many triples, each named after the offset it starts at.

Why

The name is the segment's base offset, zero-padded to 20 digits so that lexical order equals numeric order. To find offset 400, the broker binary-searches this list of names and picks the segment whose base offset is the largest one not greater than 400 — without opening a single file. Zero-padding is what makes a plain string sort do that correctly.

Only the last segment is open for writing. It is the active segment, and it is the one that steps 3 and 5 keep running into.

Check yourself

Production defaults are segment.bytes=1 GiB and segment.ms=7 days. On a topic receiving 10 records a minute at 200 bytes each, which limit rolls the segment, and how long does that take?

STEP 2Dump the log and its index

Proves: the index is sparse, and records are stored as batches rather than individually.

Predict first

A segment holds about 10 records here. How many entries do you expect in its .index — ten, or fewer? And in the .log dump, will you see 10 separate records or something else?

Run

docker exec lab02-kafka /opt/kafka/bin/kafka-dump-log.sh \
  --files /tmp/kraft-combined-logs/lab02.segments-0/00000000000000000000.log \
  --print-data-log | head -20

docker exec lab02-kafka /opt/kafka/bin/kafka-dump-log.sh \
  --files /tmp/kraft-combined-logs/lab02.segments-0/00000000000000000000.index

Expected

The log dump shows baseOffset, lastOffset, count, producerId, isTransactional, compresscodec — these are batch headers, with the records nested inside. The index dump shows very few entries, often zero or one for a segment this small.

Why

An index entry is written roughly every log.index.interval.bytes (4 KiB) of log, not per record — and a 1 KiB segment never reaches 4 KiB, so it may have no entries at all beyond the implicit base. Resolving an offset therefore ends in a short forward scan through the .log, by design.

Why not index every record? These files are memory-mapped, so a dense index competes for exactly the page-cache memory that makes reads fast. Trading a few microseconds of scan for cache headroom is the right call, and it is a good answer to give when asked why the lookup is not O(1).

The batch headers are the other half of the lesson: producerId is the idempotent producer (M5) and isTransactional is exactly-once (M7). The broker stores what the producer framed, untouched.

Check yourself

Dump the .timeindex as well. Given what it maps, which CLI operation would be impossible without it?

STEP 3The retention trap

Proves: retention deletes whole segments and never the active one. This is the most common Kafka support question there is.

Predict first

You are about to create a topic with retention.ms=30000 — thirty seconds — write a handful of records, and wait two minutes. How many records will still be readable? Write the number down before running it.

Run

docker exec lab02-kafka /opt/kafka/bin/kafka-topics.sh --bootstrap-server localhost:19092 \
  --create --topic lab02.trap --partitions 1 --replication-factor 1 \
  --config retention.ms=30000

python3 01_fill_segments.py 20 100
# ^ edit TOPIC in the script, or just produce with the console producer:
#   docker exec -i lab02-kafka /opt/kafka/bin/kafka-console-producer.sh \
#     --bootstrap-server localhost:19092 --topic lab02.trap

# wait two minutes, then ask where the log starts and ends
docker exec lab02-kafka /opt/kafka/bin/kafka-run-class.sh kafka.tools.GetOffsetShell \
  --bootstrap-server localhost:19092 --topic lab02.trap --time -2    # earliest
docker exec lab02-kafka /opt/kafka/bin/kafka-run-class.sh kafka.tools.GetOffsetShell \
  --bootstrap-server localhost:19092 --topic lab02.trap --time -1    # latest

docker exec lab02-kafka ls -la /tmp/kraft-combined-logs/lab02.trap-0/

Expected

Earliest offset is still 0. Nothing has been deleted, minutes after every record became eligible. One .log file, still the active one.

Why

Retention operates on closed segments. The active segment is never deleted, and on this topic it has not rolled because rolling needs segment.bytes (1 GiB) or segment.ms (7 days) — neither of which twenty small records will reach. Every record is eligible for deletion and none of them can go, because they share a file with records that are not.

The correct mental model: retention is a floor on how long data lives, never a ceiling. The real guarantee is "at least retention.ms, plus up to one segment's worth of time, plus up to one log.retention.check.interval.ms". Teams that promise regulators a deletion deadline on the basis of retention.ms alone are promising something Kafka does not do.

Check yourself

A compliance requirement says personal data must be gone within 24 hours. What do you set, and what do you tell the compliance team the actual upper bound is?

STEP 4Fix it and watch the data go

Proves: segment rolling is the missing half of retention.

Run

docker exec lab02-kafka /opt/kafka/bin/kafka-configs.sh --bootstrap-server localhost:19092 \
  --alter --entity-type topics --entity-name lab02.trap \
  --add-config segment.ms=20000

# produce a few more records so a roll actually happens, then wait ~60s
docker exec lab02-kafka /opt/kafka/bin/kafka-run-class.sh kafka.tools.GetOffsetShell \
  --bootstrap-server localhost:19092 --topic lab02.trap --time -2

Expected

Earliest offset moves forward from 0 — the old segment closed, aged past 30 seconds, and was deleted. The log now starts partway in.

Why

Nothing about retention.ms changed. All that changed is that segments now close, which is what makes them eligible. This is worth internalising as a pair: every retention setting needs a segment setting that lets it act.

Notice too that the earliest offset moved rather than the records being renumbered. Offsets are immutable; deleting from the front moves the log's start, which is why a consumer with a committed offset below the new earliest gets an OFFSET_OUT_OF_RANGE and falls back to auto.offset.reset — silently skipping data if that is set to latest.

Check yourself

A consumer group was down for a week on a topic with 3-day retention. It restarts with auto.offset.reset=latest. What happens, and what would earliest have done instead? Which is the safer default and why is it not the obvious one?

STEP 5Compaction, tombstones and offset gaps

Proves: compaction keeps the newest value per key, leaves holes in the offset sequence, and never touches the active segment.

Predict first

Four keys, three versions each, plus a tombstone for user-2 — thirteen records at offsets 0 to 12. After compaction, how many records survive, and what offsets do they have? That second half is the interesting one.

Run

docker exec lab02-kafka /opt/kafka/bin/kafka-topics.sh --bootstrap-server localhost:19092 \
  --create --topic lab02.compacted --partitions 1 --replication-factor 1 \
  --config cleanup.policy=compact \
  --config segment.bytes=1024 \
  --config min.cleanable.dirty.ratio=0.01 \
  --config min.compaction.lag.ms=0 \
  --config delete.retention.ms=10000

python3 02_compaction_demo.py

# the cleaner only works on closed segments — force a roll
docker exec lab02-kafka /opt/kafka/bin/kafka-configs.sh --bootstrap-server localhost:19092 \
  --alter --entity-type topics --entity-name lab02.compacted \
  --add-config segment.ms=5000

# produce one more record to trigger the roll, wait ~30s, then look
docker exec lab02-kafka ls /tmp/kraft-combined-logs/lab02.compacted-0/
docker exec lab02-kafka /opt/kafka/bin/kafka-dump-log.sh \
  --files /tmp/kraft-combined-logs/lab02.compacted-0/00000000000000000000.log \
  --print-data-log | grep -E 'offset:|payload'

Expected

Only the newest value per key survives, and user-2 is gone once its tombstone passes delete.retention.ms. The surviving records keep their original offsets, so the sequence reads something like 8, 10, 11 — with gaps where the superseded records used to be.

Why

Compaction rewrites segments and drops superseded records, but it never renumbers. An offset identifies a position in the log forever, and consumers have committed against those numbers. The consequence for consumer code: anything assuming offset+1, or counting records to infer progress, is wrong on a compacted topic.

A tombstone is a record with a null value. It marks the key deleted and survives for delete.retention.ms (default 24 h) so consumers have a window to observe the deletion — then it disappears with the key. A consumer offline longer than that window never learns the key was deleted and keeps a stale value indefinitely. That is a real correctness bug in cache-invalidation and CDC pipelines, and the usual answer is a periodic full rebuild rather than trusting incremental state.

Finally: the active segment is never compacted, so the head of the log always holds uncompacted duplicates. Compaction is eventual. A consumer at the head sees every version; one starting from the tail sees only the latest.

Check yourself

__consumer_offsets is a compacted topic. Given what compaction converges to, explain in one sentence why that is the right choice for it — and why a topic of order events would be the wrong choice.

STEP 6Cold versus warm read

Proves: reads are served from the page cache, not from disk — and the honest version of what that means on a laptop.

Run

python3 03_read_timing.py lab02.segments

Expected

Two passes with similar timings. That is not a failed experiment — it is the result. The data was written moments ago and never left the page cache, so neither pass touched a disk.

Why

Kafka does not maintain its own cache. Writes land in the OS page cache and are not fsynced per record (log.flush.interval.messages defaults to effectively never); durability comes from replication to other brokers rather than from reaching the platter. Reads of recent data come back out of that same cache and are sent with sendfile — kernel straight to socket, no copy into user space, no deserialisation.

Two consequences worth being able to state: a broker process crash loses nothing because the cache belongs to the kernel, while a machine power loss can lose unflushed data on that broker — which is exactly why durability is acks=all plus min.insync.replicas, and why M3 exists. And the JVM heap stays small, so a broker serving terabytes runs on a few gigabytes of heap with GC off the request path.

To see a genuinely cold read you would need to evict the cache (echo 3 > /proc/sys/vm/drop_caches on a Linux host) or read data old enough to have been evicted naturally. Not worth doing inside Docker on a laptop; knowing why the two numbers match is the takeaway.

Check yourself

Your cluster enables TLS. What happens to the sendfile path, and what should you expect to see in broker CPU and throughput? (This is the standard follow-up after a candidate says "zero-copy".)
