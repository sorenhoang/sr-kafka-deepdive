Module 2

Storage internals

The module that turns "Kafka is fast because sequential writes" into four separate mechanisms you can defend one at a time — and then shows what deletes data, which is where production surprises actually come from.

The log is a directory of segments

A partition is a directory named <topic>-<partition>. Inside it, the log is split into segments, each a trio of files sharing a name:

lab02.segments-0/
  00000000000000000000.log        # records
  00000000000000000000.index      # offset   -> byte position
  00000000000000000000.timeindex  # timestamp -> offset
  00000000000000000317.log        # next segment, starts at offset 317
  00000000000000000317.index
  00000000000000000317.timeindex

The filename is the segment's base offset, zero-padded to 20 digits. That is not decoration: it is the index. To find offset 400, the broker binary-searches the filenames to pick the segment, with no file opened yet.

Only the newest segment — the active segment — is open for writing. It rolls when either limit is hit: segment.bytes (default 1 GiB) or segment.ms (default 7 days). Remember both; the second one is the cause of the most common retention bug, below.

How a read resolves an offset

  1. Binary search the segment filenames → the segment containing the offset.
  2. Look up the .index → the nearest indexed offset at or below the target, giving a byte position.
  3. Scan forward in the .log from there to the exact record.

The index is deliberately sparse: one entry roughly every log.index.interval.bytes (default 4 KiB) of log, not one per record. Dense would make lookups marginally faster and cost memory proportional to record count — and these files are memory-mapped, so the index competes with the page cache for exactly the memory that makes reads fast. Sparse plus a short forward scan is the better trade, and it is why the final step is a scan rather than a direct hit.

.timeindex does the same for timestamps, which is what makes --to-datetime offset resets and time-based seeks possible.

The batch is the unit, not the record

Records are stored in record batches exactly as the producer framed them — baseOffset, lastOffsetDelta, producerId, isTransactional, then the compressed records. Compression is applied per batch, so a batch of 500 similar records compresses far better than 500 individually; this is why linger.ms affects your storage bill and not just latency.

The important property: the on-disk format is byte-identical to the wire format. The broker never parses a record, never re-frames one, never keeps per-record bookkeeping. It receives bytes, appends bytes, and later sends the same bytes. Hold on to that — it is what makes the next section possible.

Why it is fast — four mechanisms

1 · Sequential I/O

Appending to a file is sequential, and sequential throughput beats random access by roughly an order of magnitude on spinning disks and still substantially on NVMe. The index files preserve this on the read path too: an offset becomes a byte position by lookup, so reads are a seek followed by a sequential scan rather than a walk.

2 · Page cache instead of an application cache

Writes land in the OS page cache. Kafka does not fsync per record — log.flush.interval.messages defaults to effectively never, and durability comes from replication to other brokers, not from reaching the platter. Three consequences worth stating:

  • A broker process crash loses nothing, because the page cache belongs to the kernel and survives the process. A machine power loss can lose unflushed data on that broker — which is precisely why acks=all with min.insync.replicas is the durability story, and M3 is about getting that right.
  • The JVM heap stays small, since the data lives in the kernel's cache rather than a buffer pool. GC pauses stay out of the request path. A broker serving terabytes runs comfortably on a heap of a few gigabytes.
  • The cache is shared and warm across restarts of the broker process, and a consumer reading recent data usually never touches a disk at all.

3 · Zero-copy on the read path

Because the bytes a consumer wants are already in the page cache in the exact format it expects, Kafka serves them with sendfile: the kernel moves them from page cache directly to the socket, with no copy into user space and no deserialisation. The broker never materialises a record on a fetch.

The senior follow-up

When does Kafka not get zero-copy? When the connection is encrypted. TLS has to encrypt the bytes, which means pulling them into user space — so sendfile is off and throughput drops measurably. That is a real capacity-planning input, not trivia, and it is the question an interviewer asks after you say "zero-copy".

Historically there was a second case: serving an old client that needed an older message format forced the broker to down-convert, losing zero-copy and spiking broker CPU. Kafka 4.0 removed message formats v0 and v1 (KIP-724) along with message.format.version, so on a 4.x broker that case is gone — worth saying, because it shows you know what changed and when.

4 · Batching, which is what ties the other three together

The broker does no per-record work because it never needs to look inside a batch. No parsing, no re-framing, no per-message state. That is not an optimisation layered on top — it is the reason zero-copy is possible at all, since any transformation would force the broker to touch the bytes.

The through-line for the whole section: Kafka is fast because the broker was given almost nothing to do, and every mechanism above follows from refusing to keep per-message state. That refusal is the same one that costs you per-message retry and priority back in M0.

Retention — what actually deletes data

Deletion is driven by policy, never by consumption. Two limits, both enforced per partition:

  • retention.ms — delete segments older than this (default 7 days)
  • retention.bytes — keep at most this many bytes per partition, deleting oldest first (default unlimited). A 100 GB budget on a 50-partition topic is 5 TB, not 100 GB. People get this wrong.
The bug everyone hits once

Deletion happens at segment granularity, and the active segment is never deleted. So "I set retention.ms=60000 and nothing is being deleted" is almost always correct behaviour: on a low-traffic topic the active segment has not rolled, because rolling needs 1 GiB of data or 7 days of time. Every record is eligible and none can go, because they share a file with records that are not.

The fix is to make segment.ms (or segment.bytes) small enough that segments close and become whole-segment eligible. Retention is a floor on how long data lives, never a ceiling — the real guarantee is "at least retention.ms, plus up to one segment's worth of time".

The retention thread also only runs every log.retention.check.interval.ms (default 5 minutes), which adds another lag between eligible and gone.

Log compaction — retention by key

cleanup.policy=compact changes the question from "how old is this record" to "is this the newest value for its key". The cleaner rewrites segments keeping only the latest record per key. A record with a null value is a tombstone: it marks the key as deleted, survives for delete.retention.ms (default 24 h) so that consumers have a chance to see the deletion, then disappears with the key.

What compaction gives you is a log that converges to a table: replay it from the start and you end up with current state per key. That is the mechanism behind __consumer_offsets, Kafka Streams changelog topics, and CDC snapshots.

Tiered storage (KIP-405)

With remote.storage.enable=true, a topic keeps recent segments locally (local.retention.ms / local.retention.bytes) and moves older closed segments to object storage, while retention.ms continues to govern total lifetime. Consumers read through transparently; the offset space is unchanged.

Two things it buys that matter in an interview:

  • Cost. Long retention stops requiring broker disks sized for it. Keeping a year of history becomes an object-storage bill rather than a cluster-sizing problem.
  • Recovery time. Replacing a broker previously meant replicating every byte it held. With most history remote, a new broker only pulls the local window, so rebuild drops from hours to minutes. This is the one people forget, and it is the stronger argument.

The cost is a read-latency cliff for consumers that fall behind into remote segments, plus the operational surface of a second storage system. And it does not apply to compacted topics.
