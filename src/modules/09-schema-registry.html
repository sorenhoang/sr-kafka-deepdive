Module 8

Schemas, the registry & evolution

Kafka moves bytes and has no opinion about what is in them. Every topic is therefore an API between teams who deploy on different days, and this module is about keeping that API from breaking at 3am on a deploy nobody coordinated.

The broker does not know what a record is

A record's key and value are byte arrays. The broker stores, replicates and serves them without parsing — which is part of why it is fast (M2: zero-copy only works if nobody looks inside). The consequence is that the contract lives entirely in the clients: the producer's serializer and the consumer's deserializer must agree, and nothing in Apache Kafka checks that they do.

Schema Registry exists to put that agreement somewhere. It is worth saying precisely what it is: not part of Apache Kafka. The common one is Confluent's (source-available, community licence); Apicurio Registry and cloud equivalents such as AWS Glue Schema Registry fill the same role. It is a separate service with its own REST API that stores schemas — in Confluent's case, in a compacted Kafka topic, _schemas, the same trick as M4 and M7.

Avro's defining property is the one that makes a registry mandatory rather than nice: the bytes do not carry field names or tags, so a reader cannot decode a record without the exact schema it was written with. It then resolves writer schema against its own reader schema — matching by name, filling missing fields from defaults, skipping unknown ones. Evolution in Avro is that resolution step.

The wire format

byte 0      magic byte, 0x0
bytes 1-4   schema id, big-endian int    // global id in the registry
bytes 5..   [Protobuf only: message-index array, which message in the .proto]
            the encoded payload

The serializer registers (or looks up) the schema, gets an id, and prefixes it. The deserializer reads the id, fetches the schema once, caches it forever — ids are immutable — and decodes. Five bytes per record buys self-describing data without shipping the schema.

Two consequences people miss. The data is now coupled to the registry: a record whose id the registry cannot resolve is undecodable, so the registry is as critical as the brokers for anyone reading old data. And a consumer using a plain StringDeserializer on this topic sees five garbage bytes before every value — the most common first symptom of "someone switched this topic to Avro".

Subjects, and what a subject is for

A subject is the unit the registry versions and checks compatibility against. Which subject a schema lands in is decided by the client's naming strategy:

StrategySubjectMeans
TopicNameStrategy (default)<topic>-valueOne schema lineage per topic: every record on the topic is the same type
RecordNameStrategyfully-qualified record nameType evolves independently of topic; compatibility is checked across every topic using it
TopicRecordNameStrategy<topic>-<record>Several types per topic, each with its own lineage

This is where a design choice from M1 comes back. Ordering exists only within a partition, so if OrderCreated, OrderPaid and OrderShipped must be seen in order for one order, they must share a topic and a key — which the default strategy forbids, because it allows one type per topic. The fixes are a record-name strategy, or a single envelope/union type (an Avro union or Protobuf oneof, with schema references) under the topic subject. Choosing the topic layout by event ordering and then discovering the registry fights it is a classic sequence.

The mode is a statement about deploy order, not about schemas. BACKWARD says the new reader handles old data, so readers must be upgraded before any writer produces the new shape. Most teams pick it as a default and then deploy the producer first, which is exactly the order it does not protect.

Why non-transitive is a trap on Kafka specifically

Non-transitive modes check the new schema against the latest version only. v3 can be compatible with v2, and v2 with v1, while v3 cannot read v1. On a queue that would not matter. On Kafka it does: retention keeps v1 records on disk, compacted topics keep them forever (M2), and a new consumer group with auto.offset.reset=earliest or any replay reads them. If topics are replayed, the honest mode is BACKWARD_TRANSITIVE or FULL_TRANSITIVE.

Safe and breaking, per format

  • Avro — the default is the whole game. Adding a field without one is breaking under BACKWARD: the new reader has nothing to fill it with from old data. Renames are breaking unless an aliases entry maps the old name. Changing a type is breaking except for Avro's defined promotions (e.g. int → long).
  • Protobuf — field numbers are identity. Renaming a field is safe on the wire (it breaks JSON mappings and generated code, which is not nothing); reusing a number is silent corruption, which is why deleted fields should be marked reserved. In proto3 an absent field decodes as its zero value, so "not sent" and "sent as 0" are indistinguishable unless the field is declared optional.
  • JSON Schema — the pitfall is the content model. In an open model (additionalProperties unset, i.e. true) the old schema already permitted any extra property of any type, so the checker cannot prove old data matches a newly declared property — adding a field can be rejected. In a closed model the reverse problems appear. The rules are not the Avro intuitions; check them rather than assume them.

Why the broker does not validate

Apache Kafka brokers never parse payloads, and adding it would cost the zero-copy path and couple every broker to every schema. So enforcement is client-side and therefore optional: any producer with a plain ByteArraySerializer can write anything to any topic it is allowed to write to. Confluent Server adds per-topic broker-side schema-id validation (confluent.value.schema.validation), which checks that the id is registered for the subject — not that the payload actually decodes. Elsewhere, ACLs on who can produce (M11) are the real enforcement.

Two client settings matter more than anything above. auto.register.schemas defaults to true, which means a producer deploy is a schema change, made by whatever code happened to compile. In production, set it to false, register schemas from CI where the compatibility check fails the build, and have producers use the registered version (use.latest.version). The registry's compatibility check is only a gate if something cannot route around it.

When a record will not deserialize

This is M6's poison pill with a cause attached. Deserialization happens inside poll(), so a record that cannot be decoded — unknown schema id, a writer that bypassed the serializer, an incompatible change — fails before your code sees it. The Java consumer throws a RecordDeserializationException carrying the partition and offset; if nothing catches it the consumer retries the same offset forever, and that partition's lag climbs while every other partition looks healthy.

  • Catch it, seek() past the offset, and send the raw bytes to a dead-letter topic with headers saying why. Frameworks package this (Spring's ErrorHandlingDeserializer, Connect's errors.tolerance with a DLQ).
  • Skipping is a decision to lose a record. It belongs in a DLQ that someone owns and replays, not in a log line.
  • Keys deserve extra care: changing how a key is serialized changes its bytes, which changes its partition (M1) and its compaction identity (M2). A key schema change is a repartition in disguise.

Contracts and ownership

A topic with a schema is a published API, and the same rules apply: one owning team, a review process for changes, deprecation instead of deletion. The schemas belong in version control next to the producer, checked against the registry in CI. And soft-deleting a schema version in the registry does not delete the data written with it — hard-deleting one makes those records undecodable. Treat schema deletion like deleting a database column that still has rows.

This is also where M7's outbox pays off twice: the outbox row is the event's contract, written and reviewed alongside the business change, rather than an afterthought serialized in a message-publishing helper.

Answering "how do you evolve event schemas safely?"

Kafka itself is schema-agnostic, so the contract is enforced by clients through a registry — Confluent's or Apicurio, not Apache Kafka — which prefixes each record with a schema id and rejects incompatible changes per subject. The compatibility mode is really a deploy-order decision: BACKWARD means consumers upgrade first, FORWARD producers first, FULL either. Because Kafka retains and replays old data, I'd use the transitive variants, register schemas from CI with auto-registration off, and know the format's rules — Avro defaults, Protobuf's never-reuse-a-field-number, JSON Schema's content model. And I'd plan for the record that still fails: catch the deserialization error, dead-letter it, and keep the partition moving.
