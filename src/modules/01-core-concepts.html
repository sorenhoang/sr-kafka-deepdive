One definition, derive everything else from it

Mental model

Kafka is a distributed, replicated, append-only commit log in which the broker is only responsible for storing and serving the log, while the read position is owned by the consumer.

This is the one thing worth memorising. Every characteristic property of Kafka follows from it, so in an interview you can derive the answer on the spot instead of reciting it.

Because Kafka is a log and consumers own their offsetsIt follows that
The broker keeps no per-message stateVery high throughput; the broker does almost nothing but sequential I/O
Reading is non-destructiveMany consumer groups read the same data independently; replay is free
Data is deleted by retention policy, not by consumptionKeep 7 days, a year, or forever via compaction / tiered storage
There is no per-message ack at the brokerNo per-message retry, delay, priority or selective nack
Order only exists inside one log fileOrder is guaranteed within a partition only
Nothing is indexed by contentYou cannot ask for “messages where status=FAILED” — that is a database's job

Answering “Kafka or RabbitMQ?”

Do not compare throughput. Compare the unit of state: Kafka tracks state as a stream plus an offset, RabbitMQ tracks it per message. If the problem needs control over individual messages — its own retry, its own delay, its own priority — you are fighting Kafka's design. If the problem needs one event stream that several consumers share and can replay, the opposite holds.

When not to use Kafka

  1. Low-latency request/reply. Kafka is not RPC — use gRPC or HTTP.
  2. A task queue with per-task retry, delay and priority and a worker count that swings widely — RabbitMQ, SQS or Celery fit more naturally.
  3. Fan-out to end clients (mobile, browser, millions of connections). Kafka is not client-facing; it sits behind a WebSocket or push layer.
  4. Small scale, one consumer, no replay needed. Postgres with an outbox table, or a Redis stream, costs far less to operate.
  5. Querying by message content, or updating or deleting one specific message. That is a database.
  6. Scheduled or delayed delivery. Kafka has none natively — you would build tiered delay topics or an external scheduler.

Share Groups (KIP-932) — the 2026 talking point

Share Groups reached production-ready status in Kafka 4.2. Interviews have started asking about this and many candidates have not caught up.

Per-record redeliveryNoYes, with a delivery count
OrderingYes (per partition)Given up — this is the trade

A senior-level answer to “can Kafka replace RabbitMQ yet?”: much closer since 4.2, but it still lacks broker-side routing and delayed delivery, and Share Groups trade ordering away to get parallelism.

A partition is the unit of four things at once

A topic is purely logical — just a name; no file on disk is named after it. The partition is the real object: one log on disk, and simultaneously the unit of

  1. parallelism
  2. ordering
  3. replication
  4. storage and retention

Being able to say “a partition is the unit of all four” already separates you from the average candidate. A single partition cannot scale past one broker, which is why partition count is your parallelism ceiling and has to be chosen when the topic is created.

An offset is a monotonically increasing integer scoped to one partition. There is no topic-wide offset. A record is uniquely identified by (topic, partition, offset).

The assignment rule inside a consumer group

Within one group, each partition is assigned to exactly one consumer. Three partitions, four consumers:

part 0012345→ c1
part 1012345→ c2
part 2012345→ c3
—0c4 · idle, no partition assigned

So the number of useful consumers in a group is at most the partition count. Separate groups read the same topic completely independently, each with its own offsets stored in the internal __consumer_offsets topic. Groups serve both shapes — queue (consumers in one group split the work) and pub/sub (several groups read the same data) — with no separate exchange concept.

Reading the output of describe

$ kafka-topics.sh --describe --topic lab01.orders
Topic: lab01.orders  Partition: 0  Leader: 2  Replicas: 2,3,1  Isr: 2,3,1
Topic: lab01.orders  Partition: 1  Leader: 3  Replicas: 3,1,2  Isr: 3,1,2
Topic: lab01.orders  Partition: 2  Leader: 1  Replicas: 1,2,3  Isr: 1,2,3
  • Leader — the only broker that serves reads and writes for that partition. Leaders spread across the three brokers is exactly how Kafka scales writes.
  • Replicas — the replica list in preference order; the first entry is the preferred leader.
  • Isr — in-sync replicas. Isr equal to Replicas means a healthy cluster; a shorter Isr means a follower has fallen behind (M3 digs into this).

Followers behave like internal consumers fetching from the leader. The one exception is KIP-392 fetch-from-follower, where a consumer reads a rack-local replica to avoid cross-AZ traffic — a cost optimisation, not a throughput one.

Key → partition, and why adding partitions breaks ordering

partition = toPositive(murmur2(keyBytes)) % numPartitions
  • With a key, the same key always lands on the same partition — this is the only mechanism Kafka gives you for ordering related events.
  • With a null key you get the sticky partitioner: records pile into one partition until the batch fills or linger.ms expires, and only then does it switch. It is not per-record round-robin — a detail people routinely get wrong.
One-way door

Changing numPartitions changes the divisor, so roughly half the keys jump to a different partition. Old events for a key stay on the old partition while new ones go to the new one, and the consumer no longer sees that key's events in order. That is why adding partitions cannot be undone, and why there is no way to add them while preserving order — only creating a new topic and migrating deliberately.

Ordering guarantees, stated precisely

Kafka guarantees the order of records within a partition, provided the producer is configured correctly. Kafka does not guarantee order in any of these cases:

SituationWhy order is lost
Across partitions, or topic-wideNo shared clock and no global sequencer
Producer retries without idempotence and max.in.flight > 1A later request can succeed before the one being retried
Null keyRecords for the same entity spread across partitions
After increasing the partition countKeys jump partitions while old data stays behind
Consumer hands records to a thread pool after poll()Kafka delivered them in order; your code broke it
Share groups (KIP-932)Ordering traded away for parallelism
A sentence worth having ready

“Kafka gives me ordering at partition scope. For ordering at business-entity scope I have to key by entity id, enable the idempotent producer, and process each partition sequentially.”

Six common traps

ClaimWhat is wrong with it
“Kafka is a FIFO queue”FIFO only within a partition
“Kafka is exactly-once by default”The default is at-least-once; EOS needs transactions and only holds Kafka-to-Kafka (M7)
“More consumers means more throughput”Capped by partition count
“Messages are deleted once consumed”Deletion follows retention and is entirely independent of consumption
“acks=all means every replica has the write”It means every replica in the ISR. If the ISR shrinks to one, acks=all protects nothing — it needs min.insync.replicas alongside it (M3)
“High consumer lag means a slow consumer”Lag is an offset difference; it can be a producer burst, or partitions not yet assigned

Lab 01 — a three-broker KRaft cluster

In labs/lab01/: a docker-compose.yml (three nodes in combined mode plus Kafka UI) and five Python scripts.

# bring the cluster up; all three nodes healthy in ~30-60s
docker compose up -d && docker compose ps
# UI: http://localhost:8080 — bootstrap: localhost:19092,localhost:29092,localhost:39092

docker exec kafka1 /opt/kafka/bin/kafka-topics.sh --bootstrap-server localhost:9092 \
  --create --topic lab01.orders --partitions 3 --replication-factor 3

pip install -r requirements.txt && cd scripts
