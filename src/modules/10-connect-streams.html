Module 9

Connect, CDC & Kafka Streams

The ecosystem around the log: Connect moves data in and out, Debezium turns a database's own log into a topic, and Streams processes topics without a separate cluster. Each one is mostly configuration — and each one has a single operational fact that decides whether it works in production.

Kafka Connect: a runtime, not a library

Connect is a separate JVM process — a worker — that runs plugins. You do not write producer or consumer code; you submit JSON config over a REST API and the worker runs it. Three nouns, which interviews mix up:

IsScales by
ConnectorThe logical job: "copy table X to topic Y". Decides how to split the work—
TaskThe unit that actually moves data. A connector produces up to tasks.max tasksNumber of tasks, bounded by what the source can be split into
WorkerThe process tasks run inAdding workers to the same group

tasks.max is a ceiling, not a request. A sink reading a 6-partition topic gets at most 6 useful tasks; a Postgres source connector reading one replication slot gets exactly one. Raising tasks.max past what the source can split into does nothing.

Distributed mode keeps its state in Kafka

Workers sharing a group.id form a cluster and balance connectors and tasks between them using the group protocol — incremental cooperative rebalancing, so adding a worker moves some tasks rather than stopping all of them. All state lives in three compacted topics:

  • config.storage.topic — connector configs. Must be one partition, because config order matters.
  • offset.storage.topic — source connector positions (an LSN, a binlog coordinate, a file offset). Sink connectors do not use it: they are ordinary consumers and commit to __consumer_offsets under group connect-<name>.
  • status.storage.topic — connector and task state.

The same move as M4 and M7: a distributed system that needs durable coordination state writes it to Kafka. A worker is stateless and replaceable; deleting or mis-retaining these topics is what loses things. They must be compacted, never delete-retention — a source offset expiring means the connector restarts from scratch.

Converters and SMTs do different jobs

  • Converter — bytes ↔ Connect's internal record. Set per worker or per connector as key.converter / value.converter: JSON, Avro, Protobuf, String. This is where Schema Registry (M8) plugs in.
  • SMT (single message transform) — a stateless per-record function: rename a field, route to a different topic, mask a column, extract a key. Optionally gated by a predicate.

SMTs are for shape, not logic. One record in, zero or one out, no state, no lookups, no joins. The moment you want any of those you want Streams or Flink, and an SMT chain that has grown to eight entries is usually a stream processor that nobody admitted to building.

Errors, and what the DLQ actually catches

errors.tolerance=none (the default) fails the task on the first bad record. all skips it — logged with errors.log.enable, and for sink connectors routed to errors.deadletterqueue.topic.name, with the failure reason in headers if errors.deadletterqueue.context.headers.enable is on.

The gap in the DLQ

The dead-letter queue covers failures in conversion and transformation — the stages the framework runs. A failure inside the connector's own write to the target, such as a constraint violation in the database, is only routed to the DLQ if the connector reports it through the errant-record reporter (KIP-610). Many do not, so a sink can fail its task on a bad row even with errors.tolerance=all configured. And the DLQ exists only for sinks; a source has nowhere to put a record it could not read.

errors.tolerance=all without anyone watching the DLQ is at-most-once with extra steps.

Delivery semantics on each side

Sinks are consumers that commit after writing, so they are at-least-once. Exactly-once into an external system is the M7 boundary again: it exists only if the connector makes the write idempotent (upsert on a key, a deterministic file name per offset range) or stores the offsets in the target in the same transaction as the data.

Sources were at-least-once until KIP-618, which added exactly-once source support: with exactly.once.source.support=enabled on the workers, each task writes its records and its source offsets in one Kafka transaction — consume-transform-produce where the "consume" side is an external system. It needs the connector to support it and the cluster to allow transactions, and downstream readers still need read_committed for it to mean anything.

CDC with Debezium

Change data capture reads the database's own replication log — the Postgres WAL via logical decoding (pgoutput), the MySQL binlog — and emits one event per row change with before and after images. It does not poll tables, so it sees every change including deletes, in commit order, with no load from queries.

A connector starts with a snapshot — a consistent read of existing rows — then switches to streaming from the log position the snapshot was taken at, so nothing falls in the gap. Incremental snapshots let you re-snapshot a table later while streaming continues, which matters because a full blocking snapshot of a large table can take hours.

Events are keyed by primary key, so changes to one row land on one partition in order. That is the ordering guarantee: per row. Not per transaction and not across tables — a transaction touching an order and its line items produces events on different partitions of different topics, and consumers that need them together have to reassemble them, using Debezium's transaction metadata if enabled.

The CDC incident: the replication slot fills the disk

Postgres keeps WAL until every replication slot has confirmed it. If the Debezium connector stops — crashed task, paused connector, deleted connector with the slot left behind — the slot stops advancing and Postgres retains WAL forever. Disk on the primary database grows until it fills, and a CDC outage becomes a production database outage.

The quieter variant: the connector is healthy but watches a low-traffic database on a busy server. WAL is server-wide, so other databases' writes accumulate behind a slot that never sees a change worth confirming. Debezium's heartbeat.interval.ms (with a heartbeat.action.query writing to a heartbeat table) forces periodic progress.

Defences: alert on slot lag (pg_replication_slots, retained WAL bytes), set max_slot_wal_keep_size so Postgres invalidates the slot rather than filling the disk — trading a re-snapshot for an outage — and drop slots as part of decommissioning a connector. MySQL fails the other way: the binlog is purged on its own schedule, and a connector down longer than binlog retention has lost its position and must re-snapshot.

The outbox, finished

M7's outbox pattern needed a relay from the outbox table to Kafka. Debezium is that relay: it reads outbox inserts from the WAL, and the outbox event router SMT routes each row to a topic by its aggregate type and keys it by aggregate id, so events for one aggregate stay ordered. No polling, no "mark as sent" update, and the order is the commit order. Rows can be deleted immediately after insert — the WAL entry is what gets captured.

Kafka Streams: a library, not a cluster

Streams is a Java library inside your application. There is no Streams cluster to run: you deploy more instances of your service and they share the work as members of one consumer group (the application.id). Kafka itself is the only infrastructure — for input, output, coordination and state durability.

AbstractionA record meansBacked by
KStreamAn event. Each one is independentA topic, read as a stream
KTableAn update. Latest value per key wins; null deletesA local state store over this instance's partitions
GlobalKTableAn update, but every instance holds every partitionA full local copy per instance

State lives locally and is made durable in Kafka

Stateful operations — aggregations, joins, windowing — use state stores, RocksDB by default, on local disk. Every write to a store is also written to a compacted changelog topic. The local disk is a cache; the changelog is the truth. Lose the instance and another one rebuilds the store by replaying the changelog.

That replay is the real recovery cost. A 50 GB store restores at whatever rate the instance can fetch and write RocksDB, and the task does nothing else until it finishes. Standby replicas (num.standby.replicas) keep warm copies on other instances so failover is a short catch-up rather than a full restore — the same trade as Kafka's own replication factor, paid in disk and network for recovery time.

Tasks, partitions and repartitioning

Streams splits a topology into tasks, one per input partition; tasks are distributed across stream threads (num.stream.threads) and instances. Parallelism is capped by partition count, exactly like a consumer group.

Any operation that changes the key before a stateful step — selectKey, map, groupBy on a new field — forces a repartition topic: Streams writes the records back to Kafka keyed by the new key so that all records for one key reach one task. It is correct and it is a full extra write and read of the data, which is why a topology with three hidden repartitions is three times the traffic it looks like. Topology.describe() shows them.

Co-partitioning — the join requirement that fails at runtime

A KStream–KTable or KStream–KStream join works by joining partition n of one input with partition n of the other, inside one task. So both inputs must have the same number of partitions and be keyed and partitioned the same way. Mismatched partition counts are rejected when the app starts; a different partitioner on one producer is not detected at all, and the join silently misses. A GlobalKTable is exempt, because every instance has all of it — which is its purpose, and its cost.

Exactly-once and time

processing.guarantee=exactly_once_v2 is M7's consume-transform-produce applied to the whole topology: output records, changelog writes and input offsets commit in one transaction per commit interval. It works because everything Streams touches is Kafka — and stops at the same boundary for anything the application does outside it.

Windowed aggregations group by event time, the timestamp in the record, not arrival time. Records arriving after their window closed are late; the grace period decides how long a window stays open for them, after which they are dropped. Longer grace means more correct results and more state held longer. Results are emitted as updates while the window is open, so a downstream consumer sees intermediate counts unless you use suppress to emit only the final value. The older API defaulted to a 24-hour grace silently; the current API makes you choose one, which is the right default.

When Flink instead

  • Streams — Kafka in, Kafka out, logic that belongs inside a service you already deploy, state that restores in acceptable time. No new cluster to operate.
  • Flink — sources and sinks beyond Kafka, very large state (incremental checkpoints to object storage rather than replaying a changelog), event-time logic across many inputs, SQL as the interface, or a platform team running many jobs centrally.

The honest decision point is operational: Streams costs you nothing new to run but ties recovery time to changelog replay; Flink recovers faster from checkpoints and handles more, at the price of a cluster and a team that understands it.

Answering "how would you get changes from Postgres into Kafka?"

CDC with Debezium on Kafka Connect, reading the WAL through a replication slot — not polling, because polling misses deletes and intermediate updates and loads the database. Snapshot first, then stream from the snapshot's position. Ordering is per primary key, not per transaction. The thing I would set up on day one is monitoring of the replication slot's retained WAL, plus max_slot_wal_keep_size, because a stopped connector otherwise fills the primary's disk. If the goal is publishing domain events rather than table changes, I would put an outbox table in front and use the outbox event router, so the topic carries a contract rather than the schema of an internal table.
