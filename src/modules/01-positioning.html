Module 0

Positioning Kafka

Before any mechanism: what Kafka actually is, what follows from that, and when the honest answer is to use something else. Most wrong answers in a Kafka interview trace back to a broken mental model at this level.

One definition, derive everything else from it

Mental model

Kafka is a distributed, replicated, append-only commit log in which the broker is only responsible for storing and serving the log, while the read position is owned by the consumer.

This is the one thing worth memorising. Every characteristic property of Kafka follows from it, so in an interview you can derive the answer on the spot instead of reciting it.

Because Kafka is a log and consumers own their offsetsIt follows that
The broker keeps no per-message stateVery high throughput; the broker does almost nothing but sequential I/O
Reading is non-destructiveMany consumer groups read the same data independently; replay is free
Data is deleted by retention policy, not by consumptionKeep 7 days, a year, or forever via compaction / tiered storage
There is no per-message ack at the brokerNo per-message retry, delay, priority or selective nack
Order only exists inside one log fileOrder is guaranteed within a partition only
Nothing is indexed by contentYou cannot ask for “messages where status=FAILED” — that is a database's job

Answering “Kafka or RabbitMQ?”

Do not compare throughput. Compare the unit of state: Kafka tracks state as a stream plus an offset, RabbitMQ tracks it per message. If the problem needs control over individual messages — its own retry, its own delay, its own priority — you are fighting Kafka's design. If the problem needs one event stream that several consumers share and can replay, the opposite holds.

When not to use Kafka

  1. Low-latency request/reply. Kafka is not RPC — use gRPC or HTTP.
  2. A task queue with per-task retry, delay and priority and a worker count that swings widely — RabbitMQ, SQS or Celery fit more naturally.
  3. Fan-out to end clients (mobile, browser, millions of connections). Kafka is not client-facing; it sits behind a WebSocket or push layer.
  4. Small scale, one consumer, no replay needed. Postgres with an outbox table, or a Redis stream, costs far less to operate.
  5. Querying by message content, or updating or deleting one specific message. That is a database.
  6. Scheduled or delayed delivery. Kafka has none natively — you would build tiered delay topics or an external scheduler.

Share Groups (KIP-932) — the 2026 talking point

Share Groups reached production-ready status in Kafka 4.2. Interviews have started asking about this and many candidates have not caught up.

Consumer groupShare group
Consumers reading one partitionExactly oneMany
Unit of progressAn offset — a single cursorPer-record state: acquired / acknowledged / released
Parallelism ceilingPartition countNot bounded by partition count
Per-record redeliveryNoYes, with a delivery count
OrderingYes (per partition)Given up — this is the trade

A senior-level answer to “can Kafka replace RabbitMQ yet?”: much closer since 4.2, but it still lacks broker-side routing and delayed delivery, and Share Groups trade ordering away to get parallelism.

Lab 00 — a log and a queue, side by side

Everything above is a claim until you watch it happen. labs/lab00-log-vs-queue/ runs one Kafka topic and one RabbitMQ queue next to each other and pushes the same five messages through both.

StepWhat to watch for
01_publish_both.pyFive messages into each side. Note the RabbitMQ queue depth.
02_consume_both.pyBoth hand you the same five. Then: RabbitMQ queue depth drops to 0 — acking deleted them — while Kafka still holds all five and only the group's committed offset moved.
03_read_again.pyA new Kafka consumer group replays all five from offset 0. RabbitMQ has nothing for anybody.

Verify it yourself rather than trusting the script's output — the end offset stays at 5 while the group's position is what changed:

docker exec lab00-kafka /opt/kafka/bin/kafka-run-class.sh kafka.tools.GetOffsetShell \
  --bootstrap-server localhost:19092 --topic lab00.events
docker exec lab00-kafka /opt/kafka/bin/kafka-consumer-groups.sh \
  --bootstrap-server localhost:19092 --describe --group reader-a
docker exec lab00-rabbitmq rabbitmqctl list_queues name messages

The lab README carries four exercises. The one that matters most is the first: set retention.ms=60000 and watch the records vanish with nobody consuming them — that is the proof that deletion is driven by retention and never by consumption.
