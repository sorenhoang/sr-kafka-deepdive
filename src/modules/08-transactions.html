Module 7

Delivery semantics & transactions

The module where "exactly-once" has to be said precisely or not at all. Kafka does provide it — within a boundary that most people who claim it have not located.

The three semantics, stated honestly

MeansYou get it byCosts
At-most-onceNever duplicated, may be lostCommit offsets before processing; acks=0/1Silent loss
At-least-onceNever lost, may be duplicatedCommit after processing; acks=all; retriesDuplicates the application must absorb
Exactly-onceNeither lost nor duplicatedTransactions, within KafkaLatency, throughput, a reader-side blocking mode, real operational complexity

At-least-once is the default and the honest baseline. Most production systems that believe they have exactly-once have at-least-once plus an idempotent sink, which is a perfectly good answer — and a different one.

Where duplicates actually come from

  1. Producer retry — the write landed, the ack was lost, the producer retried. Solved by the idempotent producer (M5), per session.
  2. Producer restart — a new PID means the broker cannot recognise the previous instance's writes. Idempotence does not help. Transactions do.
  3. Consumer reprocessing — a crash or rebalance between processing and committing replays the batch. Solved by transactions only if the output is also Kafka.

Naming which of the three a given mechanism addresses is the quickest way to show the distinction is understood rather than memorised.

How a Kafka transaction works

A transaction makes a set of writes across multiple partitions — and the consumer offset commit that accompanies them — atomic: all visible, or none.

producer.initTransactions()        // once, at startup
producer.beginTransaction()
producer.send(...)                 // to any partitions, any topics
producer.sendOffsetsToTransaction(offsets, groupMetadata)
producer.commitTransaction()       // or abortTransaction()

The pieces

  • transactional.id — a stable, application-chosen identity. It is what makes fencing possible, and it must survive restarts to mean anything.
  • Transaction coordinator — a broker, chosen by hashing the transactional.id to a partition of the internal __transaction_state topic, the way a group coordinator is chosen from __consumer_offsets.
  • Control records — commit or abort markers written into every partition the transaction touched. They are records in the log, invisible to applications, which is how a reader knows the outcome without consulting the coordinator.

Commit is two-phase

  1. The coordinator writes PREPARE_COMMIT to __transaction_state. From here the outcome is decided and will be completed even if brokers restart.
  2. It writes commit markers to every participating partition.
  3. It writes COMPLETE_COMMIT to __transaction_state.

The state lives in a replicated Kafka log, so a coordinator failure does not lose the decision — the new coordinator reads the log and finishes the job. The same observation as M4, one layer up: Kafka solves its own coordination problems by writing to Kafka.

Zombie fencing — why transactional.id must be stable

initTransactions() bumps the epoch for that transactional.id. Any older producer instance holding the previous epoch is immediately fenced: its writes are rejected with ProducerFenced.

This is the mechanism that solves the problem idempotence could not. A process partitioned from the cluster but still running — a "zombie" — cannot write once its replacement has started, so the split-brain write that would otherwise duplicate work is refused at the broker.

The configuration mistake this invites

A random or hostname-derived transactional.id silently disables fencing: the zombie and its replacement have different ids, so neither fences the other, and the mechanism you added for correctness does nothing. For consume-transform-produce the id must be bound to the input partitions an instance owns, so that whoever takes over those partitions takes over that identity.

Which is precisely why Kafka Streams' exactly_once_v2 matters: before KIP-447 it needed one producer per input partition, so a task with 100 partitions meant 100 producers. EOS v2 uses one producer per instance and derives fencing from consumer group metadata instead. exactly_once and exactly_once_beta were removed in 4.0 — exactly_once_v2 is the only value now.

The reader side: isolation level and the LSO

isolation.level on the consumer:

  • read_uncommitted (default) — every record, including those from transactions that later abort. Transactions are invisible; you see everything.
  • read_committed — only records from committed transactions. Aborted records are filtered out by the consumer, which is why they still occupy offsets.

A read_committed consumer cannot read past the Last Stable Offset: the offset of the first record belonging to an open transaction. Everything before the LSO has a known outcome; everything after might still abort.

The operational consequence people discover the hard way

An open transaction blocks every read_committed consumer on those partitions. Not slows — blocks, at the LSO, until the transaction commits, aborts, or times out. A producer that crashes mid-transaction stalls downstream consumers for up to transaction.timeout.ms (60 s by default, capped by the broker's transaction.max.timeout.ms of 15 minutes).

So a long-running transaction is not just its own latency: it is a lower bound on every downstream consumer's latency. This is the single strongest argument for keeping transactions short, and it is the thing a candidate who has only read about transactions will not mention.

Three more reader-side facts worth having: aborted records consume offsets, so a read_committed consumer legitimately sees offset gaps — the same lesson as compaction in M2, different cause. Control records also consume offsets, which is why lag can read as non-zero on a fully consumed transactional topic. And read_committed adds latency even when nothing aborts, because the LSO lags the high watermark.

Consume-transform-produce, which is what EOS is for

The only pattern transactions genuinely solve: read from Kafka, transform, write to Kafka, atomically.

while (true) {
  records = consumer.poll()
  producer.beginTransaction()
  for (r : records) producer.send(transform(r))
  producer.sendOffsetsToTransaction(offsets, consumer.groupMetadata())
  producer.commitTransaction()
}

sendOffsetsToTransaction is the load-bearing call. It writes the consumer's offsets to __consumer_offsets as part of the transaction, so the offset commit and the output records share one atomic outcome. Crash anywhere and either both happened or neither did — which is what removes the reprocessing window that M6's Q10 could not close.

Note what has quietly changed: the consumer no longer commits its own offsets. enable.auto.commit must be off, and the producer commits on the consumer's behalf.

What exactly-once does not cover

The boundary is Kafka-to-Kafka. The moment an external system is involved — a database, an HTTP API, an email — the transaction cannot include it, because that system is not a participant in Kafka's commit protocol. There is no distributed transaction across the two.

So for an external sink the honest design is at-least-once plus idempotency at the boundary: an idempotency key derived from (topic, partition, offset), a dedupe table keyed on the same, or a naturally idempotent operation such as an upsert. Saying this plainly is worth more in an interview than claiming exactly-once and being asked how the database participates.

The dual-write problem and the outbox pattern

The mirror image, on the way in: an application that writes to its database and publishes to Kafka has two systems and no shared transaction. Either order fails somewhere — publish first and the database write may fail, leaving an event for something that never happened; write first and the publish may fail, leaving state nobody downstream knows about. Retries do not fix it; they change which inconsistency you get.

Outbox: in one database transaction, write the business row and an outbox row. A separate process — a poller, or CDC with Debezium reading the write-ahead log — publishes outbox rows to Kafka and marks them sent. Now there is only one transaction in one system, and the publish is a retriable, at-least-once delivery of something already durably recorded. Consumers must be idempotent, which they should have been anyway.

Worth stating as the general principle: you cannot make two systems atomic, so arrange for only one of them to need to be. That sentence generalises well beyond Kafka and is a good thing to have ready.

What transactions cost

  • Latency — coordinator round-trips plus a marker write to every participating partition, per transaction. Small transactions amortise badly; large ones block readers for longer.
  • Reader blocking — the LSO problem above. Your transaction duration becomes downstream latency.
  • Throughput — measurably lower than plain idempotent production, and the gap widens with more participating partitions.
  • Operations — __transaction_state to monitor, hanging transactions to detect, and transactional.id assignment to get right across deploys and scale events.

The current protocol version helps with the worst of this: transaction version 2 (KIP-890) is enabled on the server by default from Kafka 4.0, controlled by the transaction.version feature flag. It bumps the producer epoch on every transaction so that a transaction can only contain its intended records and duplicates cannot leak into the next one, and it moves partition addition into a single server-side call instead of a client add plus a server verification round-trip. Producers pick it up at the start of their next transaction, without a restart.

Answering "does Kafka support exactly-once?"

Yes — for Kafka-to-Kafka pipelines, via transactions that make the output records and the input offset commit atomic, with transactional.id fencing zombie producers and read_committed consumers held at the last stable offset so they never see an uncommitted write. It does not extend to external systems, because they cannot participate in the commit; there, the correct design is at-least-once with idempotency at the boundary. And it costs real latency, throughput and reader blocking, so it is worth it when reprocessing is genuinely unacceptable and not by default.
