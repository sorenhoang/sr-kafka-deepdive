Module 12

System design with Kafka

Where every earlier module gets spent at once. A Kafka design interview is not a test of whether you know the API; it is a test of whether you make the five or six decisions that actually matter, in an order that lets each one constrain the next, and say out loud what each one costs.

A framework you can run every time

The failure mode in a design round is starting with boxes and arrows. Start with the questions whose answers decide the boxes. Run these in order — each one narrows the next.

Step 2 is the one that separates answers. The key determines ordering, parallelism, hot-partition risk and what a consumer can keep in local state. Choose it from the ordering requirement, not from whatever ID is lying around — and say what is not ordered as a result.

The duplicate question

Ask "what happens if this event is processed twice?" for every consumer you draw. If the answer is "nothing, the write is an upsert", you have at-least-once and you are done. If the answer is "the customer is charged twice", you now know where the idempotency key goes — and that is a more useful thing to say than "we use exactly-once".

What an event is for: three patterns that get confused

PayloadConsumer doesCoupling
Event notification"Order 42 changed" + IDCalls back to the source for detailsRuntime coupling: the source must be up and must scale with every consumer's lookups
Event-carried state transferThe full new state of order 42Keeps its own copy, never calls backSchema coupling only; consumers survive the source being down
Event sourcingEvery state change, as the system of recordRebuilds state by replaying eventsThe log is the database

Event-carried state transfer on a compacted topic keyed by entity is the pattern Kafka is best at: the topic is a changelog, the latest value per key is a table, and any new consumer can bootstrap the full current state by reading from the beginning (M2). It is how Kafka Streams' KTables and changelog topics work (M9).

Why Kafka is a poor event store

Event sourcing needs to load one aggregate's history to handle a command. Kafka can only read a partition sequentially from an offset — there is no "give me every event for order 42". With order 42 sharing a partition with a million other orders, rebuilding it means scanning them all, or keeping a materialised view that is itself the real store. Nor can it do optimistic concurrency ("append only if the aggregate is still at version 7"). The workable shape is: an event store (or a database with an events table) as the system of record, and Kafka as the distribution log that publishes those events — usually via outbox or CDC. Kafka as a projection feed, not as the aggregate store.

CQRS read models

The write side publishes events; each read model is a consumer that projects them into whatever shape its queries need — search index, cache, analytics table. Read models are disposable: reset the group's offset and replay to rebuild one, or build a new one alongside the old and switch over. The price is eventual consistency, and a read-your-own-writes requirement has to be handled explicitly — return the new state from the write path, or have the client wait on a version — rather than discovered in production.

Getting events in: outbox and CDC

Any service that changes its database and must announce it has the dual-write problem from M7. The answer is the same: write the event to an outbox table in the same database transaction, and let CDC (Debezium reading the write-ahead log, M9) publish it. One transaction, one system; the publish is a retriable at-least-once delivery of something already committed. Plain CDC on business tables is the cheaper variant but publishes your schema as a contract — the outbox lets you publish an event designed for consumers instead of an internal row.

Sagas: business transactions across services

There is no distributed transaction across services, so a multi-step business process is a sequence of local transactions, each with a compensating action that semantically undoes it (refund, release the reservation, cancel the shipment). Compensations are not rollbacks — the intermediate state was visible, and a compensation can itself fail and must be retried until it succeeds.

Rule of thumb: once a process needs timeouts ("cancel if payment has not arrived in 15 minutes"), it wants an orchestrator — a durable workflow engine or a state machine keyed by saga ID — because timeouts in pure choreography have nowhere to live.

Retries, DLQs, and what they do to ordering

A message that fails processing has three possible fates, and each costs something different:

  • Blocking retry — retry in place with backoff. Preserves ordering. Stalls the whole partition behind one bad message, and long backoffs risk max.poll.interval.ms (M6) — so pause the partition rather than sleeping in the poll loop.
  • Non-blocking retry topics — publish the failure to orders.retry.1m, orders.retry.10m, then a DLQ, and commit. The main partition keeps flowing. Ordering for that key is now broken: the next event for order 42 is processed before the retried one.
  • Dead-letter topic — park it with headers recording the error, source topic, partition and offset, for inspection and replay. A DLQ nobody alerts on or replays from is just a slower way to lose data.
The trap

Non-blocking retry and per-key ordering are incompatible unless you add machinery. If order matters, either retry blocking, or — when a key has a message in retry — route every later message for that key to the retry path too, which needs a store of "keys currently in retry". Also separate transient failures (timeout, 503: retry) from permanent ones (deserialization error, validation failure: straight to the DLQ). Retrying a poison message ten times only delays the DLQ.

Idempotent consumers

At-least-once is the default, so every consumer with side effects must tolerate redelivery. In order of preference:

  1. Naturally idempotent writes — upsert on a business key, SET status = 'shipped' rather than count = count + 1.
  2. Version or sequence guard — apply only if the event's version is newer than the stored one. Also defends against reordering.
  3. Processed-ID table — store the event ID (or topic-partition-offset) in the same database transaction as the effect, with a unique constraint.
  4. Downstream idempotency key — for an external API that supports one (payment providers do), derive the key from the event, never generate it at send time.

Request-reply over Kafka, and why it is usually a smell

It can be done: a reply topic, a correlation ID header, a pending-requests map waiting on a future. But the caller is now synchronous on an asynchronous system — latency includes producer batching, consumer polling and possibly a rebalance; replies must be routed back to the one instance holding the future; and timeouts leave orphaned work. If the caller needs an answer now, use RPC. Kafka earns its place when the caller does not need to wait: return 202 Accepted with an ID and let the result arrive as an event or a status query.

Multi-region

  • Stretch cluster across nearby zones/regions — synchronous replication, RPO zero, but every acks=all write pays the inter-region round trip and the controller quorum (M4) needs a majority to survive a region loss, which wants three locations.
  • Active-passive with MirrorMaker 2 (M10) — asynchronous, so RPO is the replication lag, and offsets differ between clusters; MM2's checkpointing translates consumer group offsets for failover. Rehearse failover; an untested DR plan is a hope.
  • Active-active — each region writes locally and mirrors the other's topics under a prefix. Fine for append-only, commutative data (clickstream). For data with a single owner per entity, pin each key's writes to a home region, or accept conflict resolution you have designed rather than discovered.

Worked designs

1 · Order processing

  • Key: orderId. Ordering matters per order (created → paid → shipped); nothing needs ordering across orders. Not customerId: a large B2B customer becomes a hot partition.
  • Topics: orders.events (event-carried state, via outbox from the order service), payments.events, shipments.events. Partitions sized for peak (Black Friday, not Tuesday) with headroom — say 48 or 64 — because adding partitions later moves keys (M1).
  • Semantics: at-least-once everywhere, idempotent consumers keyed on orderId + version; payment calls carry an idempotency key derived from the event.
  • Saga: orchestrated — reserve stock, take payment, ship — with compensations and a payment timeout.
  • Failure modes: poison event → DLQ with alerting; payment provider outage → blocking retry with paused partitions rather than retry topics, since order state must not be applied out of sequence.

2 · Clickstream / activity analytics

  • Requirements flip: very high volume, small events, duplicates tolerable (aggregates), a little loss arguably tolerable, latency in seconds.
  • Key: sessionId or userId if sessionisation needs per-user order; otherwise null key and the sticky partitioner (M5) for even spread. Beware bots: one user ID at a thousand events per second is a hot partition.
  • Producer: high linger.ms, compression (zstd or lz4), large batches — this is a throughput system.
  • Downstream: Kafka Streams or Flink for windowed aggregates; a sink connector to the warehouse or object storage. Retention short on the raw topic; tiered storage (M2) if replay windows must be long.
  • Semantics: at-least-once; dedupe on an event ID within a window if counts must be exact.

3 · Payment ledger

  • The decision that matters: the ledger's system of record is a database with double-entry constraints, not Kafka. Kafka distributes ledger entries via outbox; it does not hold the balance.
  • Key: accountId, so entries for one account apply in order and a balance projection can live in local state.
  • Durability: RF=3, min.insync.replicas=2, acks=all, unclean leader election off (M3). Retention long or infinite; this topic is audit evidence.
  • Semantics: transactions for Kafka-to-Kafka projections (balances, fraud features); every external effect behind an idempotency key. Schema compatibility FULL_TRANSITIVE (M8), because old entries are replayed forever.
  • Access: prefixed ACLs so only the ledger service principal can write (M11).

When the right design has no Kafka in it

Back to M0, now with reasons. Do not reach for Kafka for: a work queue where each task is independent and you want per-message ack, retry and delay (a queue — or Share Groups — fit better); synchronous request-reply; a few hundred events a day between two services (a table and a poller); per-entity lookups of history (a database); or a team with no one to operate it and no managed offering. Saying "I would not use Kafka here, because…" is a strong answer when it is true.

Answering "design an order processing system on Kafka"

Start from requirements — peak throughput, latency, and what a duplicate or a loss costs. Key by orderId, because ordering is needed per order and nowhere else, and say that cross-order ordering is deliberately given up. Size partitions for peak with headroom, since changing the count remaps keys. The order service publishes event-carried state via an outbox and CDC, so there is no dual write. Consumers are at-least-once and idempotent on order ID and version, external calls carry idempotency keys, and the multi-step flow is an orchestrated saga with compensations and timeouts. Poison messages go to an alerted DLQ; transient failures retry blocking so per-order state is never applied out of order. Schemas are registered with a compatibility mode, topics are RF=3 with min.insync.replicas=2, and lag per group is the first alert. Then name what the design does not do — no global ordering, eventual consistency in read models — because a design without its trade-offs stated is not finished.
