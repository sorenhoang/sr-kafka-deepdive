Module 5

Producer internals

What actually happens between send() returning and the record reaching a log — and why the idempotent producer is the first thing in this course that is genuinely subtle.

The path of one record

send() does not send anything. It is asynchronous, returns a future, and hands the record to a buffer that another thread drains.

send(record)
  → serializer            key and value to bytes
  → partitioner           pick a partition
  → RecordAccumulator     append to that partition's current batch, in memory
  → [returns]            the future is not yet complete
      ⋮
  Sender thread           drains ready batches, groups them per broker,
                          sends one request per broker, handles the response,
                          completes the futures and fires the callbacks

Two consequences fall out immediately. A callback runs on the Sender thread, so blocking in it stalls all sending for that producer. And a producer that has not been flushed or closed can lose everything still sitting in the accumulator — which is why close() matters and why a container killed with SIGKILL mid-batch loses records that send() appeared to accept.

The accumulator is a memory pool, and it can block you

buffer.memory (default 32 MiB) is the total memory for all unsent batches. When it is exhausted — the broker is slow, a partition's leader is unavailable, the application produces faster than the network drains — send() stops being asynchronous and blocks for up to max.block.ms (default 60 s), then throws.

The symptom nobody attributes correctly

"Our service got slow and we don't know why" is frequently a producer blocked on buffer.memory, propagating broker backpressure into application latency through a call everyone assumes is non-blocking. The giveaway is that request latency rises in a service that is doing no more work than usual. max.block.ms also covers waiting for topic metadata, so a producer writing to a topic that does not exist blocks the same way.

Batching: the two settings and the thing people get wrong

  • batch.size (16 KiB) — maximum bytes per partition in one batch. Not a global size, and not a count.
  • linger.ms (0 in the Java client) — how long to wait for more records before sending a partially full batch.

A batch goes when it is full or linger expires. The part that surprises people: linger.ms=0 still batches. While a request is in flight to a broker, records for that broker keep accumulating, and the next request takes everything that arrived meanwhile. Under load you get large batches with zero configured linger — batching is driven by the in-flight window, not only by the timer. Raising linger.ms adds a latency floor to get bigger batches at low load, where there is nothing in flight to accumulate behind.

This matters beyond throughput: compression is applied per batch, so bigger batches compress better. linger.ms is also a storage-cost setting, and the M2 point that the broker stores exactly the bytes the producer framed is what makes that true end to end.

Leave the topic at compression.type=producer so the broker stores the batch untouched. Setting a different codec on the topic forces decompress and recompress on every batch, which costs broker CPU and loses zero-copy — the M2 point, arriving from the producer side.

The partitioner changed, and the old answer is now wrong

With a key, the partition is murmur2(key) % partitions — unchanged since M1. With a null key:

  • Before 2.4: round-robin per record, which spread a small number of records across every partition and produced many tiny batches.
  • 2.4 (KIP-480): the sticky partitioner — fill one partition's batch, then switch. Far fewer, far larger batches.
  • 3.3 (KIP-794): the strictly uniform sticky partitioner. The 2.4 version allocated batches equally but, because slow brokers drain slower, could send more bytes to the brokers least able to take them. The new default assigns by how much each partition has actually accepted, and with partitioner.adaptive.partitioning.enable it steers away from slow brokers. DefaultPartitioner is deprecated; leave partitioner.class unset to get the current behaviour.

Knowing all three, and that the answer changed twice, is the kind of detail that marks someone who has followed Kafka rather than learned it once.

Tuning retries is the classic mistake: it has not been the limit since delivery.timeout.ms was introduced. If you want a producer to give up after 10 seconds, that is the setting to change.

And the M1 point, now with its mechanism: a retry reorders only when max.in.flight > 1, because request 2 can succeed while request 1 is being retried. max.in.flight=1 is safe and slow. The real fix is idempotence.

The idempotent producer

enable.idempotence=true — the default in the Java client since 3.0 (KIP-679), along with acks=all. The mechanism:

  • The producer requests a producer id (PID) and an epoch from a broker.
  • Every batch carries the PID, the epoch, and a sequence number per partition, incrementing by batch.
  • The broker keeps the last sequence number per (PID, partition). A batch whose sequence it has already seen is acknowledged and discarded — the duplicate never reaches the log. A batch arriving ahead of the expected sequence is rejected with OutOfOrderSequenceException.

So the broker both deduplicates and enforces order, which is why idempotence makes max.in.flight up to 5 safe instead of forcing it to 1: out-of-order arrivals are rejected and retried in order rather than being written in the wrong order.

Those are the producerId and sequence fields visible in kafka-dump-log.sh since lab 01 — this is what they were for.

What idempotence does not do

It does not survive a producer restart. A new producer instance gets a new PID, so the broker has no way to recognise records the previous instance already wrote. Retry after a crash duplicates. Idempotence is per producer session.

It is not cross-partition or cross-topic atomicity. Two records to two partitions can still end with one written and one not. That is transactions, and it is M7.

It is not end-to-end exactly-once. It removes duplicates introduced by producer retries. An application that calls send() twice sends two records, and the broker is right to store both.

The honest one-liner: idempotence makes a retry safe, not a system exactly-once.

Two more things that bite

Record size has two limits and they are set in different places. max.request.size (producer, 1 MiB) and message.max.bytes (broker/topic). Raise one without the other and the failure appears at whichever is lower — and the broker-side rejection arrives as a confusing error after the record has crossed the network. Consumers have fetch.max.bytes and max.partition.fetch.bytes to match; a message too large for a consumer to fetch is a stall, not an error.

Errors come in two kinds. Retriable — NotLeaderOrFollower, NotEnoughReplicas, timeouts — the client handles them within delivery.timeout.ms. Non-retriable — RecordTooLarge, serialization failures, authorization — fail immediately and reach your callback. Code that treats every callback error the same either retries what can never succeed or drops what would have.
