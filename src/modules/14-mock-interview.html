The senior rubric, made concrete

Same question for all three: "Can a Kafka write with acks=all be lost?"

GradeSounds likeWhat gives it away
Missing the point"No — acks=all means every replica has it, so it's durable."Wrong model of the mechanism. acks=all means every in-sync replica, and the ISR can be one broker.
Correct but shallow"Yes, if the ISR shrinks to the leader alone. Set min.insync.replicas=2."Right answer, recited. No failure sequence, no cost, nothing about what min.insync.replicas does to availability.
Senior levelWalks the sequence: followers fall out of the ISR, leader accepts with ISR=1, leader dies, a lagging replica is elected — only with unclean election enabled, which is off by default. Then min.insync.replicas=2 with RF=3: writes fail with NotEnoughReplicas instead of being lost, so you have traded availability for durability on purpose. Then names what is still not covered: the page cache is not fsynced, so a correlated power loss across all ISR members can still lose acknowledged data.Mechanism, failure sequence, the knob, what the knob costs, and the edge it still does not cover — unprompted.

The pattern generalises: a senior answer is the correct answer plus the trade-off it makes plus the boundary where it stops holding. Most "correct but shallow" grades are missing one of those two, not the core fact.

Incident scenarios

Posed the way an interviewer poses them: a symptom and nothing else. The grade is mostly in the questions you ask before you propose anything.

1 · "Consumer lag on one partition keeps climbing; the others are fine."

  • Ask: is it always the same partition? Is the topic keyed, and by what? Is the consumer for that partition slow, or is it receiving more?
  • Likely causes: a hot key routing a disproportionate share to one partition; one poison or very slow record being retried; the consumer owning it co-located with something noisy.
  • Fix: per-partition produce rate tells you which. Hot key → re-key with a salt, accepting the loss of per-key ordering, or isolate the key. Adding partitions does not help — the hot key still hashes to one. Draws on M1, M6, M10.

2 · "Every few minutes the whole consumer group rebalances, and lag never recovers."

  • Ask: what do the logs say leaves the group — session timeout or poll interval? How long does processing one poll() batch take? Did a deploy or a downstream dependency change?
  • Likely causes: processing per batch exceeds max.poll.interval.ms, the member is evicted, its partitions are reprocessed, load rises, the next member is evicted — a self-sustaining loop.
  • Fix: lower max.poll.records first; raise the interval only knowingly, since it trades a loud failure for a slow one. Cooperative or KIP-848 rebalancing limits the blast radius; static membership stops restarts from triggering it. Draws on M6.

3 · "Producers see latency spikes of several seconds, but brokers look healthy."

  • Ask: is the time in send() itself or in the callback? What are buffer.memory and max.block.ms? Any under-replicated partitions or ISR churn at the same moments?
  • Likely causes: buffer exhaustion making send() block; acks=all waiting on a slow follower that has not yet dropped out of the ISR; request queueing on one overloaded broker.
  • Fix: measure blocked time in send() separately; find the slow follower via replica fetch lag; rebalance leadership if one broker leads too much. Draws on M3, M5, M10.

4 · "After a deploy, the order service is processing some orders twice."

  • Ask: twice within Kafka, or twice into the database? Auto-commit or manual? Are transactions in use, and how is transactional.id derived? Did the deploy coincide with a rebalance?
  • Likely causes: commit-after-process reprocessing on rebalance — at-least-once doing exactly what it promises; a hostname-derived transactional.id so the old and new pod never fence each other; a non-idempotent database sink.
  • Fix: the duplicate is expected; the bug is a sink that cannot absorb it. Idempotency key from (topic, partition, offset) or a business key with a unique constraint. Draws on M6, M7.

5 · "A new producer version shipped and two downstream consumers started failing to deserialize."

  • Ask: is there a schema registry, and what compatibility mode is the subject in? Was the field removed, renamed, or had its type changed? Which side was deployed first?
  • Likely causes: compatibility set to NONE, or a change the mode permits but deploy order did not respect; a consumer using a generated class that cannot read the new shape.
  • Fix: roll the producer back — records already written stay on the log, so consumers must be fixed to read them regardless. Enforce compatibility in CI, not at runtime. Draws on M8.

Senior-answer anti-patterns

Things that cap an answer at "correct but shallow"
  • Claiming exactly-once. Without saying "Kafka-to-Kafka", the next question is how the database participates, and there is no good answer to it.
  • "Just add partitions." It reshuffles keys and breaks per-key ordering, does nothing for a hot key, adds controller and file-handle cost, and cannot be undone.
  • Ignoring ordering. Any design that parallelises, retries or re-keys must say what happens to order — and whether anyone actually needed it.
  • Not naming the trade-off. Every knob in this course buys something with something: durability with availability, throughput with latency, ordering with parallelism. An answer that names only the benefit reads as recited.
  • Defaults from the wrong client. Java client defaults are what interviewers quote; librdkafka's differ.
  • Solving before asking. In an incident scenario, a fix proposed before scale, keys, ordering needs and the actual symptom are established is a guess.
What "senior level" means across this whole course

Not knowing more settings. Knowing which mechanism a setting acts on, what it costs, and where it stops working — and saying all three without being asked. The rapid-fire round checks the facts; the scenarios and the follow-ups check whether the facts are connected.
