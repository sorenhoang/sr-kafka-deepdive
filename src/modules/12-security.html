Module 11

Security & multi-tenancy

The module where a cluster stops trusting its network. Most Kafka security incidents are not breaches — they are outages caused by turning security on: clients that can no longer connect, a CPU graph that doubles, or an authorizer that denies the brokers themselves.

Listeners: one port, one protocol, one name

A broker accepts connections on one or more listeners. Each has a name, a host and port, and a security protocol, mapped by listener.security.protocol.map:

ProtocolEncryptedAuthenticated byUse
PLAINTEXTNoNobody — principal is ANONYMOUSLocal development only
SSLTLSClient certificate, if ssl.client.auth=required (mTLS)Service-to-service with a PKI
SASL_PLAINTEXTNoSASL mechanismAlmost never — credentials or tokens cross the wire in the clear
SASL_SSLTLSSASL mechanismThe usual production choice
 
listeners=INTERNAL://:9092,EXTERNAL://:9093,CONTROLLER://:9094
advertised.listeners=INTERNAL://kafka-1.svc:9092,EXTERNAL://kafka-1.example.com:9093
listener.security.protocol.map=INTERNAL:SASL_SSL,EXTERNAL:SASL_SSL,CONTROLLER:SSL
inter.broker.listener.name=INTERNAL
controller.listener.names=CONTROLLER   // KRaft: the quorum has its own listener

Listener names are arbitrary labels, which is the point: the same protocol can run on two listeners with different settings — a private network with mTLS and a public one with OAuth — and every ssl.* or sasl.* property can be scoped per listener with the listener.name.<name>. prefix.

The connection bug everyone hits once

A client connects to the bootstrap address only to fetch metadata. From then on it connects to whatever each broker advertises for the listener it came in on. If the advertised address is a container name, a pod IP or an internal DNS name, a client outside that network bootstraps successfully, then times out on every produce and fetch. The symptom looks like a network or TLS problem; the cause is one line of broker config. It is also why a TLS hostname-verification error can appear only after bootstrap: the certificate must match the advertised name, not the one you typed.

Encryption: TLS, and what it costs

TLS gives confidentiality and integrity in transit and, with ssl.client.auth=required, authenticates the client by certificate (mTLS). Hostname verification (ssl.endpoint.identification.algorithm=https) is on by default on clients; turning it off to make a certificate error go away removes the protection against a man in the middle while keeping the cost.

The cost is the interesting part, because it connects back to M2. A plaintext fetch is served with sendfile: bytes go from page cache to socket without entering the JVM. TLS breaks zero-copy. The broker must read the bytes into user space to encrypt them, so every fetch now costs a copy, heap or direct buffer pressure, and encryption CPU. Produce-side cost is smaller; consume-side cost scales with fan-out, since each consumer group re-reads and re-encrypts the same data.

  • Expect broker CPU to rise noticeably on fetch-heavy clusters, and plan the capacity before the rollout, not after.
  • Modern JDKs with AES-NI and TLS 1.3 make the cipher itself cheap; the lost zero-copy and extra copying are what remain.
  • Compression helps twice: fewer bytes to encrypt, and batches stay compressed end to end.

Authentication: who are you?

Authentication produces a principal, written User:alice. Everything downstream — ACLs, quotas, audit — keys on it. With mTLS the principal comes from the certificate's distinguished name, reshaped by ssl.principal.mapping.rules; with SASL it is the authenticated username or token subject.

MechanismCredentialStrengthWeakness
PLAINUsername + password, sent as isSimple; fine inside TLSDefault implementation reads passwords from the broker's JAAS file — a restart to add a user. Production use needs a custom callback handler
SCRAM-SHA-256/512Salted challenge-responsePassword never crosses the wire; credentials stored in cluster metadata, managed with kafka-configs, no restartStill passwords: rotation and distribution are yours
GSSAPIKerberos ticketsFits an existing AD/Kerberos estate; no static secrets in clientsKDC is now a dependency of every connection; ticket renewal and clock skew failures
OAUTHBEARERBearer token (JWT) from an identity providerShort-lived tokens, central identity, fits cloud IAMThe built-in unsecured JWT handler is for development only; production needs OIDC validation configured against your IdP

In KRaft the inter-broker SCRAM user has a chicken-and-egg problem — brokers need the credential to talk to each other before metadata is available — which is solved by adding SCRAM credentials at kafka-storage format time.

One detail that matters for rotation: authentication happens at connection time. A connection that authenticated with a password you have since changed, or a token that has since expired, stays authenticated unless connections.max.reauth.ms is set — it is 0, disabled, by default. Revoking a credential without it does not disconnect anyone.

Authorization: what may you do?

Enabled by setting an authorizer. In KRaft that is org.apache.kafka.metadata.authorizer.StandardAuthorizer, which stores ACLs in the metadata log — the same log from M4 — so ACL changes replicate to every broker the way topic changes do.

An ACL is: principal is allowed / denied operation on resource from host. Resource types are Topic, Group, Cluster, TransactionalId, DelegationToken and User; patterns are LITERAL (including the * wildcard) or PREFIXED.

  • Deny beats allow. Any matching deny wins over any number of allows, regardless of how specific either is.
  • No match means deny — unless allow.everyone.if.no.acl.found=true, which turns a resource with no ACLs into an open one. It exists for migration; left on, every new topic is public until someone remembers to lock it.
  • super.users bypass ACLs entirely. The broker and controller principals must be in it, or must have explicit ClusterAction grants — otherwise turning on the authorizer denies the cluster to itself.
  • Read, Write, Delete and Alter imply Describe; AlterConfigs implies DescribeConfigs.

What each client actually needs

ClientACLs
ProducerWrite on the topic. Older brokers also wanted IdempotentWrite on Cluster for an idempotent producer; current ones accept topic Write as sufficient — worth knowing when an upgrade suddenly needs one fewer grant, or a downgrade one more
Consumer in a groupRead on the topic and Read on the group. Missing the second gives GroupAuthorizationException while the topic grant looks correct
Transactional producerWrite on the TransactionalId, Write on output topics, and Read on the consumer group if it calls sendOffsetsToTransaction

kafka-acls.sh --bootstrap-server ... --add \
  --allow-principal User:orders-svc \
  --operation Write --topic orders. --resource-pattern-type prefixed
kafka-acls.sh ... --add --allow-principal User:billing \
  --operation Read --topic orders. --resource-pattern-type prefixed \
  --group billing- --resource-pattern-type prefixed   // topic and group both

Prefixed ACLs are what make ACLs manageable at all: grant per team or per tenant prefix once, rather than per topic forever. They only work if topic naming is enforced — which is a governance decision, not a Kafka feature.

Multi-tenancy: sharing a cluster without sharing the blast radius

Kafka has no tenant object. Multi-tenancy is assembled from three things: naming (a tenant prefix on topics, groups and transactional ids), ACLs (prefixed grants per tenant principal), and quotas.

QuotaLimits
producer_byte_rateBytes/s produced, per broker
consumer_byte_rateBytes/s fetched, per broker
request_percentageShare of network and I/O thread time — catches the client that sends tiny requests very fast, which byte rates never see
controller_mutation_rateRate of partition creations and deletions — the tenant who scripts topic creation in a loop

Quotas are enforced by throttling, not rejection: the broker computes how long the client must wait to fall back under its rate, delays the response and reports throttle_time_ms. To the tenant it looks like latency, which is why throttle-time metrics have to be visible to them.

client.id is not an identity

Quotas can be set on user, client-id or the pair, most specific match wins. But client.id is a string the client chooses. A quota on client-id alone is a politeness convention: any tenant can dodge it by changing a config value. Enforceable isolation needs an authenticated principal, so quotas belong on user, with client-id as a sub-division within it.

What quotas do not isolate: disk and page cache. One tenant's lagging consumer reads cold segments from disk and evicts everyone's hot data from page cache (M2), and a tenant with long retention fills shared disks. Shared clusters work when tenants are cooperative and observable; for regulatory isolation, very different SLOs, or a tenant whose traffic dwarfs the rest, a separate cluster is the honest answer. Clusters are cheap compared to the meeting about who broke the shared one.

What Kafka does not encrypt

Kafka has no encryption at rest. Segments on disk are plaintext; anyone with the volume has the data. The options sit outside Kafka: disk or volume encryption (protects against a stolen disk, not a compromised broker), object-store encryption for tiered storage, or end-to-end encryption in the client, where brokers only ever see ciphertext. The last is the strongest and the most invasive: key management becomes yours, and compaction compares key bytes, so a compacted topic needs keys encrypted deterministically or left in the clear — otherwise every record looks unique and compaction never removes anything.

Rotation, which is where the outages are

  • Certificates: keystores and truststores can be updated on a running broker through dynamic per-listener config, so rotation does not require a rolling restart. Roll the truststore to trust both old and new CA first, then rotate leaf certificates, then remove the old CA — in that order, or something stops trusting something.
  • SCRAM passwords: one credential per user per mechanism, so changing it is a cut-over. Rotate by introducing a new principal, moving clients, then deleting the old one — and set connections.max.reauth.ms so the old one actually stops working.
  • OAuth: short token lifetimes do the rotation for you, provided re-authentication is on; otherwise a token that expired an hour ago keeps a connection alive indefinitely.
Answering "how would you secure a Kafka cluster?"

Separate listeners for inter-broker, controller and client traffic, all over TLS, with advertised addresses that are actually reachable by the clients that use them. Authentication via mTLS or SASL — SCRAM where there is no identity provider, OAUTHBEARER where there is one — so every connection has a real principal. The KRaft StandardAuthorizer with allow.everyone.if.no.acl.found=false, prefixed ACLs per team on an enforced naming scheme, and broker principals in super.users. Quotas on authenticated users, not client ids. Re-authentication enabled so revocation means something. And an explicit statement that Kafka does not encrypt at rest, so that is disk encryption or end-to-end encryption by design — with the TLS CPU cost, from losing zero-copy, planned for before the rollout.
