Module 4

KRaft & the metadata plane

Everything so far has been the data plane. This is the other half: how the cluster knows who leads which partition, and why Kafka spent five years replacing the system that used to answer that.

What ZooKeeper was actually doing

Before 4.0, a Kafka cluster was two distributed systems. ZooKeeper held the metadata: which brokers are alive, which topics exist, how partitions are assigned, who leads each one, the ISR, topic configs and ACLs. One broker was elected controller and was the only component allowed to write that metadata; everyone else read it.

The data plane never touched ZooKeeper — producing and consuming went broker to broker. ZooKeeper was the control plane only, which is why clusters could be enormous and still keep a modest ZooKeeper ensemble.

Why it had to go

  • Two systems to operate. Two sets of config, two security models, two upgrade paths, two sets of failure modes, two on-call runbooks — for one product. Most Kafka outages that were not disk-related were ZooKeeper-related.
  • Controller failover was O(partitions). A new controller had to load the entire cluster state out of ZooKeeper before it could act. On a large cluster that was minutes of no leader elections, no topic changes, and no recovery from any other failure happening at the same time. Failover time grew with the thing you most wanted to grow.
  • Metadata propagation was RPC push. The controller pushed updates to brokers individually. A broker that missed one had no way to notice: there was no version, no offset, nothing to compare. Divergence was possible and hard to detect.
  • A hard ceiling on partitions. Roughly 200k per cluster in practice, set by that load-everything failover, not by disk or throughput.

KRaft: metadata as a Kafka log

The insight behind KIP-500 is almost circular, and it is the thing to lead with in an interview: Kafka is a replicated log, and metadata is a thing that needs replicating — so store the metadata in a Kafka log.

A set of controller nodes forms a Raft quorum over a single-partition internal topic, __cluster_metadata. The Raft leader is the active controller; the others are followers that already hold the whole log.

Three consequences are worth being able to state in your own words:

  1. Brokers are observers of the metadata log. They fetch records and apply them in order, exactly as a consumer does. Metadata becomes eventually consistent with a measurable lag rather than a push that might have been missed — and "this broker is 4,000 metadata records behind" is now a sentence you can say, and alert on.
  2. Failover is fast because nothing is loaded. Standby controllers have been applying the same log all along, so promotion is a Raft election, not a state transfer. Milliseconds instead of minutes, and it no longer scales with partition count.
  3. The metadata log is compacted, with snapshots. It would otherwise grow forever. Periodic snapshots capture the full state so the log can be truncated, and a new controller or a far-behind broker loads the latest snapshot and replays only what came after.

Deployment shapes and quorum sizing

Every node declares process.roles:

  • Isolated — controller or broker, never both. Dedicated controllers are small, cheap, and insulated from data-plane load; a broker under GC pressure cannot destabilise the control plane. This is the production shape.
  • Combined — broker,controller on one node. Fewer machines, fine for development and small clusters, and what every lab in this repo uses. The risk is exactly the one it saves money on: data-plane load can starve the controller.

Quorum sizing follows Raft, not replication factor: a quorum of N tolerates (N-1)/2 failures, so 3 controllers tolerate one loss and 5 tolerate two. Even numbers buy nothing — 4 tolerates the same single failure as 3, while adding another node that must agree. Three is the normal answer; five is for clusters where controller loss is genuinely costly.

Controllers are sized by metadata volume, meaning partition count, not by throughput. This surprises people: a cluster pushing gigabytes a second can run a perfectly happy three-node controller quorum on small instances.

The operational consequence people miss: because 4.0 removed ZooKeeper support outright, a cluster still on ZooKeeper cannot upgrade directly to 4.x. It has to go to a 3.x version first, migrate to KRaft there, and only then upgrade. That is a real migration-planning fact rather than trivia, and it is the kind of detail that separates "I read the release notes" from "I have had to plan this".

Answering "why did Kafka drop ZooKeeper?"

The weak answer is "to simplify operations" — true, and it sounds like a slide. The strong answer names the mechanism: controller failover required loading the entire cluster state out of ZooKeeper, so recovery time scaled with partition count and capped cluster size. Putting metadata in a Raft-replicated Kafka log means standby controllers already hold the state, so failover becomes an election rather than a state transfer — and brokers consume metadata as a log with an offset, which makes "behind" a measurable quantity instead of an invisible one. Operational simplicity is a consequence, not the reason.
