Model answers — module 4

Written rather than attempted. Flagged for a cold retry in M13.

Q1-Q3 · Junior tier, condensed

ZooKeeper held the control plane: broker liveness, the topic list, partition assignments, leadership, the ISR, configs and ACLs. One broker was elected controller and was the only writer. It never touched the data plane — produce and consume went broker to broker — which is why big clusters ran on small ensembles.

In KRaft, metadata lives in __cluster_metadata, a single-partition internal topic replicated by Raft across the controllers. The Raft leader is the active controller; other controllers are followers with the same log; brokers are observers that fetch it like consumers.

process.roles picks the shape. Isolated means a node is either controller or broker — the production shape, because controllers stay insulated from data-plane load. Combined puts both on one node: fewer machines, fine for development. Quorum sizing follows Raft, so N voters tolerate (N-1)/2 failures: 3 tolerates one, 5 tolerates two, and even numbers buy nothing.

Q4-Q6 · Mid tier, condensed

Brokers fetch metadata rather than being pushed to. Under the old RPC push, a broker that missed an update had no version or offset to compare against, so divergence was possible and undetectable. With a log, every broker has an offset and lag is a number — MetadataLag is graphable and alertable.

Failover is fast because standby controllers have been applying the same log all along and hold the state in memory. Promotion is a Raft election, not a state transfer. Under ZooKeeper the new controller loaded everything from ZooKeeper first, making failover O(partitions) — minutes on a large cluster, which is also what set the practical ~200k partition ceiling.

Snapshots stop the metadata log growing forever and startup getting slower every month. A snapshot captures full state at an offset so earlier segments can go; a new controller or a far-behind broker loads the newest snapshot and replays only what follows. Same problem compaction solves for user topics, solved for the control plane.

Q7 · Why Kafka dropped ZooKeeper, at the mechanism level

"Operational simplicity" is the consequence. The reason is three specific mechanisms.

Failover scaled with partition count. A newly elected controller had to load the entire cluster state out of ZooKeeper before it could act. On a large cluster that was minutes during which no leader could be elected, no topic changed, and nothing could recover from any other failure happening at the same time. Recovery time grew with exactly the dimension you most want to grow.

That set the cluster ceiling. The practical limit of roughly 200k partitions per cluster came from failover time, not from disk, memory or throughput — an architectural ceiling with no tuning knob behind it.

Propagation was an unverifiable push. The controller sent metadata updates by RPC with no version and no offset. A broker that missed one could not detect it, so divergence was silent, and "is this broker's view current?" had no answer.

What KRaft changes. Metadata goes in a Raft-replicated Kafka log, so standby controllers already hold the state and promotion is an election rather than a state transfer — failover stops scaling with partitions, and the ceiling goes with it. Brokers consume that log with an offset, which turns "behind" from an invisible condition into a measurable one. Having one system to operate, secure and upgrade instead of two is a real benefit, but it is the payoff, not the rationale — and leading with it is how you sound like you read the announcement rather than the design.

Q8 · Planning a 3.4-on-ZooKeeper cluster onto 4.x

The constraint that shapes the whole plan: 4.0 removed ZooKeeper support outright, so there is no direct upgrade. The cluster must reach a 3.x release that supports migration, complete the KRaft migration there, verify it, and only then upgrade to 4.x.

Sequence, and why in this order:

  1. Upgrade 3.4 → a late 3.x, still on ZooKeeper. A routine rolling upgrade. Doing it first means the migration starts from a supported, current base.
  2. Provision the controller quorum — three dedicated nodes, isolated mode, sized by partition count rather than throughput.
  3. Start the controllers in migration mode and let them copy metadata out of ZooKeeper, with the cluster still serving traffic.
  4. Roll brokers into KRaft mode one at a time, verifying metadata lag after each.
  5. Dwell in dual-write. This is the window in which rollback is still possible, and the only reason to leave it is confidence. Finalising is irreversible.
  6. Finalise, then — separately, later — upgrade to 4.x.

Verification at each gate: kafka-metadata-quorum.sh --describe --status and --replication, MetadataLag across every broker, ActiveControllerCount summing to exactly 1, and under-replicated partitions back at zero before the next step.

The judgment the question is really testing: the risk is not the migration mechanics, which are well documented. It is combining a version upgrade with a metadata-plane migration so that when something degrades, nobody can attribute it to either, and the rollback decision has to be made under that ambiguity. Two changes, two windows, two rollback plans. Saying that is worth more than reciting the steps.

Q9 · ActiveControllerCount is 2 across the cluster

What it means. Exactly one node should report 1 and all others 0, so a cluster-wide sum of 2 means two nodes each believe they are the active controller — split brain in the control plane.

Why it is probably not what it looks like. Raft makes genuine dual leadership nearly impossible: becoming leader requires a majority of the quorum, and two leaders in the same epoch cannot both have one. So the realistic explanations are a partial network partition in which a superseded leader has not yet learned it lost, a metrics artifact from summing across a scrape window that contained an election, or a node excluded from the quorum still publishing its stale belief.

How bad. Metadata writes go through Raft, so a stale leader cannot commit anything without a majority. Divergent metadata is therefore unlikely; the real exposure is operator confusion and delayed metadata operations, not corruption. That distinction matters because the instinct — restart something immediately — is usually worse than spending two minutes establishing the facts.

How to diagnose. Ask the quorum, not the nodes: kafka-metadata-quorum.sh --describe --status from several nodes, using --bootstrap-controller so brokers being unhealthy does not block you. The quorum's own view of leader and epoch is authoritative; the per-node metric is only that node's belief about itself. Then check network reachability between controllers, since a partial partition is the explanation that actually needs fixing.

The calibration to state. A brief 2 during an election is noise. A sustained 2 is a partition to find — and the finding will be in the network, not in Kafka.

Q10 · Does KRaft change the durability story from M3?

For user data, no. Partition replication, the ISR, acks and min.insync.replicas are untouched. KRaft is the control plane; every durability guarantee from M3 holds unchanged.

What changes is the failure behaviour around it, and the answer lives in separating two things that sound alike:

  • The data plane keeps running. Losing the controller quorum does not lose data and does not stop produce or consume on partitions whose leaders are alive. Brokers act on the metadata they already hold.
  • Recovery freezes. No leader elections, no ISR changes recorded, no topic creation, no broker joining. So a partition leader failing while the quorum is down leaves that partition leaderless until the quorum returns. The cluster keeps doing what it was already doing and cannot respond to anything new.

Why faster failover matters here specifically. Under ZooKeeper, a controller failover window of minutes was a window in which no partition could recover from a broker failure — so an unlucky coincidence became a compound outage. KRaft shrinking that window to an election does not change any guarantee; it shrinks the period in which two independent failures can combine into something worse than either.

The two wrong answers are symmetrical: "KRaft doesn't affect durability, so controller loss is harmless" ignores the frozen recovery; "losing the controllers is catastrophic" ignores that the data plane is unaffected and nothing is lost. Being able to hold both halves at once is the answer.
