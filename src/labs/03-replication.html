Lab 03 — Replication, ISR and the durability line

Six steps in which you break three brokers on purpose. One question asked five ways: under which failures does Kafka lose an acknowledged write? Step 2 makes the high watermark visible, which is the thing most people only ever read about.

Expect 50-70 minutes. Keep two terminals open throughout — one watching the ISR, one doing things.

Setup

Broker ports clash with lab 01, so stop that first: cd ../lab01 && docker compose down.

cd labs/lab03-replication
docker compose up -d && docker compose ps     # three healthy, ~45s

docker exec lab03-kafka1 /opt/kafka/bin/kafka-topics.sh \
  --bootstrap-server localhost:9092 \
  --create --topic lab03.durable --partitions 1 --replication-factor 3 \
  --config min.insync.replicas=2

python3 -m venv .venv
source .venv/bin/activate                     # in BOTH terminals
pip install -r requirements.txt
cd scripts

One partition on purpose: one leader, two followers, nothing else moving while you break things.

STEP 1Get the ISR on screen and leave it there

Proves: the ISR is a live set, not a configuration value.

Run — terminal A, and leave it running for the whole lab

python3 03_watch_isr.py 900

It prints only when something changes, so a quiet screen means a healthy cluster.

Expected

[14:02:11] p0 leader=2 replicas=[1, 2, 3] isr=[1, 2, 3]

Why

Three replicas, all in sync, one of them leader. Replicas is the fixed assignment made when the topic was created; isr is who is keeping up right now. Everything in this lab is about the gap between those two lists, and almost every durability question in an interview reduces to how large the ISR was at the moment of failure.

Check yourself

With min.insync.replicas=2 and this ISR, how many brokers can you lose before acks=all writes stop being accepted? Write the number down — step 4 checks it.

STEP 2Pause a follower and watch the high watermark stall

Proves: consumers cannot read past the high watermark, and the HW is held back by the slowest in-sync replica.

Predict first

You will freeze one follower, then produce one record with acks=1 — so the leader acknowledges without waiting for anyone. The producer gets a successful response and an offset. Can a consumer read that record? Answer before running it.

Run — terminal B

# find a follower (anything in isr that is not the leader) from terminal A
docker pause lab03-kafka3

python3 02_watch_hw.py 1

Expected

produced hw-probe-9f2c41a8 at offset 12 with acks=1
now polling as a consumer until it becomes readable...
    1.0s  not readable yet
    2.0s  not readable yet
  ...
   31.4s  readable after 31.4s

Why

The record was on the leader's disk the whole time, with an offset the producer already knew. It was not readable because the high watermark — the minimum log end offset across the in-sync replicas — could not advance past the frozen follower, which was still in the ISR and still at its old offset.

That is the guarantee working. A record only on the leader is not durable: if the leader died now, a follower that never received it would be promoted and the record would be gone. Serving it would let a consumer read something that later ceases to exist, making the log appear to go backwards. So reads stop at the HW, and anything a consumer can see has reached every in-sync replica.

It became readable at ~30s because that is when replica.lag.time.max.ms expired and the leader evicted the frozen follower from the ISR. With a smaller ISR, the minimum LEO jumped forward and the HW with it. You just watched durability and availability trade places on a timer.

Check yourself

The producer was told the write succeeded at offset 12, thirty seconds before any consumer could see it. Is there any acks setting where the acknowledgement and the readability happen at the same moment? What does that tell you about using produce latency as a proxy for end-to-end latency?

STEP 3Watch the ISR shrink, then expand

Proves: ISR membership is a timer, and it is the early-warning signal in production.

Run

# terminal A should already have printed the shrink during step 2:
#   p0 leader=2 replicas=[1, 2, 3] isr=[1, 2]

docker exec lab03-kafka1 /opt/kafka/bin/kafka-topics.sh \
  --bootstrap-server localhost:9092 --describe --under-replicated-partitions

docker unpause lab03-kafka3

Expected

The under-replicated query lists the partition while the follower is out. After unpausing, terminal A shows the ISR returning to [1, 2, 3] within a few seconds — rejoining is fast, because the follower only has to catch up on what it missed.

Why

A follower stays in the ISR while it has fetched up to the leader's log end offset within replica.lag.time.max.ms (default 30 s). A GC pause, a slow disk, a saturated link or a restart pushes it out; catching up puts it back. Nothing was reconfigured here — a frozen process looks exactly like a very slow one.

In production the metric to alert on is not the shrink itself but the rate: IsrShrinksPerSec flapping is the early warning that fires before anything else does, and it usually means GC, disk or network rather than a broker that is actually down.

Check yourself

Why does Kafka use a time threshold rather than a message-count threshold for ISR membership? (It used to have both. Think about what a sudden burst of traffic does to a count-based threshold on a perfectly healthy follower.)

STEP 4Kill brokers until acks=all is refused

Proves: min.insync.replicas turns a silent degradation into a loud rejection.

Predict first

Three replicas, min.insync.replicas=2. You kill one broker, then a second. At which point does an acks=all producer start failing, and what error does it get?

Run

python3 01_produce_acks.py all 5        # baseline: all healthy

docker stop lab03-kafka3
python3 01_produce_acks.py all 5        # ISR = 2, still at the floor

docker stop lab03-kafka2
python3 01_produce_acks.py all 5        # ISR = 1, below the floor

Expected

acks=all: producing 5 records to lab03.durable
  FAILED:    5
    KafkaError{code=NOT_ENOUGH_REPLICAS,...}

If the leader was on a broker you stopped, you will see a leader election first and a brief retry; the end state is the same.

Why

With one broker down the ISR is exactly 2, which equals min.insync.replicas — writes still succeed, but there is no margin left. With two down the ISR is 1, below the floor, and the leader rejects the write with NOT_ENOUGH_REPLICAS.

This is the setting earning its place. Without it, acks=all would be satisfied by the leader alone — because "all" means all replicas in the ISR, not all replicas — so it would silently become acks=1 at exactly the moment the cluster is least healthy, with no error anywhere. min.insync.replicas converts that silent degradation into a visible failure.

The sentence worth keeping: Kafka's durability story is to refuse writes rather than lose them. A rejected produce here is the system doing its job.

Check yourself

Someone proposes min.insync.replicas=3 on this RF-3 topic for "maximum safety". What actually happens the first time any single broker restarts for a routine upgrade?

STEP 5acks=1 succeeds — and that is the problem

Proves: the loss window is an acknowledged write with no second copy.

Run — with two brokers still down

python3 01_produce_acks.py 1 5

Expected

All five delivered, with offsets. No error, no warning.

Why

The leader wrote to its own log and answered. There is exactly one copy of these five records in the cluster, and the producer was told they are safe. If this broker's disk fails now, or if it is the one that does not come back, those records are gone — and nothing upstream will ever know, because the write was acknowledged.

That is the entire argument for acks=all plus min.insync.replicas. Not that acks=1 is slow or sloppy, but that it fails silently: the failure mode is a successful response. Compare the two commands you just ran — one errored loudly with everything intact, one succeeded quietly with data at risk. Most incidents are the second shape.

Check yourself

A team sets acks=1 because acks=all "added latency". From M3 and from step 2, give them two numbers they should measure before accepting that trade — and name the question they have not asked.

STEP 6Heal the cluster, then put leadership back

Proves: recovery is not finished when the brokers come back.

Run

docker start lab03-kafka2 lab03-kafka3
# watch terminal A: isr goes [1] -> [1,2] -> [1,2,3]

docker exec lab03-kafka1 /opt/kafka/bin/kafka-topics.sh \
  --bootstrap-server localhost:9092 --describe --topic lab03.durable

docker exec lab03-kafka1 /opt/kafka/bin/kafka-leader-election.sh \
  --bootstrap-server localhost:9092 --election-type preferred --all-topic-partitions

Expected

The ISR refills one broker at a time. The leader is probably not the first entry in Replicas any more — it stayed with whichever broker survived. The preferred election moves it back.

Why

Leadership does not return on its own when a broker recovers; it stays where the failover put it. After a few incidents, leaders pile onto whichever brokers happened to survive, and that broker now serves all the traffic for those partitions while others idle. auto.leader.rebalance.enable (default true) corrects this periodically, and kafka-leader-election.sh --election-type preferred forces it now.

An unbalanced cluster is a throughput and latency problem long before it is an availability one, which is why it is easy to miss — nothing is broken, the cluster is just quietly using a third of itself.

Check yourself

You have run a rolling restart across all three brokers. Nothing failed, every partition is fully replicated. Why might p99 produce latency still be worse afterwards than before, and what one command would you run?

Not in this lab: unclean leader election

Demonstrating it means destroying data in a way that is fiddly to stage and teaches nothing you cannot reason out. The scenario: every in-sync replica is gone and only a stale replica remains. With unclean.leader.election.enable=false (the default, and set explicitly in this compose file) the partition goes offline and stays offline until an in-sync replica returns — no acknowledged write is lost, and availability is gone for as long as that takes. With true, the stale replica is promoted immediately, writes resume, and every record beyond its log end offset is permanently gone; consumers that already read them see the log move backwards.

Confirm what your cluster would do:

docker exec lab03-kafka1 /opt/kafka/bin/kafka-configs.sh --bootstrap-server localhost:9092 \
  --describe --entity-type brokers --entity-name 1 --all | grep unclean

The interview answer is per topic class, not a preference: clickstream and metrics where a gap is survivable and downtime is not — enable it; a payment ledger or anything another system reconciles against — never, take the outage. The dimension is whether a downstream consumer treats the log as a source of truth.

docker compose down -v
