Lab 05 — Producer internals

Six experiments about what happens before the broker sees a byte. Every one of them is measurable on disk or on the clock, which is the point: producer tuning is full of folklore, and these numbers are yours.

Expect 45-60 minutes. One broker on port 9092 — stop lab 02 first.

Setup

cd labs/lab05-producer
docker compose up -d && docker compose ps
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
cd scripts
Read this before trusting any number here

The Python client is librdkafka, and several defaults differ from the Java client that interview answers quote: linger.ms is 5 not 0, enable.idempotence is off not on, and the producer's record-size cap is called message.max.bytes rather than max.request.size. Every script sets what it depends on explicitly. This is worth knowing in itself — "the default is X" is a statement about a client, not about Kafka.

STEP 1linger.ms, and what lands on disk

Proves: batching is real and measurable — and that linger.ms=0 still batches.

Predict first

2000 records of 200 B, once with linger.ms=0 and once with 50. How many batches do you expect on disk in each case — 2000 and a handful, or something else? Write both numbers down.

Run

for t in lab05.linger0 lab05.linger50; do
  docker exec lab05-kafka /opt/kafka/bin/kafka-topics.sh --bootstrap-server localhost:19092 \
    --create --topic $t --partitions 1 --replication-factor 1
done

python3 01_batching.py lab05.linger0  0
python3 01_batching.py lab05.linger50 50

for t in lab05.linger0 lab05.linger50; do
  printf "%s batches: " "$t"
  docker exec lab05-kafka /opt/kafka/bin/kafka-dump-log.sh --print-data-log \
    --files /tmp/kraft-combined-logs/$t-0/00000000000000000000.log | grep -c baseOffset
done

Expected

Far fewer than 2000 batches in both cases. linger.ms=50 produces fewer still, but linger.ms=0 is nowhere near one record per batch.

Why

This is the part people get wrong. linger.ms=0 does not mean "send each record immediately" — it means "do not wait". While a request is in flight to the broker, records keep accumulating in the accumulator, and the next request takes everything that arrived meanwhile. Under load, batching is driven by the in-flight window, not by the timer.

So what does linger.ms actually buy? Bigger batches at low load, where there is nothing in flight to accumulate behind and each record would otherwise go alone. It is a latency floor traded for batch size exactly when traffic is thin.

Look at a batch header in the dump: the count: field is records in that batch. That number, not the record count, is what the broker handles as one unit.

Check yourself

Your producer sends 10 records a second in bursts of one. Does raising linger.ms to 50 help throughput, latency, storage, or none of them? Now the same question at 50,000 records a second.

STEP 2Three codecs, measured in bytes

Proves: compression is per batch, and the choice is a real number rather than a preference.

Predict first

5000 copies of the same ~120-byte JSON record. Roughly how much disk does none use? And what ratio do you expect from zstd on data this repetitive — 2×, 5×, 20×?

Run

for c in none lz4 zstd; do
  docker exec lab05-kafka /opt/kafka/bin/kafka-topics.sh --bootstrap-server localhost:19092 \
    --create --topic lab05.comp-$c --partitions 1 --replication-factor 1
  python3 02_compression.py $c
done

docker exec lab05-kafka du -sh /tmp/kraft-combined-logs/lab05.comp-*/

Expected

A large gap between none and either codec, and a smaller one between lz4 and zstd. The exact ratios depend on your payload; identical repeated records compress absurdly well, so treat the direction as the lesson and the magnitude as specific to this data.

Why

Compression applies to the batch, so step 1 and step 2 are the same lever: bigger batches compress better, which means linger.ms is a storage-cost setting as much as a latency one. A producer with linger.ms=0 at low load pays twice — more requests and worse ratios.

And from M2: the broker stores these bytes exactly as framed, as long as the topic is left at compression.type=producer. Set a codec on the topic instead and the broker decompresses and recompresses every batch — paying CPU and losing zero-copy. Compression belongs on the producer.

Check yourself

Your cross-AZ replication bill is the problem, not disk. Does switching from lz4 to zstd help? (Think about what crosses the AZ boundary and in what form.)

STEP 3Exhaust the buffer and time the block

Proves: send() is asynchronous until it is not.

Predict first

The producer buffer is capped at 500 messages. You produce 20,000 as fast as Python can. What does send() do when the buffer is full — drop, throw immediately, or something else?

Run

python3 03_buffer_block.py

# then the extreme version, with nothing draining the buffer at all
docker stop lab05-kafka
python3 03_buffer_block.py
docker start lab05-kafka

Expected

Lines reporting send() blocked NNNms, then a BufferError once max.block.ms is exceeded. With the broker stopped, it blocks almost immediately and gives up quickly.

Why

The accumulator is a fixed memory pool — buffer.memory in the Java client, 32 MiB by default. When it fills, send() blocks for up to max.block.ms (60 s by default) and then throws. It does not drop and it does not grow.

That makes it a backpressure mechanism, and it is the most commonly misdiagnosed symptom in this whole course: "the service got slow and we don't know why" is frequently a producer blocked on buffer memory, propagating broker backpressure into application latency through a call everyone assumes returns instantly. The tell is request latency rising in a service doing no more work than usual.

One more trap: max.block.ms also covers waiting for topic metadata. A producer writing to a topic that does not exist blocks in exactly the same way, with a completely different cause.

Check yourself

A service has a 200 ms SLA and a producer with default settings. A broker becomes slow for 90 seconds. What does the service's p99 look like, and which setting would you change to make the failure fast instead of slow?

STEP 4What idempotence writes into the log

Proves: the PID and sequence numbers you have been seeing since lab 01 are the dedupe mechanism.

Run

python3 04_idempotence.py on
python3 04_idempotence.py off

for m in on off; do
  echo "=== idempotence $m ==="
  docker exec lab05-kafka /opt/kafka/bin/kafka-dump-log.sh --print-data-log \
    --files /tmp/kraft-combined-logs/lab05.idem-$m-0/00000000000000000000.log | head -4
done

Expected

With idempotence on: a real producerId, a producerEpoch, and sequence values that increase batch by batch. With it off: producerId: -1 and sequence: -1.

Why

The broker keeps the last sequence number per (producerId, partition). A batch whose sequence it has already seen is acknowledged and discarded — the duplicate never reaches the log. A batch arriving ahead of the expected sequence is rejected with OutOfOrderSequenceException. So the broker enforces dedupe and ordering together, which is precisely why idempotence makes max.in.flight up to 5 safe instead of forcing it to 1.

With producerId: -1 the broker has nothing to compare against. A retried batch is simply a new batch, written again.

And the limit worth saying out loud: the PID belongs to a producer session. Restart the process and it gets a new one, so the broker cannot recognise anything the previous instance wrote. Idempotence makes a retry safe; it does not make a crash-and-replay safe. That gap is what transactions close, in M7.

Check yourself

Your service produces a record, crashes before the response arrives, restarts, and produces the same record again. How many copies are in the log, and why does idempotence not help?

STEP 5retries is not the limit

Proves: delivery.timeout.ms bounds the attempt; retries mostly does not.

Predict first

retries=3, retry.backoff.ms=200, delivery.timeout.ms=8000, and the broker is down. How long until the callback reports failure — under a second, or about eight?

Run

docker stop lab05-kafka
python3 05_retry_timeout.py
docker start lab05-kafka

Expected

About eight seconds. Three retries at 200 ms of backoff would be well under one.

Why

retries defaults to Integer.MAX_VALUE and has not been the practical limit since delivery.timeout.ms was introduced. The timeout bounds the whole attempt — initial send, every retry, every backoff — from send() to a terminal callback.

So setting retries=3 to "fail fast" does nothing useful, and can do harm: it gives up on a transient leader election that would have resolved in two seconds, while the surrounding timeout structure still governs how long the caller waits. If you want the producer to give up after ten seconds, set delivery.timeout.ms=10000. That is the whole answer.

Check yourself

You want at-most-5-second produce latency with no silent loss. Which settings do you change, and what must your application do when the callback reports a timeout? (Note that a timeout is not proof the record was not written.)

STEP 6Two size limits, in two places

Proves: raising one limit moves the failure rather than removing it.

Run

docker exec lab05-kafka /opt/kafka/bin/kafka-topics.sh --bootstrap-server localhost:19092 \
  --create --topic lab05.size --partitions 1 --replication-factor 1

python3 06_too_large.py 2048

Expected

With the client limit at 1 MB, a 2 MiB record is rejected before leaving the process. With the client limit at 4 MB, the record crosses the network and the broker rejects it, because message.max.bytes is still ~1 MiB.

Why

Two independent limits: max.request.size on the producer and message.max.bytes on the broker or topic. Each is checked in its own place, and raising only one relocates the error rather than fixing it — now with a wasted network round trip and a less obvious message.

The subtlety that makes this intermittent in production: the limit applies to the compressed batch, not the individual record. A record that fits alone can fail when batched with others, and whether it does depends on timing and on how well that batch happened to compress. Same payload size, different outcome, which is maddening to debug without knowing this.

And the consumer side has to match — fetch.max.bytes and max.partition.fetch.bytes. A message too large for a consumer to fetch does not raise an error; the consumer stalls on it forever. An error is the good outcome.

Check yourself

A team needs to send 5 MB payloads. List what has to change, on all three sides — and then give the alternative design a senior engineer would propose first.
