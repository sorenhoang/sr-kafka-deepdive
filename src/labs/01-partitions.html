Lab 01 — Partitions, consumer groups and ordering

Seven steps, each one proving a single claim from the notes. Every step asks you to predict the output before running it — that prediction is where the learning happens, so do not skip it. Reading the result afterwards only confirms what you already saw.

Expect 40-60 minutes. Nothing here depends on a previous lab.

Setup

cd labs/lab01
docker compose up -d
docker compose ps          # all three nodes must say healthy — 30-60s

python3 -m venv .venv
source .venv/bin/activate  # once per terminal, step 4 needs four of them
pip install -r requirements.txt
cd scripts

Kafka UI at http://localhost:8080 if you want to watch the same thing in a browser. Bootstrap from the host is localhost:19092,localhost:29092,localhost:39092.

STEP 1Cluster up, and read describe properly

Proves: a partition — not a topic — is the unit of replication, and leadership is spread across brokers so that writes scale.

Predict first

You are about to create a topic with 3 partitions and replication factor 3 on a 3-broker cluster. How many partition replicas exist in total across the cluster? How many of them accept writes?

Run

docker exec kafka1 /opt/kafka/bin/kafka-topics.sh \
  --bootstrap-server localhost:9092 \
  --create --topic lab01.orders --partitions 3 --replication-factor 3

docker exec kafka1 /opt/kafka/bin/kafka-topics.sh \
  --bootstrap-server localhost:9092 --describe --topic lab01.orders

Expected

Topic: lab01.orders  Partition: 0  Leader: 2  Replicas: 2,3,1  Isr: 2,3,1
Topic: lab01.orders  Partition: 1  Leader: 3  Replicas: 3,1,2  Isr: 3,1,2
Topic: lab01.orders  Partition: 2  Leader: 1  Replicas: 1,2,3  Isr: 1,2,3

Which broker leads which partition will differ on your run — that assignment is made when the topic is created. What must hold is the shape: three lines, three replicas each, Isr identical to Replicas, and the leaders spread across all three brokers rather than piled on one.

Why

Nine replicas exist (3 partitions × 3 copies) and exactly three of them accept writes — one leader per partition. That is the answer to the prediction, and it is also the reason Kafka scales writes: a producer sending to this topic is talking to three brokers at once, one per partition. A topic with one partition, however many replicas, writes to exactly one broker.

Replicas is ordered by preference; the first entry is the preferred leader, the one Kafka returns to after a failure heals. Isr is the set currently keeping up. Equal lists mean a healthy cluster — you will see them diverge in M3.

Check yourself

If you created this topic with --partitions 1 --replication-factor 3, how many brokers would serve its writes? What would that do to the cluster's write throughput for this topic?

STEP 2Produce without a key

Proves: keyless records are batched by the sticky partitioner, not round-robined one at a time.

Predict first

Twelve records, no key, three partitions. Write down the split you expect before running. Most people write 4 / 4 / 4.

Run

python3 01_produce_no_key.py

Expected

Not 4 / 4 / 4. You will typically see most or all twelve land on one partition, or a lopsided split like 12/0/0 or 7/5/0. The exact numbers vary between runs and that variation is itself the point.

Why

With a null key the producer uses the sticky partitioner: it picks one partition and keeps filling the same batch until the batch reaches batch.size or linger.ms expires, and only then switches to another partition. Twelve small records produced in a tight loop fit comfortably inside one batch, so they go to one place.

This is a throughput optimisation. One batch to one partition is one request to one broker; round-robin per record would mean three requests of four records each, three times the request overhead for the same data. Kafka chose fewer, larger requests — and it can, because without a key you have declared that you do not care where records land.

Check yourself

Open 01_produce_no_key.py and change "linger.ms": 0 to 50, then re-run. Does the distribution get more or less even, and why? Then consider: if your consumers lag on one partition and that topic has null keys, is the partitioner the cause or a symptom?

STEP 3Produce with a key

Proves: a key maps to a partition deterministically, and that mapping is the only ordering mechanism Kafka offers.

Predict first

Five keys, three records each. Will the three records for user-1 land on the same partition? Will user-1 and user-2 land on the same one? Will the five keys be distributed evenly across the three partitions?

Run

python3 02_produce_with_key.py

Expected

user-1   -> partition [2]  ok (stable)
user-2   -> partition [2]  ok (stable)
user-3   -> partition [2]  ok (stable)
user-4   -> partition [1]  ok (stable)
user-5   -> partition [1]  ok (stable)

Every key lands on exactly one partition — that is deterministic and will match on any cluster, because it is pure arithmetic on the key bytes. But the spread across partitions is not even, and with five keys it can easily leave one partition empty.

Why

partition = toPositive(murmur2(keyBytes)) % numPartitions

A hash, nothing more. Same key, same bytes, same partition, forever — no state is kept anywhere, which is why any producer in any language agrees without coordinating. Even distribution is a statistical property of having many keys, not a guarantee; a handful of keys can collide on one partition, and a single very hot key puts all of its traffic on one broker no matter how many partitions you have. That is the hot partition problem, and M10 comes back to it.

Check yourself

Open the partition calculator on the notes page and enter user-1 with 3 partitions. Does it agree with what the cluster just did? It should, byte for byte — and that is worth confirming, because it means you can reason about key placement without a broker in front of you.

STEP 4Consumer group assignment and rebalance

Proves: one partition goes to exactly one consumer in a group, so partition count is the parallelism ceiling; and separate groups are fully independent.

Predict first

Three partitions. You will start consumers one at a time in the same group. Write down what each of the first three gets. Then: what does the fourth get? And when the fourth joins, does anything happen to the first three?

Run

Four terminals, each with its own source .venv/bin/activate. Start them one at a time and read the output of the ones already running before you start the next.

# terminal 1
python3 03_consumer_group.py g1 c1
# terminal 2, after c1 has printed its assignment
python3 03_consumer_group.py g1 c2
# terminal 3
python3 03_consumer_group.py g1 c3
# terminal 4 — three partitions, four consumers
python3 03_consumer_group.py g1 c4

Expected

[c1] ASSIGNED  -> [0, 1, 2]      # alone, it owns everything
[c1] REVOKED   -> [0, 1, 2]      # c2 joins: rebalance
[c1] ASSIGNED  -> [0, 1]
[c2] ASSIGNED  -> [2]
...
[c4] ASSIGNED  -> NO PARTITIONS (idle)

The important detail is the REVOKED line on the existing consumers. A new member does not simply take a free partition — the whole group stops, gives everything back, and is reassigned.

Why

Each partition is owned by exactly one consumer in a group, so the fourth consumer has nothing to own and sits idle. Adding processes past the partition count buys you nothing; the only way up is more partitions, which step 6 shows is a one-way door.

The stop-the-world revoke is the cost of a rebalance, and in production it is what makes a flapping consumer expensive: every flap pauses the entire group. Cooperative sticky assignment and the newer KIP-848 protocol exist to shrink exactly this window — M6.

Then run, while the group is live

docker exec kafka1 /opt/kafka/bin/kafka-consumer-groups.sh \
  --bootstrap-server localhost:9092 --describe --group g1

This is the view you will actually use in production: which consumer owns which partition, the committed offset, the log end offset, and the lag between them. Learn to read it now, while you know what the right answer looks like.

Then: a second group

python3 03_consumer_group.py g2 x1

g2 replays everything from the beginning while g1 is still running and entirely unaffected. One topic is serving a queue (consumers inside g1 splitting work) and a pub/sub fan-out (g1 and g2 both seeing all records) at the same time, with no exchange and no copy of the data. Progress for each group lives in __consumer_offsets keyed by (group.id, topic, partition).

Check yourself

Kill c2 with Ctrl+C and watch the other terminals. How long before its partition is reassigned, and what decides that delay? (Look up session.timeout.ms — then note that a consumer that leaves cleanly announces itself, while one that is killed hard must be timed out.)

STEP 5Ordering: inside a partition vs across the topic

Proves: "Kafka preserves order" is only ever true at partition scope.

Predict first

Two keys, A and B, five numbered events each, produced strictly alternating: A-0, B-0, A-1, B-1, and so on. When one consumer reads the whole topic, will it see them in that produced order?

Run

docker exec kafka1 /opt/kafka/bin/kafka-topics.sh --bootstrap-server localhost:9092 \
  --create --topic lab01.orders.ordering --partitions 3 --replication-factor 3
python3 04_ordering_demo.py

Expected

The consumer drains one partition before moving to the next, so you see all of A's events together and all of B's together — not the interleaving you produced. Within each key the sequence numbers are strictly increasing.

Why

Each partition is a separate file and a separate fetch. There is no shared clock and no global sequencer, so "the order records were produced in" across partitions is not information Kafka has — and could not provide without serialising every write through one broker, which is the throughput it exists to avoid.

What it does guarantee is per-key order, because the key pinned both A's events to one partition and B's to another. That is the whole trick, and the sentence worth memorising: order at partition scope; to get order at business-entity scope, key by entity id, enable the idempotent producer, and process each partition sequentially.

Check yourself

Suppose a bug report says "the cancel event was processed before the create event for order 42". Given everything above, name three places that could have gone wrong — only one of which is Kafka's doing.

STEP 6Grow the topic and watch ordering break

Proves: increasing the partition count moves keys, and it cannot be undone. This is the step that matters most in this lab.

Predict first

Before running anything: of ten keys, how many do you expect to change partition when the topic goes from 3 to 6? And will Kafka let you go back from 6 to 3?

Run — offline prediction first

python3 05_key_remap.py        # no broker needed, pure arithmetic
key         3 parts  6 parts   moved?
user-1            2        2   -
user-3            2        5   YES -> ordering lost
user-5            1        4   YES -> ordering lost
user-8            0        3   YES -> ordering lost
...
5/10 keys changed partition going from 3 -> 6

Then confirm against the real cluster

docker exec kafka1 /opt/kafka/bin/kafka-topics.sh --bootstrap-server localhost:9092 \
  --alter --topic lab01.orders --partitions 6
python3 02_produce_with_key.py

Compare the key-to-partition mapping printed now against what step 3 printed. It should match the script's prediction exactly, because both are computing the same hash.

Then try to go back

docker exec kafka1 /opt/kafka/bin/kafka-topics.sh --bootstrap-server localhost:9092 \
  --alter --topic lab01.orders --partitions 3

Kafka refuses. Read the error text rather than skimming it.

Why

The partition count is the divisor in hash(key) % numPartitions, so changing it rewrites the mapping for roughly half the keys. Nothing moves the existing records, though: user-3's history stays on partition 2 while its new events go to partition 5. A consumer following that key now sees a gap and then a fresh sequence, in no relation to each other.

Shrinking is refused because each partition is its own log with its own offset sequence. Merging two logs would mean inventing offsets that consumers have already committed against, and there is no correct answer to what the merged order should be. So partition count only ever goes up, and the increase itself is a breaking change for ordered consumers.

In production this means: pick the partition count with growth in mind at creation time, and when you really must resize an ordered topic, create a new one and migrate deliberately rather than running --alter.

Check yourself

Your team needs to go from 6 to 24 partitions on a topic keyed by user_id, and ordering per user is a business requirement. Sketch the migration. Where does the cutover happen, and what is the window during which ordering cannot be guaranteed?

STEP 7Look at the log on disk

Proves: a partition really is a file, and sets up everything in M2.

Run

docker exec kafka1 ls -la /tmp/kraft-combined-logs/lab01.orders-0/

docker exec kafka1 /opt/kafka/bin/kafka-dump-log.sh \
  --files /tmp/kraft-combined-logs/lab01.orders-0/00000000000000000000.log \
  --print-data-log | head -20

What to notice

  • The directory is named <topic>-<partition>. There is no directory for the topic itself — the topic is a name in metadata, nothing more.
  • .log holds the records; .index maps offsets to byte positions; .timeindex maps timestamps to offsets. The filename is the base offset of the segment, zero-padded — which is how Kafka finds the right file for an offset without scanning.
  • In the dump: baseOffset, lastOffset, count, producerId, isTransactional. Note that records arrive in batches — the batch, not the record, is the unit the broker stores and ships.

Those three fields are the thread into the next three modules: the segment and index files are M2, producerId is the idempotent producer in M5, and isTransactional is exactly-once in M7.

Tear down

docker compose down -v

The -v removes the volumes. Without it the next up finds an old CLUSTER_ID and the brokers refuse to form a quorum — the most common way this lab fails on a second run.

When something goes wrong

SymptomCause and fix
ModuleNotFoundError: No module named 'confluent_kafka'The venv is not active in this terminal. source .venv/bin/activate, then confirm with which python3 — it must point inside .venv.
A node never reports healthydocker compose logs kafka1 | tail -50. Almost always a stale CLUSTER_ID in an old volume: docker compose down -v and start again.
Producer hangs or times outThe brokers advertise localhost:19092/29092/39092 to the host. If you changed the ports in docker-compose.yml, KAFKA_ADVERTISED_LISTENERS has to change with them.
Consumer prints nothingIt has already committed past these records under that group id. Use a new group.id, or reset: kafka-consumer-groups.sh --group g1 --topic lab01.orders --reset-offsets --to-earliest --execute with no live members.
Rebalance seems instant, unlike productionKAFKA_GROUP_INITIAL_REBALANCE_DELAY_MS: 0 is set deliberately so the lab does not make you wait. Never 0 in production.

Done when

You can answer these without looking anything up: why twelve keyless records do not split evenly; why a fourth consumer on three partitions is useless; why half the keys move when a topic grows; and why Kafka refuses to shrink one. If any of the four is shaky, the step that proves it is worth running a second time — the commands are cheap, the prediction is the expensive part.
